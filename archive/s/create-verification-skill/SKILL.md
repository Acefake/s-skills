# 创建一个验证 skill

每个正经的项目都需要一种用脚本操作真实应用、证明其行为的办法：启动它，像用户那样使用某个功能，并采集证据。这个 skill 会生成这样一个放在项目里的 skill（`.cursor/skills/verify-<app>/`），并针对这个仓库量身定制。你写的生成结果是给下一个智能体看的，而不是给人看的：读它的会是一个从没见过这个应用、正在任务中途、毫无背景的智能体。

## 1. 去问仓库，而不是去问用户

从代码库里回答这些问题，只有你观察不到的才去问用户：

- **界面（Surface）：** 用户实际接触的是什么？网页界面、命令行/终端界面（CLI/TUI）、桌面应用、API、手机应用，还是一个库？一个仓库可能有好几种；选出主要的那个，记下其余的。
- **运行（Run）：** 应用在本地怎么启动？优先用仓库自己写明的开发命令（package 脚本、Makefile、README 里的快速上手）。记下端口、环境变量、种子数据、登录认证。
- **操作（Drive）：** 智能体怎样用程序和它交互？先找已有的测试工具：Playwright/Cypress 测试、expect 脚本、PTY 辅助工具、可以用 curl 访问的接口、一个调试端口。没有的话，再选一个通用的做法：网页和 Electron 用浏览器/CDP，命令行/终端界面用 tmux/PTY 测试工具，服务用普通的 HTTP。
- **观察（Observe）：** 能采集哪些证据？截图、终端记录、响应内容、日志、退出码、数据库状态。
- **隔离（Isolate）：** 两个实例能不能并排运行（端口、数据目录、配置档）？如果不能，就在生成的 skill 里写明：拒绝同时操作一个共享实例，总比弄坏用户的会话强。

如果检出的代码原样没法构建或启动，先修好它（或者准确地报告问题），再去生成；在一个坏掉的基础上写出来的 skill，会教出错误的步骤。如果是一个无关紧要的缺失文件挡住了启动（一个 API 从来不提供的静态目录、一个示例配置），生成的 skill 可以创建它，但要清楚地标明这是验证用的脚手架，并在清理时删掉它。

## 2. 生成 skill

写出 `.cursor/skills/verify-<app>/SKILL.md`，带上 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，写明应用名、界面类型，以及什么时候该用它；没有 frontmatter，这个 skill 永远不会被注册），并包含下面这些部分，每一部分都要基于访问中实际发现的东西（不能留下任何占位符）：

- **Launch（启动）：** 为验证而启动应用的确切命令，以及怎么判断它已经准备好了（一行日志、一个提示符）。启动必须能从一个空的数据目录到达可用状态，包括所有的迁移和种子数据。准备好的意思是可以用，而不只是某个进程有响应。数据库的健康检查可能已经通过，而它的初始化脚本还在运行。要包括关闭步骤。对于短命的命令行或终端界面工具，没有需要保持运行的服务器：启动的意思是先构建一次可执行文件（或安装依赖），然后每次操作都在它自己隔离的 PTY 或 tmux 会话里开始。
- **Doctor（健康检查）：** 一个只读的检查，回答“这个实例值得操作吗？”：进程在运行、版本/构建正确、端口归我们所有、登录有效。只要有任何地方看起来不对，智能体就先运行这个。
- **Drive（操作）：** 测试工具的做法，用这个仓库里真实的选择器/命令，而不是示例。优先用稳定的标识（ARIA 标签、data 属性、提示字符串、路由路径），而不是坐标和 Tab 键顺序。
- **Evidence（证据）：** 一次证明要采集什么、放到哪里。写明证明的标准：走真实的用户路径，而不是内部的 setter 或只供测试用的接口；采集动作和由此产生的状态，而不只是最后的画面；在检查看得见的东西的同时，也验证副作用（写入的文件、插入的数据行、发出的消息）；只有在生产环境本来就有边界把外部系统隔离开的地方，才能用模拟。如果安全的路径是一个试运行（dry-run）或测试模式，要通过观察（文件、网络、git 引用）来验证它实际跳过了什么，而不是相信它的名字：有些试运行仍然会访问网络或打开浏览器。
- **Cleanup（清理）：** 怎样关闭这次运行创建的实例。永远不要按进程名去杀进程；杀你自己启动的那些。清理会删除实例和临时状态，但永远不删证据：证明用的产物在关闭之后仍然保留，放在 skill 指定的位置。
- **Helpers（辅助脚本）：** 这个 skill 附带的任何脚本都是可执行的，它的调用方式写在 skill 正文里。一个需要读者去反向推敲的辅助脚本，就不算辅助脚本。

## 3. 播下功能地图的种子

创建 `.cursor/skills/verify-<app>/features/README.md`，再为你能识别出的每个面向用户的功能各建一个文件（一开始先做最重要的 3-5 个，从路由、命令、菜单或文档里找）。按照 [`references/feature-map-example/`](references/feature-map-example/) 里的形状来做：一个 README 索引，加上每个功能一个文件。每个文件都从用户的角度回答：这个功能是什么、怎么到达它、怎么用测试工具操作它，以及什么样的可观察的最终状态能证明它是好的。四个二级标题是 `Sub-features`（子功能）、`How to get to it (user POV)`（怎么到达，用户视角）、`Driving it with <harness>`（用某测试工具操作它）和 `Gotchas`（容易踩的坑）。如果种子数据缺少某个使用流程需要的前提条件，这个流程就报告失败，原因写进那个功能的 `Gotchas`。永远不要为了让流程通过而削弱它。这份地图是仓库里持续维护的验证来源；如果地图列出了多个入口，只操作其中一个方便的入口，证明就不完整。

## 4. 交出去之前，先证明生成的 skill 是好的

把它自己的指示从头到尾跑一遍：启动、doctor、操作地图里的一个功能（一个就够了；地图存在的意义，就是让以后的运行去覆盖其余的）、采集证据、清理。清理之后，确认证据仍然在指定的位置；如果清理把证明吃掉了，这一步就算失败。修好失败的地方，并且在每一次失败的迭代之后也运行生成的清理步骤，免得失败的尝试留下没关掉的进程和端口。一个从来没被执行过的生成 skill，只是草稿，不是交付物。如果你是在一个替代品上证明它的（用一个容器代替一台全新的虚拟机，用一个本地环境代替一个远程环境），就列出替代品上做过、而真实目标上不会做的每一个设置步骤。在真实目标上的一次运行覆盖它们之前，这些步骤都算未验证。

## 5. 提供维护循环

告诉用户可以用 `/maintain-verification-skill` 在应用变化时让地图保持真实。只有在用户问起时，才建议多久做一次。
