# 纠错

操作者在这个仓库里一直在因为同样的错误纠正智能体。改造这个仓库，让下一个智能体没法再犯这些错。

假设每个贡献者都是一个智能体：它只看到自己打开的文件，照抄离它最近的例子，走能编译通过的最短路径。要把仓库设计成：一个从单个文件看起来正确的改动，对整个仓库也是正确的。

## 找出错误的类别

首先，读最近的提交、回滚、审查意见、给智能体的指示文件，以及那些解释绕过办法的注释。把错误归成几类。一类错误发生过两次，就算数。

## 在能奏效的最高层级上修掉每一类

1. **用架构消除它。** 让每一份状态只有一个归属者，每一项任务只有一种受支持的做法。把内部实现藏起来，让错误的 import 直接失败。用唯一的事实来源代替靠手工同步的列表。删掉智能体可能会照抄的旧做法和死代码。
2. **用类型强制它，让坏状态根本写不出来。** 如果坏代码仍然能编译，就加一条 lint 或 CI 检查，它的报错要写明应该改用哪个文件、类型或函数。如果这种写法已经很普遍，只在一个改动又新增了这种写法时才让检查失败。
3. **测试行为。** 如果一个测试在它所检查的行为坏掉时仍然通过，或者只是内部实现改变时就失败，就修好它或者删掉它。
4. **最后才写文档或智能体规则，而且只用于需要判断的情况。** 智能体跳过它们时，什么都不会失败。

## 修复并证明

然后，现在就修掉最常见的几类，每类一个提交。证明每个新检查都能在一个真实的历史错误上失败。在本地和 CI 里运行同一条命令。例外要写在出问题的那一行上，附上理由、过期日期和一个人的批准。

## 维护规则表

最后，在给智能体的指示文件里维护一张表，把每条规则和强制执行它的东西对应起来。当操作者纠正你时，修掉这个错误，并加上这条规则。如果这条规则早就在表里、却没有东西强制执行它，那就是重犯，要在同一个改动里在最高层级上修掉。一旦某个错误已经不可能发生，就把对应的规则删掉。

**回复：** 每一类错误和它的证据、你选的层级，以及为什么更高的层级行不通。
