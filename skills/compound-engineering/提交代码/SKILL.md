# Git 提交

根据当前工作区（working tree，就是你本地改过的文件）做出写得好的本地提交（一个或多个）。不推送（push），不开 PR——要走完整的发布流程，请用 `提交推送开PR`。

**完成标准：** 每一组逻辑上的改动都用明确的文件清单和一条说明“结果是什么”的提交信息提交了，并且 `git status` 里已经没有这些改动。**停止条件：** 工作区是干净的（没有可提交的东西）。

## 了解现状

每条命令都单独作为**一次**shell 工具调用来收集信息（只写程序名和参数）。**不要**用 `;`、`&&`、`||`、管道、`$(...)` 或重定向把命令连起来——这些写法在 Windows PowerShell 下会失败。命令返回非零退出码是需要理解的正常情况，不是要掩盖的失败。

| 命令 | 用途 | 非零 / 空结果表示 |
| --- | --- | --- |
| `git status` | 工作区状态 | 不是 git 仓库——停下 |
| `git diff HEAD` | 还没提交的改动 | 仓库刚建、还没有任何提交 |
| `git branch --show-current` | 当前分支 | 空 = 处于游离 HEAD（detached HEAD，不在任何分支上） |
| `git log --oneline -10` | 最近的提交信息写法 | 仓库刚建——没有历史 |
| `git rev-parse --abbrev-ref origin/HEAD` | 远程仓库的默认分支 | 没有 `origin/HEAD` / 只返回 `HEAD`——试试 `gh repo view --json defaultBranchRef --jq '.defaultBranchRef.name'`，再不行就用 `main` |

把这些结果当作一张快照。如果中间可能有变化，就在提交前一刻重新看一下分支和已暂存的文件。

**默认分支名：** 去掉 `origin/HEAD` 结果开头的 `origin/`（所以 `origin/trunk` → `trunk`）。所有“是不是在默认分支上？”的检查都用这个去掉前缀的名字——绝不要和 `origin/<name>` 比较。

## 流程

0. **收集信息**——把上面“了解现状”里的每条命令都跑一遍（每条单独调用一次 shell），然后继续。

1. **没有可提交的东西**——如果 `git status` 显示没有已暂存、已修改或未跟踪的文件，就报告这一点然后停下。不要只用 `git diff HEAD` 判断干不干净（它看不到未跟踪的新文件）。

2. **先处理分支**——如果是游离 HEAD，或者在默认分支上（`main` / `master` / 上面得到的默认分支名），就根据改动内容新建一个功能分支（`git checkout -b <name>`），然后重新看一下 `git branch --show-current`。不要问——即使只是提交，也不能把工作只留在游离 HEAD 或默认分支上。如果起的名字已经存在，就加个不冲突的后缀。

3. **提交信息的写法规范**——如果上下文里已经有项目的提交规范，就照它来；没有就照最近提交记录的写法；再没有就用约定式提交（conventional commits，格式 `type(scope): description`）。用约定式提交时，如果 `fix` 和 `feat` 都说得通，默认用 `fix:`（修好坏掉或缺失的行为）；`feat:` 留给新功能。用户另有要求时，以用户为准。

4. **按逻辑拆分提交**——如果改动的文件明显属于不同的事情，就分开提交（只按文件拆分，最多 2–3 个，不用 `git add -p`）。拿不准时，就提交一次。

5. **提交信息**——标题用祈使句（命令语气），写出结果（现在能做什么了，或修好了什么），而不是文件清单。只有当动机或取舍从标题看不出来时，才写正文。如果手上已经有这次提交对应的计划实现单元编号（来自对话、调用方，或者这些文件都属于同一个单元），就在后面用括号加上这个 U-ID——`(U3)` 表示第 3 个单元。不要特意去找计划。如果这次提交跨了多个单元、单元不清楚，或者手上没有计划，就不加。

   - 不好：`Update checkout.rb` / `Add tests and fix stuff`
   - 好：`Fix double-submit on checkout`
   - 好：`Add per-subscription mute (U3)`

6. **暂存并提交**——只暂存**点名的文件**（绝不用 `git add -A` 或 `git add .`）。如果调用时带了 `exclude:<paths>`，就照办：不管其他地方改了什么，这些文件都保持不提交；在报告里说明它们被排除了。用你的写文件工具，把完整的提交信息——标题行、空一行、可选的正文——写到仓库外面的一个文件里，然后每组提交分两次调用来暂存和提交：

```bash
git add file1 file2 file3
```

```bash
git commit -F <message-file> -- file1 file2 file3
```

用 `-F` 时，没有任何 shell 会去解析提交信息：`$`、引号、反引号或多行正文，在任何 shell 下都会原样传过去，不用操心引号转义规则。git 平常的空白整理仍然会生效（去掉行尾空格，合并连续空行），这对提交信息没有影响。

`git commit` 后面那串文件路径是必须的：单独的 `git commit` 会提交整个暂存区（index），所以在这次运行之前就已经暂存的东西（调用方用 `exclude:` 排除的路径，或者用户自己暂存但没点名的工作）都会被一起带进提交。写明路径，就只提交这一组文件，暂存区里的其他内容不受影响。

7. **确认**——运行 `git status`；报告提交的哈希值（hash，提交编号）和标题。
