# 排查并修复

找出故障的根本原因（root cause），然后——在用户选择修复时——按“先写测试”的规矩修好它。

**完成标准：** 已经说清从触发点到症状的完整因果链，中间没有断档，并附有 文件:行号 的证据；同时，要么已经交接了一个验证过的修复（PR、提交，或用户选择停在哪一步），要么已经给出了一份“只诊断”的总结。**该升级就升级，不要硬撑：** 试了 2-3 个假设都没被证实，或者修了 3 次都失败，就要去诊断*为什么*，而不是再试一次——这就是 `references/investigate.md` 里说的聪明的升级方式。一次只验证一个假设、只做一个改动；同时改好几处看哪个管用，叫“霰弹枪式排查”（shotgun debugging），不要这样做。

`<bug_description>` 就是调用这个 skill 时传进来的内容——一段故障描述、一个 `mode:` 标记，或一个 issue 引用（`#123`、`org/repo#123`、issue 网址）——可能来自用户，也可能来自调用它的 skill（`ce-babysit-pr` / `全自动开发` 在 `mode:pipeline` 下会传入失败的任务和日志末尾；`全自动开发` 的修 bug 路线会传入 `mode:return-to-caller` 和用户自己的引用）。什么都没传时就是空的。


## 模式

默认是**交互模式**：调查，走 Phase 2 的“选择是否修复”关卡，然后做 Phase 4 的交接。

**`mode:pipeline`**（由 `ce-babysit-pr` 或 `全自动开发` 这类编排程序设置）：完全不交互地运行，绝不调用会等待回答的提问工具。先把这个标记从 `<bug_description>` 里去掉，然后**读 `references/pipeline-mode.md` 并照做**——它把每一个“问用户”的地方都换成保守的默认做法，把 Phase 2 的修复关卡换成“收敛的 bug 就修，分歧的 bug 就延后”，并把 Phase 4 的交接换成一个结构化的返回结果，其中 `status` 必须正好是 `fixed-and-pushed | fixed-not-pushed | diagnosed-no-fix | flaky-infra | needs-human` 之一。调用方会按这些确切的拼写来分支处理，所以绝不要改名、缩写或增加取值。

（说明：“收敛的”（convergent）修复指不改变原有设计意图、大家都会同意的修复；“分歧的”（divergent）修复指会推翻某个有意做出的约定、行为或产品决定的修复。）

**`mode:return-to-caller`**（由 `全自动开发` 在修 bug 路线上设置）：不交互地运行，但修复之后的所有事都归调用方负责。先去掉这个标记，然后**读 `references/return-to-caller.md` 并照做**——它保留 Phase 0-3 和“收敛就修、否则延后”的修复边界，应用 Phase 3 的分支规则让修复落在功能分支（feature branch）上，提交修复相关的文件但不推送，跳过修复后的打磨和审查步骤，并返回一个结构化结果，其中 `status` 必须正好是 `fixed | diagnosed-no-fix | needs-human | blocked` 之一。拼写规则同上。

## 会等待回答的提问

这个 skill 里凡是要问用户的地方，都用运行环境当前工具列表里已有的“会等待回答的提问工具”（按功能匹配，不按某个环境特有的名字）。工具出现在当前列表里，就证明它存在；绝不要为了确认它存不存在而去调用面向用户的提问工具。如果列表里有匹配的工具但还没加载，就用运行环境的“工具发现”功能把它加载进来——不要去找别的环境的工具名。只有列表里没有这种工具，或者真的调用时报错，才退回到在聊天里列出带编号的选项。绝不要悄悄跳过问题，也绝不要在没得到回答时结束一个阶段。

## 证据里的密钥

排查时会不断出现原始输出——命令结果、抓到的数据、日志片段——而且运行环境可能在命令一运行时就把输出显示出来，所以要在写命令的时候就检查密钥（secret），而不是事后再查。把凭证放在环境变量里，不要写在命令行上；如果某个命令的输出可能带有密钥（详细的 HTTP 跟踪、打印出来的请求头、打印配置或环境变量），就把输出存到文件里，只展示清理过的片段，每个密钥都用 `<REDACTED>` 代替。任何展示出来、写下来或提交的内容里，都不能出现密钥（凭证、令牌 token、认证请求头、连接字符串）。如果清理后诊断需要的信息没了，就说明这一点并问用户，而不是把密钥还原出来。

只有在第一次要拼出 `<root>/` 开头的路径时，才去确定 `<root>`——如果一次运行里一个这样的路径都不用拼，就整个跳过这一步。

**在拼出任何产物路径之前，先确定 CE 产物根目录 `<root>`。**

- **读取：** 只从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取。没有设置时，`<root>` 就是 `docs`，和以前完全一样。
- **校验：** 如果设置了值，它必须是一个相对于仓库的目录，它的真实路径（把符号链接 symlink 解析之后）要在仓库里面，而且既不能是仓库根目录，也不能在 `.git/` 下面。否则就报错停下，报错里写明 `docs_root` 和它的值——绝不要退回用 `docs`。
- **使用：** 把 `<root>` 作为唯一的产物存放位置：不存在就创建；每个路径都拼成 `<root>/<subdir>`，用这个 skill 自己的子目录；绝不要同时再去读 `docs`。

## 执行流程

按顺序分五个阶段：**0 分诊 -> 1 调查 -> 2 根本原因 -> 3 修复 -> 4 交接。** 除了 Phase 0 的“小 bug 快速通道”，不能跳过任何阶段，也不分复杂度等级。难的 bug 在每个阶段花更多时间，但不会少走阶段。

**现在就读 `references/investigate.md`，并在 Phase 0-2 照着做**——包括获取 issue、复现问题、检查环境是否正常、对有未提交改动的工作区做 stash（暂存）实验、往回追踪、搜索工单系统和 PR 历史、让假设有依据，以及升级对照表。这里只列出下面这些关卡。

**正式记录的 issue。** 如果用户给了你一个工单或 issue，不管它在哪个系统里，这个 bug 就已经“住”在那里了；Sentry 上的 issue 和 Linear 上的工单一样算数。把它的编号和网址一直带到 Phase 4。如果输入只是一段报错调用栈（stack trace）、一个测试路径或一段描述，那么这次运行就**没有正式记录的 issue**。这是很平常的情况，不是需要补上的缺口：没有 issue 也照样提交修复，绝不要为了凑一条记录去开工单，也绝不要问用户要不要开。Phase 1 的工单搜索只是查看之前做过的工作，**绝不为这个 bug 建立新的“家”**。如果已经有这个 bug 的工单，就在 Phase 4 里*关联*它，绝不要新建。

**小 bug 快速通道**（从输入就能看出原因、改一行就能修好、不需要深入追踪）在改代码之前仍然要走 Phase 2 的“选择是否修复”关卡：它省掉的是调查的繁琐步骤，而不是用户决定要不要修的权利。

**选择回归测试。** 针对*已确认缺陷*的回归测试（regression test，防止同一个 bug 再出现的测试），应该放在已经负责测这个行为的现有测试里：从已有的测试出发，而不是新建一个文件。在写 Phase 2 的建议之前（不只是在 Phase 3 改代码之前），就要读 `references/fix.md`，了解测试该放哪里和命名规则。如果一个测试失败，是因为改动有意推翻了它所断言的行为，那这个测试的预期并没有错——这属于下面说的“分歧”情况，要延后处理，而不是去改测试。

### Phase 2 关卡：先展示，再提问

**因果链关卡：** 在你能完整解释整条链——从触发点经过每一步直到看到的症状——并且中间没有断档之前，不要进入 Phase 3。“X 不知怎么就导致了 Y”就是断档。调查卡住时，只有用户可以授权按目前最可能的假设继续。

根本原因确认之后，把发现写成用户能看到的一段内容：带 文件:行号 引用的因果链；建议的修复以及它会改哪些文件；要用、新增、修改或加强哪些测试，以及现有测试本来是否应该抓到这个问题；还有任何相关的工单或 PR，以及它们怎样影响你的建议——如果已经有一个打开的 PR 修了这个问题，就先给出那个链接，而不是再做一个新修复。

**在关卡之前、同一轮里先展示：** 在那段发现完整写出来之前——在这一轮，或者紧挨着的上一条助手消息里——不要提出“选择是否修复”的问题。在弹窗式的运行环境里，提问工具只显示它自己的问题文字，所以如果只凭一句“根本原因已确认”就发问，用户做选择时眼前完全看不到因果链。列出选项不等于展示了发现，答应“选完再解释”也太晚了。

如果需求里还没授权下一步，就（按上面**会等待回答的提问**的规定）问用户走哪条路，给出下面三个选项。明确要求修复的，就直接进 Phase 3。明确只要诊断的，就跳到 Phase 4。`mode:pipeline` 和 `mode:return-to-caller` 永远不问。不管怎样，测试建议都是诊断的一部分。

1. **Fix it now（现在就修）**——进入 Phase 3
2. **Diagnosis only — I'll take it from here（只要诊断，后面我自己来）**——不修，写 Phase 4 的总结，结束这个 skill
3. **Rethink the design（重新考虑设计）**（`头脑风暴`）——只有当这个 bug 在现有设计下修不好时才用：根本原因是职责或接口分错了，而不是逻辑写错了；或者需求本身就是错的；或者每个候选修复都只是绕过一个已经不成立的假设。改动量大本身不算设计问题。

**`mode:pipeline` 和 `mode:return-to-caller`：** 不要问。直接进入 Phase 3，应用**收敛的**修复；**分歧的**修复——会推翻一个有意做出的约定、行为或产品决定的修复，包括一个断言了预期行为的“失败”测试——按 `references/pipeline-mode.md` 或 `references/return-to-caller.md` 的规定延后，不应用。这里绝不转到 `头脑风暴`；设计问题会变成一个 `needs-human`（需要人来处理）的遗留项。

### Phase 3：修复

如果用户选了“只要诊断”，就跳到 Phase 4 的总结。如果用户选了“重新考虑设计”，控制权已经交给 `头脑风暴`，这个 skill 结束。

**在改任何文件之前，先读 `references/fix.md`**——里面有先写测试的步骤顺序、修复失败时的规则，以及什么时候要做多层防护（defense-in-depth）和事后复盘（post-mortem）。有两条规则决定修复能不能开始，所以留在这里：

- **分支。** 先看 `git status`；如果用户在需要修改的文件里有还没暂存（unstaged）的改动，改之前先确认。如果当前分支是默认分支，不用问，直接新建一个功能分支——根据 bug 起个名字，运行 `git checkout -b <name>`，并说明你切到了哪个分支。判断默认分支的方法：和 `main`、`master` 比较，或者和 `git rev-parse --abbrev-ref origin/HEAD` 的结果比较，**但要先去掉它的 `origin/` 前缀**——原始输出是 `origin/<name>`，不去掉前缀的话永远比不上。
- **记录修复前的范围：** 当前的 `HEAD`、`git status --short` 是否干净，以及原本就有改动的文件。然后在干活过程中维护一份**修复自有文件**清单（为这个 bug 改过的测试和实现文件）。Phase 4 的两个问题都要靠这份记录来回答，事后没法重建。

### Phase 4：交接

**`mode:pipeline`——整个跳过这一段交互式交接。** 没有打磨或审查步骤，没有遗留问题提问，没有预览，也不提议记录经验。按 `references/pipeline-mode.md` 提交并推送收敛的修复，然后输出那个参考文件规定的**结构化返回结果**。分歧的 / 需要人处理的项目在那里延后处理（开一个讨论串，或写在调用方的运行报告评论里——绝不要写成 PR 说明里的一节）。**`mode:return-to-caller`——也跳过：** 在功能分支上提交修复自有文件，什么都不推送，然后输出 `references/return-to-caller.md` 规定的结构化返回结果。在这两种模式下，返回结果都是这个 skill 写的最后一样东西。它结束的是这个 skill，而不是这一轮对话。调用方就在同一个会话里运行，它的下一步紧跟着返回结果；不要宣布“交接给它”。这一节剩下的内容只适用于交互模式。

**结构化总结**——总是先写这个：

```
## Debug Summary
**Problem**: [What was broken]
**Root Cause**: [Full causal chain, with file:line references]
**Recommended Tests**: [Tests to add/modify to prevent recurrence, with specific file and assertion guidance]
**Fix**: [What was changed — or "diagnosis only" if Phase 3 was skipped]
**Prevention**: [Test coverage added; structural fix or defense-in-depth if applicable, or the structural fix left as follow-up]
**Confidence**: [High/Medium/Low]
```

（上面这个模板各项的意思：Problem＝哪里坏了；Root Cause＝完整因果链，带 文件:行号；Recommended Tests＝为防止再出现要新增或修改的测试，具体到文件和断言；Fix＝改了什么，跳过 Phase 3 时写 "diagnosis only"；Prevention＝新增的测试覆盖，适用时写结构性修复或多层防护，或者把结构性修复留作后续；Confidence＝把握程度 高/中/低。）

**如果跳过了 Phase 3**，写完总结就停——用户已经说了后面他自己来。不要再提问。

**如果做了 Phase 3，现在读 `references/post-fix-handoff.md`，并在走下面的路线之前照着做。** 它规定了修复后的质量步骤：根据上下文覆盖默认做法的检查、机械性修复的跳过规则、让 `简化代码` 和 `代码审查` 不碰分支上无关工作的范围限定、遗留发现怎么处理、`## Post-Fix Quality` 这一段，以及什么情况下提议记录经验。这些内容正文里都没有。下面的路线只说明*执行哪个*操作，从不说明保证安全的范围规则，所以不能凭它即兴发挥。不读这个文件，就会发出一个没审查过的修复，让审查伸到分支上无关的工作里，还会让已接受的发现滞留在会话里没人处理。

#### 路线

**把修复落地，但不要顺带捎上任何用户没主动给出的东西**——不进提交、不进推送、不进 PR。不要问要不要开 PR；“有没有许可”不是这里的关卡。交接由两个问题决定。根据 Phase 3 记录的修复前范围来回答，而不是根据这个分支是怎么来的。**直接执行操作本身**，用平台调用 skill 的功能——绝不要只是告诉用户去输入一条命令。

**1. 提交里可以放什么——只有修复自有文件，别的都不行。** 这是对第 2 个问题里负责提交的 skill 的限制，本身不是一个操作。不管走哪条路线、有没有远程仓库，都成立。不要在这里提交。

- 如果修复自有文件里没有一个原本就带改动，这些文件就是提交范围。把它们交给负责提交的 skill。
- 如果某个修复自有文件里原本就有用户的改动，那么任何提交都没法把两者分开：`提交代码` 按文件分组，从不拆分一个文件。在任何提交发生*之前*，（按**会等待回答的提问**的规定）问用户：是连同他的改动一起提交这个文件、让修复保持不提交、还是停下。只有第一个答案会继续。另外两个答案会结束交接，所以第 2 个问题不会执行，什么都不提交；说明留下了什么以及原因。每个选项都会损失一些东西，智能体不能替用户做这个选择，所以这个问题必须保留。Phase 3 的确认只涵盖*修改*这个文件，从不包括把用户的改动和修复一起提交。

**2. 由谁提交，以及要不要发布。** 下面三种只会执行其中一种。

- **发布（Ships）**：三个条件都满足时：修复前的工作区是干净的；分支上没有用户还没主动给出的工作；并且 `origin` **能开 PR**：也就是 `gh`（GitHub 命令行工具）真的能在那里开 PR。用适合眼前这个仓库的方法确认这三点。有两个事实让它没看上去那么简单：
  - `提交推送开PR` 会推送**整个分支**，它开的 PR 包含分支上的所有提交，而不只是你的修复。所以问题在于整个分支，而不是你的改动。它还会在创建 PR *之前*先推送，所以如果远程仓库是 `gh` 开不了 PR 的地方，分支就会被发布出去，却没有 PR。
  - 已经推送过，不等于已经**主动给出**。在打开的 PR 里的提交正在被审查，算是已给出，这次运行要更新那个 PR，而不是再开第二个。为了备份或触发 CI 而推送的提交不算已给出，第一次开 PR 会把它们公开。要和远程仓库比较，而不是和本地引用比较：本地分支（包括 Phase 3 可能从它分出来的默认分支）本身就可能比已推送的内容更新。

  如果三点不能全部确认，就改走本地路线；那是安全的方向，预览不能代替它。否则，先预览：要提交什么、在哪个分支上、是新开 PR 还是更新 PR，然后**用 `branding:on` 调用 `提交推送开PR` skill。** 它会按第 1 个问题的范围提交，所以你不要先提交。预览是一句陈述，不是一个问题。最后给出生成的 PR 网址。
- **留在本地（Stays local）**：三个条件里任何一个不满足时。按第 1 个问题的范围调用 `提交代码` skill，什么都不推送。用一句话说明哪些留在了本地以及原因，并说明用户要求时你会推送并开 PR。不要先问；本地提交是可以撤销的。
- **不是 git 仓库**：什么都不提交。写完总结和质量那一段就停。
