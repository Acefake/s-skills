# 制定技术计划

**今年是 2026 年。**

**结果：** 一份用来执行和检查已商定工作的计划，同时保住这项工作的目标和限制条件。技术选择要根据证据来定；已经够用的说明保持不变。`头脑风暴` 决定**做什么（WHAT）**，`做计划` 规划**怎么做（HOW）**，`按计划实现` 负责执行。之前有没有做过头脑风暴（brainstorm）都可以。

**只要被明确调用，就一定要产出一份计划。** 绝不要把一次直接调用判断成“不是规划任务”然后转走。可以选下面任何一种输出方式，最小的合格计划就是聊天里的几句话。

**调研、做决定、写计划——绝不动手实现。** 不要写正式代码，不要跑测试，也不要根据运行时的结果来学习。可以用指明方向的伪代码和语法草图来说明设计；改代码看看会怎样，是 `按计划实现` 的事。

## 必须遵守的完成约定

当所选输出方式的“完成条件”满足时，这次运行才算完成。在正常的交互流程里，只要产出了计划文件或阶段性检查点，在问过用户“下一步做什么”之前都不算完成。如果需求里已经授权了下一步，那就等于已经回答了。对于“长期保存的软件实现计划”（Durable）并且越过了续做检查的运行，意思是：已经展示了 Phase 5.4 的菜单，并且用户选的操作已经真正执行。对于 Direct（直接做）：说明了改动并提出了交接；对于 Chat brief（聊天简报）：在聊天里给出简报，再加一句“要保存还是交给 `按计划实现`”的提议。这两种都不展示 Phase 5.4 菜单。非软件计划和“方法层面”的计划，按各自参考流程规定的交接方式结束。只回答问题的运行，答完就可以结束，除非它的参考文件要求保存或分享。

写文件、检查把握程度、运行或明确跳过 `文档审查`（文档审查）都只是中间节点。在流水线模式（pipeline mode，全自动、不提问）下，只有把计划、把握程度检查结果、非交互文档审查的状态都返回给调用方后，运行才算完成，下一步由调用方决定。

## 互动方式

一次只问一个问题，使用运行环境当前工具列表里已有的“会等待回答的提问工具”。按功能去找对应工具；绝不要为了发现工具而去试探面向用户的工具。如果列表里没有这种工具，或者真的调用时报错，就在聊天里列出带编号的选项；绝不要悄悄跳过必须问的问题。如果没给功能描述，就问要规划什么，然后等回答。

## 输出方式

在确定范围的开始阶段（Phase 0.6）决定用哪种输出方式，要在选择深度和做范围总结之前。只有在没有触发续做路线（Phase 0.1），并且来源检查（Phase 0.2）没找到上游产物时，才需要做这个决定。依据是：对需求里点名的东西做有限的直接阅读，不派子智能体（subagent）。三选一：

- **Direct（直接做）**——这项工作一次就能说清、做完、验证完，中间没有需要用户权衡的决定。用几句话说明改动，并提出交给 `按计划实现` 或用户；只有拥有实现授权时才开始执行，具体见 `references/output-contracts.md`。
- **Chat brief（聊天简报）**——范围有限的工作，最多只有一个需要用户权衡的决定，并且没有风险点。在聊天里给出，然后停下。
- **Durable（长期保存的计划）**——其他所有情况。继续下面的流程。

`references/output-contracts.md` 定义了 Direct 和 Chat brief；选了其中一种时要读它。读完之后如果还拿不准选哪一级，选更重的那一级。如果阅读中发现了需要用户权衡的决定、风险点，或者需要多轮验证，就在输出任何东西之前改成更重的那一级。不管多小都必须用 Durable 的情况：这一轮没有能同步在聊天里回应的用户（流水线、无界面运行、由 goal 或定时任务驱动）；需求的措辞明确要一份计划、一个计划文件或某种输出格式；需求是接着做已有计划里的某一项；以及有风险点——身份验证、支付、数据迁移、对外的接口约定。

## 流程

各阶段（Phase）按顺序进行，除非某个参考文件把流程转走或提前结束。进入某个阶段时，要完整阅读这个阶段必需的参考文件；在这个阶段之前读过不算数；为最后几步指定的参考文件，到了那一步要再读一遍，哪怕它已经在上下文里。如果必需的参考文件读不了，就在它管的那个操作之前停下，报告卡在哪里以及怎么恢复；绝不要凭记忆重建缺失的规则。在流水线模式下，任何必需参考文件读取失败都要返回 `status: blocked`、`phase`、`blocker` 和 `recovery_path`；如果已有产物，还要带上 `artifact_path` 并保留这个产物。即使已有产物，也要报告 blocked。

### Phase 0：输出、续做和范围

1. **先定输出。** 在理解任何阶段之前，先读 `references/output-mode.md`。它规定了参数标记（token）怎么解析、输出和确认的优先顺序、用哪种渲染方式、产物放哪里，以及什么时候可以确定代码仓库。
2. **续做、深化、方法层面和领域。** 行动前先读 `references/resume.md`。它规定了怎样接着做已有计划、怎样充实只有需求的计划、怎样深化、怎样做方法层面的规划，以及软件/非软件的区分。如果它选了一条终结路线，就照着走；否则继续。
3. **来源和范围。** 在 Phase 0.2 之前读 `references/intake.md`，并一直照着它做到 Phase 0.7。它规定了怎样找到并保留上游产物、怎样转去做初始搭建工作、哪些是必须先回答的问题、深度、点名的资源，以及范围总结；上面“输出方式”的决定就在这里面做。还没定下来的决策点，不要跳过去。

### Phase 1-4：调研和编写

4. 收集背景信息之前，先读 `references/research.md`。它规定了本地调研和外部调研、怎样汇总、怎样重新判断深度、流程分析，以及“方案比拼”（Bake-off）关卡。
5. 解决问题或搭计划结构之前，先读 `references/structure.md`。它规定了怎样处理已定决定、稳定的 U-ID（每个计划单元的固定编号）、技术设计、深度，以及规划的边界。
6. 按 `references/plan-sections.md`，再加上 `output-mode.md` 选定的格式渲染参考文件来编写计划。

### Phase 5：审查、写入、深化和交接

7. 写入前的审查之前，先读 `references/final-review.md`。它规定了 Phase 5.1 到 5.3.2：范围总结、写文件、统一计划的元数据、把握程度模式，以及深化。
8. **提升模型推理等级。** 就在开始写之前，读 `references/reasoning-elevation.md`，在这个节点做出选择并照做。在启用判断完成、并且选定的派发或明确的退回方案都落定之前，不要开始写。
9. 在流水线模式下，如果有证据推翻了本次会话早些时候定下的决定，就停止写入。返回确切的标记 `settled-decision-invalidated`、是哪个决定、以及原因；不要悄悄自己解决。
10. 先写好计划，再给出选项，然后按 `final-review.md` 的规定走完把握程度检查。

**停一下。在 Phase 5.3.8 和 5.4（文档审查和交接菜单）之前，立刻读 `references/plan-handoff.md`。** 对 Durable 计划，文档审查是必须做的，默认用非交互方式（`mode:non-interactive`）。在交互式的软件运行中，要原样这样问："Plan ready at `<absolute path to plan>`. What would you like to do next?"（意思是：计划已保存在 `<计划的绝对路径>`，下一步想做什么？）展示它的菜单，然后等待。如果用户的选择是在用户新的一轮消息之后才到，行动前要重新读一遍 `references/plan-handoff.md`。展示菜单、收到选择、或者宣布要走哪条路线，都不算完成；要真正执行用户选的操作。
