# 解释“怎么样”和“为什么”

给出一份解释，回答限定好的问题，并让使用它的人（或程序）理解到足够完成预定用途的程度。主题和目的来自请求和现有的上下文，不管是人提供的，还是另一个流程提供的。项目的行为要以源代码等证据为依据；要区分哪些是有文档记载的理由、哪些是推断、哪些是不知道的。

**完成标准：** 给出解释，附上支持它的证据，以及重要的、还没回答的问题；或者返回具体卡在哪里。如果要求了一份产物（文件），就交付这份产物以及它的位置。公开发布是另一个单独的动作，不是“已经解释清楚”的条件。

## 读者和互动

按照预定的读者和用途，调整解释的深度和呈现方式。一个人可能只需要一个能用的答案；一个调用你的智能体，可能需要一份教给别人看的教学材料。不要只凭调用方是谁来推断输出形式。当你是在为一个正在进行的流程出力时，交付要求的结果，后续怎么继续由这个流程的主人——调用它的流程——决定。不要在返回内容里加“发到哪里”的菜单或后续提议。

能自己查到的事实，先查清楚再问。只有当缺少的信息会实质性地改变答案，而且无法从请求或证据里弄清楚时，才去问。如果没法和人互动，就返回这个没解决的问题以及它的影响，而不是一直等或者编一个答案。一个结果可以解释已经核实的行为，同时说明它当初为什么这样设计的历史原因不清楚。

**在收集证据、提出第一个需要等待回答的问题、或派发子智能体之前，先读 `references/orchestration.md`。** 它规定了怎样收集证据、怎样使用工具、模型分档，以及各自的退回方案。

## 产物根目录

只有在归档到仓库时，说明文档（explainer）才会放到 `<root>/explainers/` 下；可能会读取 `<root>/solutions/` 下的经验文档。只有在要拼出这样的路径时才确定 `<root>`；只用临时空间、或者解释外部概念的运行，从不会拼出这种路径。把确定好的路径（而不是配置）传给子智能体。

<!-- ce-docs-root:start -->
**在拼出任何产物路径之前，先确定 CE 产物根目录 `<root>`。**

- **读取：** 只从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取。没有设置时，`<root>` 就是 `docs`，和以前完全一样。
- **校验：** 如果设置了值，它必须是一个相对于仓库的目录，它的真实路径（把符号链接 symlink 解析之后）要在仓库里面，而且既不能是仓库根目录，也不能在 `.git/` 下面。否则就报错停下，报错里写明 `docs_root` 和它的值——绝不要退回用 `docs`。
- **使用：** 把 `<root>` 作为唯一的产物存放位置：不存在就创建；每个路径都拼成 `<root>/<subdir>`，用这个 skill 自己的子目录；绝不要同时再去读 `docs`。

## 执行流程

### Phase 1：确定问题和用途

现在读 `references/intake.md`。它规定了怎样确定主题和时间范围、输入的参数标记，以及怎样选择交付形式。只解释被要求的主题。如果只是单纯调用、又找不出主题，就按上面的互动规则去澄清，而不是自己编一个话题或默认产出一份文件。

### Phase 2：收集证据

按 `references/orchestration.md` 做一轮限定范围的证据收集。已有证据足够而且是最新的，就直接用；对那些缺少依据、有争议、或者受源代码改动影响的说法，要去核查。

只有当一份产物或一份证据档案需要时，才创建运行目录。写这两样东西之前，先用下面这段代码；它会拒绝符号链接，也会拒绝属于其他用户的临时目录：

```bash
SCRATCH_ROOT="/tmp/compound-engineering-$(id -u)";
[ ! -L "$SCRATCH_ROOT" ] && (umask 077; mkdir -p "$SCRATCH_ROOT") 2>/dev/null && [ ! -L "$SCRATCH_ROOT" ] && [ -O "$SCRATCH_ROOT" ] && [ -w "$SCRATCH_ROOT" ] || SCRATCH_ROOT="${TMPDIR:-/tmp}/compound-engineering-$(id -u)";
if [ -L "$SCRATCH_ROOT" ]; then echo "unsafe scratch root symlink: $SCRATCH_ROOT" >&2; exit 1; fi;
(umask 077; mkdir -p "$SCRATCH_ROOT") || exit 1;
if [ -L "$SCRATCH_ROOT" ] || [ ! -O "$SCRATCH_ROOT" ]; then echo "scratch root is not owned by the current user: $SCRATCH_ROOT" >&2; exit 1; fi;
chmod 700 "$SCRATCH_ROOT" || exit 1;
RUN_DIR="$SCRATCH_ROOT/ce-explain/$(date +%Y%m%d)-$(openssl rand -hex 3)";
(umask 077; mkdir -p "$RUN_DIR") || exit 1; chmod 700 "$RUN_DIR" || exit 1;
echo "$RUN_DIR";
```

如果一次行为追踪跨越了不同的负责范围，就会写出侦察员（scout）的证据档案。在派出这些侦察员之前，先创建这个运行目录。

- **Diff 模式（解释某个改动）。** **改动范围是空的**，或者找不到主题：不要悄悄去解释别的东西。在解释相关的其他东西之前，先报告这一点。只有在请求允许、或者用户同意时，才用替代对象；在结果里写明做了替代，如果有产物，也在它的 `Subject` 里写明。否则，就把没确定的范围返回给调用方。
- **Recap 模式（回顾一段时间的工作）。** 不要在主对话里预先扫描、统计或描述这段时间。而是直接用“提取”这一档的模型派出一个通用子智能体，以 `references/agents/work-recap-scout.md` 作为起点，并传给它确定好的时间范围、仓库根目录和 `$RUN_DIR`。**这段时间没有活动：** 报告没有活动，然后结束，不产出说明文档。**如果运行环境没有子智能体功能**，就按它提示里的来源和预算在当前上下文里直接做这个侦察，仍然要写出 `recap-evidence.md`，在完成之前不要对这段时间形成任何看法。如果派发失败，按 `references/orchestration.md` 里的退回规则处理。

### Phase 3：写出解释

用证据回答问题，保留重要的限制条件和不确定性。交付之前，把每一个事实性说法都和它的来源对照一遍。调用了某个函数，不能证明它那没看过的内部实现有什么保证。删掉没有依据的说法，或者在它出现的地方（包括图表和练习答案里）说明它不确定。如果散文、代码、表格或图示能帮助理解，就用；没有规定必须怎么安排。解释多人完成的工作时，要准确写明是谁做的。当证据比要求的范围或深度能容纳的更多、需要挑选时，要说明你做了挑选；绝不要悄悄把一个不完整的说法当成全部来呈现。

如果答案或材料是要被另一个流程拿去用的，就直接返回那份内容。每一段都要带上准确使用它所需的限定说明，不需要另外的备注。当另一个流程要用这个答案时，返回内容里要包括证据、仍然适用的限制条件，以及还没回答的问题。除非预定用途需要，否则不要单独做一份产物文件。

如果要单独做一份产物文件，写的时候按所选格式读 `references/explainer-html.md` 或 `references/explainer-markdown.md`，了解兼容性和元数据要求。如果是教学材料，还要读 `references/check-in.md`。运行从不因为“检查理解”环节而卡住；任何练习都是产物里的静态内容。写出 `$RUN_DIR/explainer.html` 或 `explainer.md`，然后在聊天里给出简短总结，加上文件路径。

### Phase 4：交付

给出答案或本地产物文件，解释就完成了。不要要求用户选择发到哪里，也不要制造后续工作。如果用户要求了目的地，行动之前先读 `references/destinations.md`；它规定了每个目的地，以及公开发布需要用户怎样同意。当外围的文档归调用它的流程负责时，把内容返回给那个流程，而不是你自己去放置或发布。

发布到 ht-ml.app 从来不能在无人值守时进行，也从来不能靠推断。用户说出这个名字，只是选择了目的地，不等于看过“会公开发布”的警告之后确认了。如果拿不到确认，就不要发布；保留正式的 HTML 文件，并报告它的本地路径 `$RUN_DIR/explainer.html`。

## 边界

- 要判断某个做法该不该采用或修改，用 `ce-pov`。解释一个过去的选择，不等于今天还赞成它。
- 要记录值得长期保留的项目经验，用 `ce-compound`。做出一份解释，不代表有权去维护仓库里的“记忆”。
- 按别人给的样子解释一个想法；想出其他方案、规划怎么实现，属于 `ce-ideate`、`头脑风暴` 和 `做计划`。
- 报告的故障要诊断或修复，属于 `查bug`；对当前行为的事实性解释，还是留在这里。
