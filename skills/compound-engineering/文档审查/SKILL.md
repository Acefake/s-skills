# 文档审查

帮助作者完成一份靠谱的文档，让他能用它来执行已商定的工作。找出那些会改变工作结果、或者会严重妨碍执行的问题，并在已经给出的权限范围内解决它们。评判文档的标准，是它能不能指导人做对事情，而不是它写了多少细节。后果严重的问题，即使缺陷很小也值得关注。一份合格的文档，可以什么都不用改。

审查角色（persona，扮演不同审查角度的子智能体）提供证据；判断由你来做。把它们的说法和整份文档、项目事实以及已定的决定对照检查。对于那些已被证实、会妨碍执行某个已有决定的错误，在综合参考文件规定的编辑权限和审查要求范围内，直接改正。只返回这些：仍然需要许可的、值得做的改进；只有用户才能做的重要选择或才能提供的关键信息；以及有用的观察。

**完成标准：** 每个选中的审查者都已经返回结果，或者在 Coverage（覆盖情况）里写明失败了；保留下来的每条发现，都已核实会对已商定的工作产生影响；每一个分配到 Apply（应用）、并且已经授权的改正都已经做完并检查过。通过交互式的批准或决定流程报告这个最终状态；在非交互模式下，就以结构化文字返回。

## 交互模式规则

**在做任何事情之前，先读 `references/modes.md`。** 它规定了怎样判断模式、非交互模式的参数约定，以及提问工具的规则：在运行环境当前工具列表里找会等待回答的提问工具（绝不要为了发现它而去调用面向用户的提问工具）；如果它在列表里但还没加载，就在交互流程一开始预先加载；只有在运行环境确实没有这种工具时，才退回到带编号的列表。

不管哪种情况，需要用户做决定的问题，都要调用这个工具，或者明显地退回到编号列表。把它当作普通文字随口说一下，是一个 bug。

## 产物根目录

**只有**在没给路径的交互分支里才确定 `<root>`，这个分支会去 `<root>/plans/` 下找最新的计划。其他所有运行，都直接读传给它的那个路径上的文档。所以，用绝对路径或非交互方式的审查——比如 `/tmp/plan.md`，可能根本不在任何仓库里——永远不依赖它用不到的仓库根目录或 CE 配置。

<!-- ce-docs-root:start -->
**在拼出任何产物路径之前，先确定 CE 产物根目录 `<root>`。**

- **读取：** 只从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取。没有设置时，`<root>` 就是 `docs`，和以前完全一样。
- **校验：** 如果设置了值，它必须是一个相对于仓库的目录，它的真实路径（把符号链接 symlink 解析之后）要在仓库里面，而且既不能是仓库根目录，也不能在 `.git/` 下面。否则就报错停下，报错里写明 `docs_root` 和它的值——绝不要退回用 `docs`。
- **使用：** 把 `<root>` 作为唯一的产物存放位置：不存在就创建；每个路径都拼成 `<root>/<subdir>`，用这个 skill 自己的子目录；绝不要同时再去读 `docs`。
<!-- ce-docs-root:end -->

## Phase 1：拿到并分析文档

**现在读 `references/document-intake.md`。** 它讲了每种模式下怎样拿到文档、找不到文档时该做什么和说什么，以及分类的依据。

其中有两条规则适用于后面的每一步。

**派发之前先核实。** 每个确定下来的路径，都必须能在磁盘上读到。只要有一个读不到，就**一个**审查角色都不派：审查者是从文件系统读文件的，所以它们读不到只存在于没切换出来的分支上的路径（issue #925）。

**按内容分类，不按“是否就绪”的标签或文件路径分类。** 只有 Product Contract（产品约定）的统一产物，属于 **`unified-requirements`**；缺少实现部分是正常的。只要有任何实现规划，就属于 **`unified-plan`**，包括还没做完或被卡住、需要审查的规划。其他产物用旧的 `requirements` / `plan` 两分法。

HTML 格式的统一产物走同样的路线。每个修改都用文档本身的格式写；绝不要往 HTML 里插 markdown。带编号的条目怎么处理，见那个参考文件。把分类结果放进 `{document_type}` 这个位置，传给每个审查角色。

## Phase 2：宣布并派发审查角色

只有当 `references/document-intake.md` 里“复用已完成审查”的条件满足时，才跳过派发；带着那份证据直接进入 Phase 3。

**读 `references/persona-selection.md`**，了解每个按条件加入的审查角色的启用信号，以及宣布的格式。其中有两个信号，在看似合理的证据面前容易被过度触发：`security-lens-reviewer` 的敏感数据界限，以及 `adversarial-document-reviewer` 的“可质疑面”门槛。然后读 **`references/dispatch.md`**，了解要传入的变量、切分、模型分档，以及审查者失败时的处理。

审查团队总是包括 `coherence-reviewer` 和 `feasibility-reviewer`，再加上每个被启用的条件审查角色。在派发之前，先宣布团队成员，并给每个角色写一句理由。

通过平台的子智能体功能，以**有限的并行度**派出通用子智能体。每个都以它对应的 `references/personas/<reviewer-name>.md` 的完整内容作为起点。绝不要按类型或名字派出独立的智能体。

因容量不够被拒绝，是“排队等待”，不是审查者失败：等一等再试。如果容量恢复不了，而选中的审查者还有没派出去的，就按 `references/cross-model-review.md` 的说明，收回并清理已经启动的跨模型任务，然后以“未完成”停下，不做综合、不做修改、也不做成功交接。保留已经收到的结果，并报告哪些审查者完成了、失败了、或没能运行，以及原因。

### 跨模型判断环节

只要**条件判断三人组**——`adversarial-document-reviewer`、`product-lens-reviewer`、`security-lens-reviewer`——中有任何一个被启用，就做这个环节。按 `references/cross-model-review.md` 做，它规定了整个环节：确认运行环境、整份文档使用的唯一目标和路线、在任何东西离开本机之前的说明，以及对等审查（peer）怎样启动、收回和合并进来。

这个环节是附加的、不会卡住流程的：失败或超时不会让任何事停下，只在 Coverage 里写明。先检查代码仓库的 `cross_model_review_mode` 设置，它可以带着写明的理由跳过这个环节。只有设置了 `CROSS_MODEL_PEERS` 时才筛选接收方——没设置表示不筛选，而不是不允许。绝不要悄悄更换明确指定的模型或接收方。

## Phase 3-5：综合、呈现和下一步

等每个派出去的智能体都返回了，包括任何跨模型的 `<reviewer-name>-<provider>.json` 返回结果。然后读 `references/synthesis-and-presentation.md`。它规定了综合的方法、每条发现怎样按把握程度和修复类别分流、怎样应用修改、非交互模式的结果格式，以及怎样交接到分流问题。在提升“多方一致”的发现时，只有带 `independence_verified: true` 的产物才算独立的审查者。

**只适用于交互模式。** 读 `references/walkthrough.md`，了解分组确认、分流问题，以及逐条过一遍发现的做法。读 `references/bulk-preview.md`，了解“按最佳判断分流”、“追加到待解决问题”（Append-to-Open-Questions）和“自动解决”背后的批量操作预览。在审查证据完整之前——不管是新收集的，还是合规复用的——这两个都不要加载；非交互运行永远不加载它们——它在结构化的审查结果处就停下。
