# Notes 验证地图

这个目录是验证 Notes（一个笔记应用示例）面向用户的行为时持续维护的来源。操作应用之前先读这份索引，然后把对应的功能文件当作操作做法来用。

## 基线前提条件

- 在 `http://127.0.0.1:4173` 启动 Notes，并使用一个用完即扔的数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让并发的运行不共享状态。
- 预先放入标题为 `Quarterly plan`（季度计划）和 `Grocery list`（购物清单）的笔记。
- 把 `control-notes` 和 `notes` 命令行工具放到 `PATH` 上。
- 运行 `control-notes doctor`，要求它报告预期的 URL、数据目录和构建版本。
- 永远不要操作不是由这次验证运行启动的实例。

## 操作约定

- 除非某个做法的前提条件另有说明，否则每个做法都从基线状态开始。
- 优先用 ARIA 角色和无障碍名称，而不是 CSS 选择器或 DOM 位置。
- 每条命令都按字面使用。带引号的名字和参数保持不变。
- 浏览器操作通过 `control-notes browser` 运行。
- 终端操作通过 `control-notes cli -- <command>` 运行。
- 修改数据之后，恢复预先放入的数据。清理时不要删掉证明用的产物。

## 证明和跳过的报告方式

- 采集用户的动作和由此产生的状态，而不只是最后的画面。
- 界面的证明包括一份 ARIA 快照，以及一张能看出是哪个应用的截图。
- 命令行的证明包括命令、标准输出、标准错误和退出码。
- 修改数据的证明包括从另一个只读视图看到的存储值。
- 每个产物都记录功能 ID 和使用的入口。
- 报告一条无法到达的路径时，写明尝试过的命令和没满足的前提条件。
- 不要把一个被跳过的入口，说成已经通过另一条路径验证过了。

## 功能条目约定

每个功能文件都以一个一级标题和一段描述用户可见行为的文字开头。接着按这个顺序，恰好使用四个二级标题。

1. `Sub-features` 列出简短的 ID，每个行为一行。
2. `How to get to it (user POV)` 列出用户的每一个入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用带标签的要点，把每个用户动作和一条确切的命令以及可观察的结果配对。
4. `Gotchas` 列出可能浪费或作废一次验证运行的陷阱。

不要把实现细节写进地图。只写用户路径、稳定的标识、需要的状态、命令和可观察的证明。

## 功能

- [新建笔记](./create-note.md) 覆盖浏览器和命令行的新建、取消、持久保存和清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘和命令行搜索，包括有匹配、空结果和清空这几种状态。
