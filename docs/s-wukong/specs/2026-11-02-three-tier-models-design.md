# setup-s-models 三档模型设计

日期：2026-11-02

状态：设计已确认，初版已实现；验证记录见同日实施计划

范围：模型配置、角色分配及已有授权工作流中的子代理派发

## 目标与结论

给 `setup-s-models` 增加轻量档，形成轻量、常规、复杂三档任务分工。模型按当前宿主实际允许用于子代理的名单推荐，允许不同档位共用模型。Luna、Terra、Sol、Astra 仅是用户表达分工时给出的例子，不作为跨宿主默认值。

第一版增加一个轻量角色，保留现有角色与配置格式，并接入实际派发规则。旧配置继续有效，已有显式模型选择优先。此方案不切换主会话模型，不自动增加子代理人数，也不扩大委派授权。

预期收益是减少明确检索和机械任务对强模型的占用。是否缩短耗时、降低额度消耗，需要真实会话验证，本设计不预先承诺收益数字。

## 当前实现与缺口

- `plugins/s-wukong/skills/setup-s-models/scripts/s_models.py` 的 `ROLES` 将现有 17 个角色分为 `FAST`、`STRONG`、`REVIEW`。`render_rows()` 主要用 `--fast` 和 `--strong` 生成角色行。
- `--third` 只在不限预算的评审列表中加入额外模型，没有轻量任务分工。它的含义保持不变。
- `--set` 已能单独覆盖角色，所以当前也能手动使用多个模型，但没有轻量档的统一推荐和任务边界。
- `how`、`why`、`swarm` 等工作流按角色行选模型。仅修改配置生成器，不修改使用方，无法形成新的任务分配。
- 预算同时规定推理目标与部分评审列表的人数。新增轻量档需要保持这些既有行为。

## 第一版的任务边界

### 轻量任务必须容易核验

轻量任务同时满足以下条件：范围明确、操作规则明确、结果可直接核对，而且不需要自行决定架构、业务语义或修改范围。

适合的例子包括查找符号定义与引用、列出指定目录中的接口、提取字段、按已确认的映射修改指定文件。重复工作涉及写文件时，必须已明确文件归属，并能通过 diff 和必要检查核验结果。

能用 `rg`、现有脚本或其他直接工具完成的任务，优先使用这些工具。新增轻量模型不要求为一次搜索创建子代理。

### 常规任务维持日常默认

常规档负责模块内功能、一般 bug、局部重构，以及需要理解上下文的代码探索。任务复杂度无法确定时，从常规档开始判断，不默认交给轻量档。

“查代码”不是轻量任务的充分条件。梳理跨模块调用链、确认状态生命周期和查找偶发缺陷，都可能需要复杂档。

### 复杂档也负责困难实现

复杂档负责跨模块根因分析、架构取舍、并发与状态问题、困难实现及需要综合多处证据的判断。是否采用复杂档取决于任务内容，不取决于“写代码”或“写文字”的名称。

## 配置与兼容

### 保留现有命令，增加 --light

保留 `--fast` 表示常规模型，保留 `--strong` 表示复杂模型；帮助文字改用这两个职责名称。新增可选参数 `--light`，表示轻量模型。`--third` 继续只表示不限预算下的额外评审模型，不改名、不复用。

新增角色行：

```text
检索和简单任务: <本次确认可用的轻量模型或 inherit-parent>
```

该角色的英文键固定为 `lookup and simple tasks`，Codex 自定义角色名为 `s-lookup-and-simple-tasks`。这一行与现有行使用相同的模型和推理档位格式。

新生成的配置包含原有 17 行和新增的轻量角色行。没有传 `--light` 时，新增行使用 `--fast` 的模型。使用 `--inherit` 时，新增行也写 `inherit-parent`。

### 旧配置保持原有含义

读取只有原有 17 行的配置时，不报缺少轻量角色的错误，不自动补写，也不改变原有角色模型。新轻量角色缺失时，派发方使用当前工作流原有角色及其模型，不通过其他角色猜测用户选过的常规模型。

重新配置时，只有用户确认新的完整标记段后才写入。原有角色值在预览阶段保留，除非用户同意采用新推荐或明确修改。配置标记以外的内容保持原样。

旧英文键继续读取，中文键优先。`--set` 可以覆盖新增角色，其优先级与现有角色相同。已有用户对本次任务的明确模型要求优先于自动推荐。

### 角色职责与预算分别处理

新增轻量行默认使用轻量模型；现有常规角色继续使用 `--fast`。现有判断类角色的生成规则继续保留，包括省预算下只有“最难的任务”默认使用 `--strong` 的行为。评审列表继续遵守现有预算规则，轻量模型不会自动加入列表。

轻量角色的起始推理目标取预算目标与 `medium` 中较低的一档，随后按实际模型支持范围下调。显式角色覆盖仍然优先。常规角色的起始推理目标沿用预算，最难任务沿用已有上调规则。宿主不能传推理档位时，说明此限制，不伪造已生效的档位。

配置最终以具体角色行为准。三档只是配置推荐与派发时的任务分类，不另加一套需要同步维护的三档模型配置块。

## 按宿主推荐模型

保持现有确认宿主、选预算、展示完整配置、确认写入的流程。在展示配置前说明本次三档推荐及依据，配置确认时展示全部角色行。

推荐只采用当前会话可验证的工具参数、模型名单和宿主资料，不按型号名字自动推断性能等级。可用性、能力定位或成本资料不足时，保留已有设置或请用户选择，不声称已找到最便宜或最强模型。

- 当前宿主能为子代理指定模型时，按实际可派发名单推荐三档。可选择同一个模型承担两档或全部档位。
- Codex 的配置块和自定义角色文件同时纳入适配，新增角色也使用宿主当前认可的文件格式。配置生成成功与当前会话发现角色分别验收。
- Claude Code、Cursor、WorkBuddy 按各自实际工具定义和既有配置位置处理，不把其他宿主的模型别名或参数复制过来。
- DeepSeek Harness 按选定 profile 的实际能力处理；Hermes 等无法验证按次指定模型的环境使用继承模式，并明确本次未实现模型分流。
- 模型存在但不能用于子代理时，不将它列为可派发候选。参数被拒绝时，报告失败并交回主线程，不静默换型号。

实现时重新核对各宿主的当前能力。本设计不将仓库已有平台说明等同于所有客户端均已实测。

## 派发规则及使用方

派发流程先检查已有授权和工具能力，再判断任务内容，最后读取具体角色行。配置文件本身不授权委派。

1. 主线程先判断直接工具是否能完成任务。能直接完成时，不为模型分档额外委派。
2. 已有工作流允许委派，而且任务满足轻量条件时，使用“检索和简单任务”。缺少此行则保留原工作流角色。
3. 一般实现和代码探索使用原工作流角色。复杂实现需要使用“最难的任务”时，保留原任务的职责、文件归属、工具要求与验收条件。
4. 用户已明确指定本任务模型时采用该选择，不因自动分档覆盖它。固定模型的宿主角色不能临时切换时，不假称已经换模。
5. 子代理遇到范围不清、跨模块语义判断、证据相互矛盾或必须扩大修改范围时，返回已查到的证据和未完成部分，由主线程决定下一步。第一版不自动重试，也不连锁升级模型。

`s-mode/references/subagents.md` 作为公共派发规则来源，`s-mode` 和 `s-agent` 引用它。`how`、`why`、`swarm` 在原有派发点接入分类，不新增工作阶段或增加人数。

`how` 的架构探索者默认仍为常规档。`why` 的历史调查涉及解释证据，默认仍为常规档。`swarm` 仅在分片任务本身满足轻量条件时采用轻量角色。综合者、架构参赛者和独立评审不因新增轻量档自动降档。

轻量子代理的返回内容应包括结果、文件与符号位置、查找范围、实际完成的修改以及未能确认的部分。主线程按原任务完成核验，不把子代理的自述当作已经验证。

## 第一版修改范围

实现围绕以下位置展开，不修改与三档分工无关的技能：

- `setup-s-models/scripts/s_models.py`：角色、参数、生成、校验、解析和旧配置兼容。
- `setup-s-models/SKILL.md` 与 `references/role-keys.md`：三档说明、完整角色模板、交互和行值格式。
- `s-mode/references/subagents.md`、`s-mode/SKILL.md`、`s-agent/SKILL.md`：统一任务边界与模型选择顺序。
- `how`、`why`、`swarm`：按上述职责接入已有派发点。
- `HOSTS.md` 与涉及配置生成或派发的宿主参考：新增角色、继承模式和可验证能力限制。
- `scripts/test_s_models.py` 及必要的现有宿主检查：验证新参数、旧配置和消费约定。
- README 及维护校验中涉及角色数量的内容：与实际模板保持一致。只有实现完成并准备发布时才按既有流程更新版本。

全局技能规则只有实际写死角色或调度约束的位置才调整，不把三档全文复制进去。本次出方案不修改任何安装目录、全局配置或模型角色文件。

## 实施顺序与验收

先完成配置生成和旧配置兼容，再接入公共派发及使用方，最后同步宿主适配与文档。每一步先核验对应行为，避免配置已更新但消费方仍未读取。

实现阶段必须覆盖以下结果：

- 新参数将轻量模型写入新增角色，原有角色与评审项数保持既有规则。
- 不传 `--light` 时回落到常规模型；旧配置缺少轻量行仍可读取和校验。
- 新增角色的中文键、英文键、`--set`、档位解析及继承模式可用。无效模型或档位在写入前被拒绝。
- 重新配置保留已有角色选择，预览和实际写入一致，标记外内容不变，重复写入不重复添加。
- 角色模板、键对照、Codex 角色生成说明与脚本保持一致，原有双模型评审行为不变。

真实会话至少覆盖：明确符号检索、模块内功能、跨模块分析、发现复杂性后返回主线程、用户指定模型、旧配置和禁止委派。核对实际工具参数或可用日志，不能只看回复中的模型名称。

真实宿主验收按实际可访问环境分别记录。文件校验、会话发现、实际读取和行为验证分别报告，没有运行的宿主标记未验证。验证不得为了本方案改变用户的委派授权。

实现后的检查沿用仓库现有脚本和适用测试。设计阶段仅审阅文档；实现后的测试与独立评审记录见同日实施计划。

## 备选方案与取舍

继续使用 `--set` 给原有角色手动配置第三个模型，改动最少，但无法表达通用轻量任务，也容易把复杂探索一起降档。因此推荐新增轻量角色并接入派发点。

把所有任务改成自动评分、失败后自动升级模型，需要额外处理重试、重复写入、消耗上限和结果交接。第一版不采用，先验证明确分类是否有效。

主要风险是任务分错档，以及配置存在但模型并未实际切换。前者用严格的轻量条件和返回主线程处理，后者用真实派发证据核验。子代理启动与上下文传递也有成本，不能仅凭型号定位认定总耗时或总消耗下降。

实施任务及检查结果见 `../plans/2026-11-02-three-tier-models.md`。当前工作区中的其他未提交修改保持原样，不纳入本方案实现范围。
