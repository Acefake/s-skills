# wukong 集成 T3 Code 编排能力方案

日期：2026-11-09。状态：首版已实施；T3 新配置的角色数量改为六个，按 [六角色实施记录](../plans/2026-11-09-t3-six-roles.md) 执行。本文原十五角色设计保留作方案沿革，其他宿主旧入口仍使用十五角色。

建议在现有技能体系中增加 T3 编排适配：保留 15 个角色、预算和任务流程，由适配规则选择原生子代理或 T3 委派工具。模型设置增加提供商实例、模型 ID 和运行参数，支持跨提供商评审及隔离工作区。首期交付配置、派发和生命周期处理，后续再接持续编排与 PR 等待。

## 1. 目标与范围

用户仍通过 s 的技能和角色描述任务，不需要手工拼接 T3 工具参数。集成后应满足：

- 在同一任务中，为实现、研究、评审选择不同提供商的模型。
- 按角色设置推理强度，保留当前已有模型和预算。
- 需要独立工作区时，让 T3 创建并绑定 worktree。
- 正确接收任务完成、失败、取消和用户输入请求。
- 没有 T3 工具的环境保持原有行为。
- 显式指定的提供商、模型或工作区不可用时停止相关派发，不擅自换模型或切回共享目录。

首期不增加独立调度服务，不自动开启多代理，不修改账号、认证和订阅，也不扩展提交、推送、发布授权。能力可用与任务授权分别判断。

## 2. 当前基础与差距

仓库已有：

- `HOSTS.md` 和各宿主工具参考，负责平台差异。
- `setup-s-models` 与 `s_models.py`，负责 15 个角色、预算、预览、写入和解析。
- `wukong-mode/references/subagents.md`，负责角色选择与派发原则。
- `subagent-driven-development` 和独立评审流程。
- `wukong-mode/playbooks/orchestrate.md` 及 `scripts/orch`，负责持续项目协调与本地业务台账。

当前缺口：

1. `scripts/check_marketplace.py` 的宿主校验明确拒绝 T3，`test_host_support.py` 也断言这一限制。
2. 角色行只表达模型及档位，无法完整表达提供商实例与任意运行参数。
3. 通用回退规则允许更换可用工具或顺序执行，需要对 T3 的显式目标加上严格限制。
4. 持续编排流程与 T3 的事件、任务 ID、取消方式尚未对齐。

本会话实时能力发现返回了可运行子任务的多个提供商，并声明支持子任务、跨提供商委派、取消、线程管理和定时任务。工具定义还提供 worktree 隔离与运行参数。以上说明接口可接入，不代表每个模型认证成功或真实任务已经通过。

## 3. 架构与职责

调用顺序为：任务授权检查 → 解析角色配置 → 读取宿主能力 → 解析目标与参数 → 选择执行工具 → 派发 → 接收结果 → 验证交付物。

职责分配如下：

| 层 | 负责内容 |
|---|---|
| 技能流程 | 拆任务、限定所有权、明确输入输出、判断是否需要独立评审 |
| 模型配置 | 保存角色、预算和命名目标，解析提供商、模型与参数 |
| 宿主适配 | 发现工具、决定派发路径、解释返回状态和后续动作 |
| T3 | 运行子任务、绑定工作区、管理运行状态与完成通知 |
| s 的业务台账 | 记录任务归属、产物、验证证据及集成状态 |

适配以技能参考和本地纯解析脚本为主。脚本不模拟 MCP 客户端，不调用内部 T3 接口，不另建进程管理器。工具调用仍由当前主代理执行。

T3 是叠加在底层 Codex、Claude 等宿主上的编排环境。不能检测到 Codex 就跳过 T3，也不能发现 T3 就把所有普通任务都转成委派。

## 4. 模型配置设计

### 4.1 配置分工

T3 管理账号、认证、提供商启用状态和模型目录。s 保存任务分工与目标选择，配置中不保存密钥。

保留原有 `# s 模型配置` 标记段和 15 个角色。给角色行新增 `t3:<别名>` 引用，复杂配置放到 JSON 文件中。

```text
# s 模型配置
# 预算: 省（medium）
检索和简单任务: t3:lookup
写功能和重构: t3:implementation
修 bug: t3:implementation
最难的任务: t3:hard
审问审查者: t3:review
# s 模型配置结束
```

这是节选，正式预览必须展示完整 15 行。首期仍按现有预算约束控制评审项数；跨厂商评审是可选设置，不因接入 T3 增加人数。

拟议目标文件名为 `wukong.t3.json`：

```json
{
  "schemaVersion": 1,
  "targets": {
    "lookup": {
      "providerInstanceId": "codex",
      "model": "gpt-6-luna",
      "options": { "reasoningEffort": "medium" }
    },
    "implementation": {
      "providerInstanceId": "codex",
      "model": "gpt-6.1-sol",
      "options": { "reasoningEffort": "medium" }
    },
    "hard": {
      "providerInstanceId": "codex",
      "model": "gpt-6-astra",
      "options": { "reasoningEffort": "high" }
    },
    "review": {
      "providerInstanceId": "claudeAgent",
      "model": "claude-sonnet-5-5",
      "options": { "effort": "medium" }
    }
  }
}
```

上述提供商及模型来自本会话能力目录，仅用于说明结构，不是已批准的新配置，也不代表模型成本排序。

别名允许字母、数字、下划线和连字符，不能带逗号。模型 ID 保存在 JSON 字符串内，可容纳 DSH 返回的带引号或逗号的 ID，不再经过角色列表的逗号切分。

### 4.2 文件位置与作用域

首期只支持项目级 T3 目标文件：`<项目根目录>/wukong.t3.json`。全局标记段中的原有裸模型名继续有效；项目规则可以按角色覆盖全局规则。

项目根目录取 T3 提供的项目工作区，Git 项目再核对仓库根目录。没有明确项目根目录时不猜路径，要求明确配置文件。

不引入未经验证的 `~/.t3` 用户配置路径。后续如需跨项目共用目标，应先确认 T3 的正式配置扩展机制，再独立设计全局作用域。

项目配置可纳入版本控制，但不得包含认证信息。其他贡献者没有同名提供商实例时，预检会指出需要本机映射。worktree 任务依赖此文件时，必须确认该文件已包含在其基准提交；未提交配置不能假定在子工作区存在。

### 4.3 优先级与兼容规则

解析优先级：本次用户明确指定 → 项目角色配置 → 全局角色配置 → 已有技能默认值。

- 裸模型名：按当前提供商解析；当前提供商没有此模型时报告错误，不到其他提供商中自动匹配。
- `t3:<别名>`：必须在目标文件中存在且字段完整，按目标指定提供商解析。
- `inherit-parent` 或 `auto`：继承父会话提供商与模型，默认保留父参数。
- 旧英文角色键：继续支持；中文键与英文键同时存在时沿用中文优先。
- 旧标记段和旧模型行：不自动重写、不静默迁移。
- 无 T3 工具时遇到 `t3:` 引用：明确报不可执行，保留配置；其他不依赖它的任务仍可继续。

目标 `options` 保存厂商专用参数，角色括号档位是通用推理强度。同一角色两处同时显式设置推理强度时，校验报冲突，要求只保留一处；不靠隐式优先级掩盖矛盾。

未显式设置推理强度时，用预算生成目标档位，再按能力目录映射到合法选项。厂商无可确认的对应档位时展示实际可选项；不凭名称猜测。明确要求的档位不支持时停止，不擅自降档。预算是角色策略，不是货币额度上限。

### 4.4 参数继承

`target.options` 会覆盖或继承父设置，必须区分缺省与空对象：

- 同提供商、相同模型且无参数覆盖：允许省略，继承父设置。
- 切换提供商或模型：构建该目标完整、合法的参数集合；不把父提供商参数直接带过去。
- 新目标没有可用参数且无需额外设置：显式传空对象清除父参数。
- 无法确认新目标支持的参数：阻止相关派发并说明，不声称已完成映射。

例如 Codex 的 `reasoningEffort` 与 Claude 的 `effort` 分别来自能力定义，不能把一个名字直接复用给另一个提供商。

### 4.5 设置交互

扩展 `setup-s-models`，沿用现有分步确认：

1. 检测底层宿主和 T3 工具，确认本次配置作用域。
2. 调用能力发现，列出可运行提供商、模型及参数。按需搜索完整目录，不把截断目录当作全部可用模型。
3. 保留已有预算并让用户选择是否调整。
4. 展示完整 15 行，以及每个别名的提供商、模型和参数；旧配置不可用项单列。
5. 预览角色标记段和 JSON 文件的完整差异，取得最终写入确认。
6. 验证两份候选文件后备份、写入、回读校验。跨文件写入中断时恢复备份，不能留下悬空别名。

确认模型设置不等于授权启动子任务。配置校验成功也不等于实际模型运行通过。

## 5. 执行工具选择

先判断任务是否已授权委派，再选择工具：

| 条件 | 执行方式 |
|---|---|
| 普通任务，无委派需要 | 主代理执行 |
| 同提供商、原生支持的模型、无额外参数和隔离要求 | 原生子代理 |
| 跨提供商 | T3 `delegate_task` |
| 用户要求额外运行设置 | T3 `delegate_task`，参数放 `target.options` |
| 独立 worktree | T3 `delegate_task`，`isolation: worktree` |
| 用户明确要求 T3 委派 | T3 `delegate_task` |

T3 的模型目录不证明原生子代理接受同一个模型名；两种工具分别按自身定义校验。

每个线程第一次 T3 委派前调用一次 `orchestrator_capabilities`；发生错误或用户要求切换提供商时重新发现。不可用目标按实际原因报告，不自动换提供商、原生工具或 CLI。

子任务不会继承父对话历史。每份任务说明应带齐目标、文件所有权、限制、已有决定、输入、交付物、验证要求和前轮发现。不得传入密钥。主代理负责检查结果，不把子任务总结直接视作交付事实。

## 6. 任务生命周期

以 T3 返回状态为事实来源，业务台账只保留任务关联和证据。

- 保存 `taskId`、子线程与运行 ID、链接、实际模型和有效参数。
- 返回 `next` 要求结束当前回合时，先报告已启动及等待事项，然后结束回合，等待完成唤醒。
- 不用循环查询、sleep、文件监听或定时任务模拟完成通知。
- `mode: wait` 只用于本回合必须依赖结果的情况；遇问题、审批或超时，按实际返回处理。超时不等于取消。
- 等待用户输入时保持任务待处理，不把超时或沉默当成批准。
- 需要用户提供令牌、PIN 或配对码时使用 T3 `request_secret`，不在任务说明或普通对话中收集。
- 替换或不再需要的委派通过 `task_cancel` 取消；不能用线程中断代替任务取消。
- 新一轮委派评审必须创建新任务，带上旧发现及修复内容，不用旧线程消息代替新审查。
- 子任务失败后先核对是否留下改动或正在运行的工作，再决定是否重试；不能立即重复启动写入任务。

`clientRequestId` 按一次逻辑派发生成并记录。接口未确认幂等保证前，只把它作为关联字段。派发响应丢失时先用 T3 提供的状态工具确认，无法确认就标为状态未知，避免重复执行。

讨论线程时使用 T3 返回的链接；只有状态或 ID 可见时明确说明链接缺失，不拼接猜测。

## 7. worktree 与集成边界

需要独立检出时由 T3 创建并绑定 worktree，不在 shell 中预先创建后假定已绑定。委派的 worktree 基于父提交，父工作区未提交改动不在其中。

派发前检查任务依赖的代码是否已在基准提交中。需要未提交改动时，说明依赖，选择已获授权的提交方式或共享目录串行处理；不能擅自提交，也不能悄悄放弃隔离。

共享目录的并发任务按文件所有权隔离；无法隔离写入时改为串行。单独检出能隔离文件写入，但仍需处理共享端口、数据库和外部资源。

只有用户明确要求新顶层线程时使用线程创建工具。新线程的基准按 T3 的 `workspaceStrategy` 规则处理，不将它与委派 worktree 的父提交规则混用。

子任务完成后由主代理核对改动、提交 SHA、验证证据和冲突。未经授权不自动合并、推送或清理工作区。

## 8. 持续编排与 PR 能力

第二阶段让 `wukong-mode` 的 orchestrate 流程使用统一执行规则。保留 `scripts/orch` 的业务台账，不复制 T3 的实时运行状态。可增加单独的任务关联记录，将业务单元 ID 关联到 T3 任务、线程、运行及链接，避免直接破坏现有 TSV 格式。

T3 管运行和唤醒，台账管任务归属、分支、产物与验证结果。重启后通过已记录 ID 查询一次并核对；发现状态矛盾时先对账，再继续派发。

PR 能力分开接入：

- 创建、接手或推送 PR 后，下一步链接完整 PR URL，包括堆叠中的每层。
- 用户要求监控，或已授权操作仍等待检查时，先完成必要推送，再调用 T3 PR watch 并结束回合。
- 等待过程中不运行轮询循环或 `gh --watch`。
- 不再监控、完成或交还控制时按 T3 当前规则解除监控；委派子任务不负责 watch。

远程机器、定时执行和工作流设计作为后续独立范围，首期不以“支持 T3”为由自动启用。

## 9. 错误处理与授权

| 情况 | 处理 |
|---|---|
| T3 工具未加载 | 按规则尝试发现；明确缺失后报告，不伪造调用 |
| 提供商禁用、模型不存在 | 停止该派发，保留用户设置，给出实际错误 |
| 参数非法或相互冲突 | 写入前或派发前拒绝，指出字段和合法选项 |
| 配置损坏、版本未知、别名不存在 | 不静默覆盖；保留文件并报告修复位置 |
| 子任务需要审批 | 交由用户或 T3 审批机制处理，父代理不代批 |
| worktree 无法创建 | 报错，不切换到共享目录写入 |
| 任务完成但证据不齐 | 标为待验证，不标交付完成 |
| 通知重复或晚到 | 按任务与运行 ID 对账，不重复合并或计入完成 |

配置是路由数据，不能携带扩大权限、自动批准或任意命令执行字段。运行权限默认继承父级；只有用户明确要求受监督运行等设置时才传对应字段。

## 11. 分阶段实施

1. **配置与规范。** 固定配置格式、优先级和工具路由；完成旧配置兼容、目标校验与预览。此阶段不启动真实模型任务。
2. **最小真实委派。** 在临时项目验证同提供商路由、跨提供商只读任务、参数传递、完成回传和取消；检查实际执行的模型。
3. **隔离与评审。** 验证 T3 worktree 绑定、基准提交、未提交改动边界，以及新的独立评审任务。形成可发布的首期能力。
4. **持续编排。** 增加台账关联、恢复对账和 PR link/watch，验证重复事件与中断恢复。
5. **发布与文档。** 按仓库版本流程同步清单、锁文件、规则和使用示例；经授权后提交、推送与发布。

每阶段通过验收后再进入下一阶段。实际工期和费用尚无测量依据，实施前按确认的范围估算。所需资源为现有开发环境、T3、至少两个可认证的提供商，以及可丢弃的测试仓库；真实模型调用消耗相应账号额度。

## 12. 验证与验收

本方案只读编写，不执行测试。实施时按以下范围验证：

### 配置测试

- 原有标记段、英文键、预算、裸模型名与继承行为保持兼容。
- 别名解析、特殊字符模型 ID、缺失目标、未知版本和冲突参数均有明确结果。
- 跨提供商不会携带父提供商参数；空对象与缺省继承行为分别验证。
- 拒绝畸形配置并保留旧文件；双文件写入失败可恢复。
- 允许 T3 适配后，其他退役宿主仍会被校验拒绝。

### 路由与生命周期测试

- 普通任务不额外委派；原生与 T3 的选择符合规则。
- `next` 要求等待唤醒时结束回合，无轮询或重复启动。
- 超时保持运行状态，取消关联到正确任务。
- 失败、输入请求、审批、重复完成通知、状态未知均不会被当作成功。

### 真实验收

- 完成一个跨提供商只读任务，核对返回的模型、参数和产物。
- 完成一个由 T3 创建 worktree 的小任务，核对父工作区未提交文件未被带入。
- 取消一个可安全中止的测试任务，确认任务最终状态。
- 对一次修复发起新的只读评审，确认评审任务 ID 与前轮不同。
- 第二阶段分别验证 PR 链接、等待、唤醒和解除监控。

认证失败的提供商只报告失败，不能通过静态目录宣称其已可运行。证据应记录任务链接、有效配置、基准 SHA、输出与验证结论，不记录密钥和无关会话内容。

## 13. 备选方案与取舍

只补一份 T3 工具说明，改动最小，但角色设置和生命周期仍可能走错，适合临时手工使用。另建编排服务可自定义更多行为，但会重复承担 T3 的进程、状态与恢复职责。

本方案选择统一适配规则加结构化模型目标，复用现有技能和 T3 的运行能力。首期配置、派发、隔离、结果处理一起交付，避免出现“能启动任务，却不能稳定使用指定模型”的半成品。

## 14. 审阅结论与实施前提

建议批准首期配置、派发、生命周期及隔离范围，持续编排与 PR 自动等待单列第二阶段。实施前需要确认本方案的项目级目标文件与别名格式；实际配置写入仍必须单独展示完整变更并取得最终确认。

方案依据为本仓库现有角色解析、宿主适配和编排台账，以及本会话 T3 工具定义与实时能力发现。未改运行配置，未启动委派任务，未将能力发现视为端到端验证。现有自动换工具规则、双文件写入恢复、不同工具的模型接受范围，是实施与审查的重点。
