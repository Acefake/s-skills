# 系统化调试

**铁律：没有完成根因调查，就不提出或实施修复。** 简单、紧急、已经尝试过多次修复，都不是跳过调查的理由。

适用于 bug、测试失败、意外行为、性能、构建和集成问题。按下面四个阶段推进，当前阶段完成后再进入下一阶段。

## 阶段 1：根因调查

1. **读真实错误。** 读完报错、警告和堆栈，记录文件、行号和错误码。
2. **稳定复现。** 明确触发步骤、输入、预期和实际结果。不能稳定复现时先收集数据，不猜原因。
3. **查近期变化。** 对照 diff、提交、新依赖、配置与环境差异。
4. **观察组件边界。** 跨组件问题在每个边界记录输入、输出、配置传播和状态；运行一次，定位第一个出现偏差的边界。具体示例见[多层系统取证](references/multi-layer-evidence.md)。
5. **反向追踪数据。** 从坏值的出现位置追到调用方和最初来源，在产生错误的地方修。详细方法见[root-cause-tracing.md](root-cause-tracing.md)。

## 阶段 2：模式分析

1. 找同一代码库中能正常工作的相似路径。
2. 套用模式前完整阅读参考实现，弄清依赖、配置和假设。
3. 列出正常路径与故障路径的差异，不因差异小就排除它。

## 阶段 3：假设与检验

1. 写一个具体假设：“我认为 X 是原因，因为证据 Y。”
2. 用最小实验检验，一次只改变一个变量。
3. 假设成立才进入实施；不成立就根据新证据形成下一个假设，不叠加猜测性补丁。
4. 不理解的地方直说，继续调查或请求所缺的信息，不装作已经确定。

## 阶段 4：实施

1. **先得到失败证据。** 按[tdd](../tdd/SKILL.md)判断是否有便宜、稳定的测试点。适用时先写回归测试并确认修前失败；不适用时用已有复现命令、真实界面操作或日志等最接近的证据，不为走流程搭建昂贵测试环境。修前无法复现时明确验证缺口。
2. **只修已确认的根因。** 一次一处，不捆绑无关改进或重构。
3. **验证。** 运行回归检查，确认用户可观察的问题消失；其他检查按[s-router验证分档](../s-router/SKILL.md)，所在模块先验，全量留到需要时。
4. **失败后返回调查。** 记录尝试次数。少于三次，回到阶段 1；三次或更多时停止，不做第四次猜测性修复。
5. **连续失败时质疑架构。** 检查是否每次修复都暴露新的共享状态或耦合、需要大范围重构、或在别处产生症状。和用户讨论根本假设及是否需要架构调整，再继续修复。

## 何时退回调查

出现下面任一情况就停下：尚未追踪数据就提修复、先补丁后调查、同时改多个变量、照抄未读懂的模式，或认为“再试一次”可以代替证据。

用户指出“那没有发生”“别猜”“我们卡住了”时，也回到阶段 1，核对自己声称看到了什么。

## 根因确属环境或时序时

只有完成上述调查，证据才可能支持“原因来自外部”。记录调查范围，采取恰当的重试、超时或错误反馈，并补监测或日志；不能以“环境问题”结束尚未完成的调查。
