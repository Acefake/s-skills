# 为领域建模

把真实的领域编码进一个数据结构，而不是把它散落在各种条件判断里。和领域相匹配的结构能让非法状态根本无法表示，还能删掉很多分支。在写代码时就选好它，成本很低。等以后再补回来，看起来就成了一次重构，然后就会被一拖再拖。

可以考虑：

- 用状态机，代替散落的布尔值、阶段标记或生命周期检查。
- 用有类型的模型，代替松散的参数或反复出现的形状假设。
- 用映射表、注册表、查找表或可辨识联合类型（discriminated union），代替分散在多个文件里的分支。
- 用 reducer 或命令/事件模型，代替随手的状态修改。
- 让一个模块围绕一块领域知识来组织，而不是按“加载、校验、转换、保存”这样的步骤顺序。执行顺序不等于归属。
- 用一个小的模块边界，把重复的行为、归属或不变量收拢到一起。
- 在访问方式需要的地方，用队列、缓存、索引、图、树或规范化的集合。
- 其他任何合适的结构。如果都不合适，就先弄清楚代码绝不能允许什么、数据会怎样被读取，再去找恰好能表达这些的结构。

不要硬套抽象。如果现在的形状已经清楚、局部，而且不太会增长，宁可用平淡无奇的代码。对那种增加了间接层、却没有删掉分支、重复规则、非法状态或生命周期风险的抽象，要保持怀疑。

如果一个新功能让已有的 if/else 链又多了一个分支，或者出现了第二个必须和第一个保持同步的布尔值，就说明你跳过了这一步。按时间顺序拆分是另一个信号：按阶段命名的模块会在各个步骤里重复同样的领域规则。
