SKILL.md「子智能体」保留派发类型、审查责任和恢复条件。模型、推理等级、速度和默认档位按下面的全文执行，派发前读完。

## 三档模型与派发顺序

模型配置只决定已获授权的子代理用哪个模型，不授权委派，也不切换主会话模型。先核对当前任务授权和宿主能力，再按下面顺序选择。每一步都保留原任务的只读限制、工具要求、文件归属和验收条件。

1. 搜索或已有脚本能直接完成时，直接用工具，不为一次检索额外派代理。
2. 用户明确指定本任务模型时采用该选择；本次明确指定的模型或档位优先于自动分类。不得覆盖宿主固定角色的模型后宣称已换模。
3. 范围明确、规则明确、结果易核对，且无需自行判断业务语义或决定修改范围时，可以使用“检索和简单任务”，英文键 `lookup and simple tasks`。例如限定范围内查符号引用、提取字段、按确认映射做机械修改。查架构、复杂调用链、历史动机不因“查代码”而视为轻量任务。
4. 轻量行缺失时，沿用当前工作流原本的角色与模型。不要从其他角色猜测常规模型。旧 17 行配置继续有效；新配置中的轻量行可以与常规行共用模型。
5. 其他任务使用原工作流角色。困难实现、棘手并发、跨模块修复使用“最难的任务”。综合、架构和评审保持各自角色，不因新增轻量档自动降档。用户明确要求某个角色模型时，不再自动改为其他角色。
6. 模型或参数被宿主拒绝时，报告实际错误并交回主线程，不静默换模型或重试。不能指定模型时采用继承模式，并如实说明没有分流。

轻量角色从其角色行读取模型与档位，行值按[角色键与格式](../../setup-s-models/references/role-keys.md)解析。没有显式档位时，预算起始档位最多取 `medium`，再按模型实际支持范围下调。显式档位优先；不能传档位的宿主不假称已生效。预算控制起始推理目标和既有评审项数，三档分类不增加人数。

例如已授权的检索任务需要轻量模型时，先运行 `python <setup-s-models>/scripts/s_models.py resolve <配置文件> 检索和简单任务 --json`，将输出中拆开的模型与档位按宿主能力传入。缺少该角色时解析原工作流角色，不能把错误结果当成轻量模型配置。宿主模型固定在自定义角色文件中时，选择与目标配置一致且本会话确实已发现的角色。

轻量任务发现范围不清、需要跨模块语义判断、证据相互矛盾或必须扩大修改范围时，返回已查证据、未完成部分与原因，由主线程决定下一步。第一版没有自动升级重试。返回结果列明文件、符号位置、查找范围、实际修改和未确认项，主线程核验后再交付。

以下原有派发类型、推理调整和恢复规则受上述顺序约束。三个档位的具体型号由 setup-s-models 根据当前宿主实际可派发名单推荐，不按厂商、系列前缀或固定型号判定强弱。

## 子智能体

**在 playbook 的某一步里派出的任何子智能体（subagent，派出去干活的小助手，比如写代码的代理、临时的帮手），都用能读写文件、能用全部工具的通用类型。** 每个子智能体的提示词里都写上这个 SKILL.md 的绝对路径，要求它动手前先完整读一遍（包括上面的原则索引），用到哪条原则，就去读那条原则的 skill。收到 `/s-mode` 的那个对话负责运行 playbook。永远不要派一个子智能体去运行 playbook 本身。被分派到的工作流程 skill（`how`、`why`、`interrogate`、`reflect`、`swarm`）会为了多模型审查自己选子智能体的类型和模型。尊重 skill 的规定，不要强行统一。各软件里这个通用类型叫什么，见宿主适配参考。

**每次派子智能体的默认设置。** 后台运行（不用干等它，做完再取结果）。用能写文件的通用模式。只做只读探索时可以用只读类型，但有的软件的只读模式会去掉 MCP 工具，需要 MCP 的活别用只读。给文件路径，而不是把上下文整段贴进去。每个角色明确指定模型：默认写代码用快速的写代码模型，文字和判断用判断力最强的模型（具体模型名和配置方法见宿主适配参考）。写代码的代理按难度分档。最难的改动（横跨多处的设计、棘手的并发、精妙的算法）交给你判断力最强的模型，不管这个任务是需要对模糊的意图做判断，还是一串要一字不差执行的、规定得很精确的步骤。简单的机械性修改按上文选择轻量角色，缺少该行时维持原角色。如果你的软件里有 s 的模型规则（`/setup-s-models` 生成的，见宿主适配参考），规则里每个角色的那一行，会覆盖这些默认值，以及被分派到的 skill（`how`、`why`、`swarm`、`architect`、`interrogate`、`reflect`）里的模型选择。没有对应行的角色保持默认值；角色行写的是 `inherit-parent` 或 `auto` 的，那个角色用父级聊天的模型运行（派的时候不指定模型）。每个写代码类 playbook 配置的模型，来自它对应的那一行（`写功能和重构`、`修 bug`、`性能问题` 或 `爬坡优化`；没有再读旧键 `feature, refactoring`、`bug-fix`、`perf-issue`、`hillclimb`），最难的改动读 `最难的任务`（旧键 `hardest tasks`）。文字和判断读 `判断和写作`（旧键 `judgment and prose`）。同一角色两行都在时用中文键。配置在 `# s 模型配置` 到 `# s 模型配置结束` 之间；旧标记 `# s model configuration` 到 `# end s model configuration` 同样有效。其余角色的中文键见 [角色键对照](../../setup-s-models/references/role-keys.md)。软件里没有这份规则时，按文末的对应关系选模型；选不了就不指定，让它继承父级。

**让模型和工作相匹配。** 每次派出之前，从这个角色的那一行或默认值出发，挑选这项工作需要的推理等级和速度。角色行值带括号时（如 `sonnet（medium）`），括号里的档位就是这个角色的起始等级，派发时按宿主参考传给推理档位参数，不能传就如实说明。`/setup-s-models` 的预算决定每个角色的起始等级。标记段 `# 预算` 或旧行 `# budget` 括号里的档位就是起始等级：`省（medium）`、`中（high）`、`大（xhigh）`、`不限（max）`；旧写法 `small (medium)`、`medium (high)`、`large (xhigh)`、`unlimited (max)` 相同。没有预算行，或预算值为 `inherit-parent` 时，常规角色起始等级是 xhigh；轻量角色仍按上文最多取 medium。对最难或最精细的工作，提高一级，最高到 max。判断类工作降低一级，常规工作降低两级或更多。只有在工作很紧急时才用快速模式，紧急的意思是 CI 或主干是红的，或者有人正卡着等这个结果。否则用标准速度，也就是同一个模型的非快速版。验证是例外，保持用 `群体作战的工作者`（旧键 `swarm workers`）的模型和速度（各软件的默认值见文末）。只改推理强度和是否为快速版，保持角色指定的系列不变，这样一个多样化的审查组仍然是多样化的。只有当前工具确实支持该系列对应档位时才调整；没有匹配项就保留确认过的配置，不猜测模型名。用 `auto` 或 `inherit-parent` 的角色保持用父级的模型。如果派子智能体的工具拒绝了调整后的模型名，不要再试另一个调整后的模型名。报告实际错误并交回主线程，不替换型号。软件不能调推理等级或快速版的，这一段只当作“难活用强模型、简单活用快模型”的提示。

每个子智能体的工作都由你负责。审查 diff，写你自己的总结，不要把它说的原样转述。第二意见，就是把同一个提示词交给一个不同的模型。意见一致是很强的信号。

**默认用新的子智能体。** 把新的工作交给一个新的子智能体，并给它整合好的范围，也就是最初的任务说明、之后的每一条指示，以及前一个智能体的报告和分支。这适用于一轮修复、一次跟进、一次重试，以及队列里的下一项。只有当新的工作严格需要存在于某个已有子智能体里、又很难转移的状态时，才恢复它、给它发消息或给它排一个跟进任务：它本地检出的代码、它未提交的改动，或者它还在运行的进程，比如一个开发服务器、一个模拟器或一个照看 PR 的监视器。对一个正在运行的智能体下达停止或暂停的命令，不算复用。像 PR 负责人这样的角色，生命期比它的智能体更长。一旦那个智能体返回，就由一个新的智能体接手这个角色的下一轮。靠中断串起来的恢复会悄悄丢掉指示，所以要派一个带着整合好范围的新子智能体，而不是相信一份“已完成”的总结。
