# 测试行为，而不是实现

一个测试，是对代码为它的使用者做了什么的一个断言。使用者可以是调用方、最终用户或另一个服务。行为，就是这些使用者通过他们所用的接口能观察到的东西。包括返回值、错误、他们能读回来的状态，以及对代码之外系统的影响，比如发出的一个请求、写入的一行数据、发出的一条消息。实现，是他们观察不到的东西：私有的辅助函数、内部的调用顺序、中间数据，以及是哪个内部协作者干的活。

用两种想象中的改动来评判每个测试：

- **把行为改坏。** 让代码返回错误的值、跳过一个影响，或者把这个影响做两次。如果测试仍然通过，它什么也证明不了。常见原因有：断言比约定宽松；期望值是用被测代码自己算出来的；重复写了一遍某个常量或提示词字符串，却从来没运行读取它的代码；断言的是测试自己构造的数据。
- **改变内部实现。** 保持每一个可观察的结果不变，只重构底层代码。如果测试现在失败了，说明它被钉在了实现上。每次重构它都要重写，而且仍然抓不到任何 bug。

保留那些能抓住第一种改动、又能扛过第二种改动的测试。其余的重写或删掉。要写出两者都做到的测试，就用一个具体的输入，通过使用者的接口去驱动代码。期望值要从需求推出来，而不是从代码的一次运行结果得来。断言约定所承诺的东西，不多也不少。

决定权在约定，而不在断言的形式。当承诺是“空购物车永远不会扣款”时，断言支付客户端没有被调用，就是在测行为。再配一个确实会扣款的用例，让测试证明它能看到调用。被模拟的外部服务收到的数据，是行为，因为那个服务能观察到它。对内部辅助函数的调用是实现，因为没有使用者能看到它。没有记录匹配时，空列表就是准确答案；而如果测试只需要有某个结果，空列表就是一个空洞的检查。精确的错误消息文字，钉住的是没有调用方会去读的措辞。调用方会据此分支处理的错误类型，才是约定。

测试也可以钉住一个不变量，而不是一次调用，比如某个键必须同时存在于两张表里，或者一个编译期的类型检查。这个不变量就是行为。
