# 把我自动化

一个有引导的流程，把用户的工作习惯变成智能体会遵守的技能。产出是一个为他量身定做的 `-mode` 技能（例如 `jay-mode`、`priya-mode`）。

本技能只负责先后顺序：挖掘历史（第 1 步）、直接提问（第 2 步），写 SKILL.md 用 [author-skill](../author-skill/SKILL.md)，文字用 [unslop](../unslop/SKILL.md)。它不代替这些步骤。

## 流程

### 0. 检查有没有已有的技能

查找和用户代号匹配的 `*-mode/SKILL.md`。Claude Code 看 `.claude/skills/` 和 `~/.claude/skills/`，Cursor 看 `.cursor/skills/` 和 `~/.cursor/skills/`；Codex、WorkBuddy 的个人技能目录不确定，再在当前仓库里搜。mode 技能可能放在个人分类目录里，不一定在最顶层。已有一个时，用当前宿主的提问工具确认意图（没有就在对话里问），除非用户已经说了“更新我的技能”之类的话：

- 更新已有的技能（重复运行时的默认选项）
- 从头重新做（很少见，做之前先问为什么）

更新模式会改变后面的流程：
- 第 1 步只挖掘这个技能上次修改之后的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是哪些变了或缺了，而不是从零开始要记录什么。
- 第 4 步直接编辑已有文件。保留用户没有否定的部分，有新证据的部分才修改，只有真正的新规则才加新章节。

### 1. 挖掘他的历史

对话记录是私人内容。读之前先说明要读哪个范围，用户同意再读。只读当前项目对应的记录目录：Claude Code 是 `~/.claude/projects/<当前项目>/`，Cursor 以系统提示里写明的 `agent-transcripts/` 为准。不对 `~/.claude/projects/*/` 这类上级目录做通配符搜索，那会越过项目边界，读到无关项目里的私人聊天。

在这个范围内，把最近的对话切成几片（例如最近 2–4 周分成 3 片，每片材料足够），按 [s-mode](../s-mode/SKILL.md)「子智能体」一节和 [subagents.md](../s-mode/references/subagents.md) 选每个子代理的模型、推理等级和速度，派只读子代理分头挖掘；没有授权或没有子代理能力时，主任务自己逐片读。每片返回一份简短的结构化清单，列出看到的模式和证据出处。默认值得寻找的信号：

- 回复偏好（长度、语气、格式、“说简单点”之类的纠正）
- 分派习惯（子智能体、模型、专门的工作流程、并行）
- 验证态度（“完成”指什么、单元测试还是真实复现、审查者）
- 代码和文字规范（风格、引用的原则、lint/格式化工具）
- 流程习惯（worktree、提交、PR、审查/合并工具）
- 元偏好（在任务中途修技能、提议新技能）

在把一个信号提升为规则之前，先在各片之间交叉核对。在 2 片或更多片里都出现的模式可信度高；只出现一次的信号很弱，通常丢掉。

### 2. 直接问用户

挖掘会漏掉还没出现过的意图。用当前宿主的提问工具做结构化多选题，没有就在对话里列选项。不要让用户从零开始打字。

形式：一两个问题，每个 4–6 个选项，分类问题允许多选。先问大的（“哪些方面最重要？”），再针对选中的方面给出具体选项。结构化的几轮问完后，再在聊天里问一个开放式问题，补上选项漏掉的东西。不要一下子甩出 20 个问题。

### 3. 把发现归类

把收集到的信号分成几个章节。常见的有这些（只用适用的）：

- **回复风格**：长度、语气、格式。
- **自主程度**：不问就做多少事、MCP 工具的使用。
- **先弄懂**：确定范围或调查一个改动时用哪些技能。
- **子智能体**：默认做法、并行、什么模型做什么任务、专门的工作流程。
- **文字/代码规范**：原则、lint 工具、风格指南。
- **审查和验证**：复现态度、验证类技能、实时测试工具。
- **流程**：git worktree、提交、PR、审查/合并工具。
- **技能**：写技能的习惯、先修技能、提议新技能。

读 [s-mode](../s-mode/SKILL.md) 来把握粒度，不要照抄它的内容。用户的规则和 s-mode 的不一样。

### 4. 起草技能

用 [author-skill](../author-skill/SKILL.md) 写。放置方式：

- 路径：保留已有 mode 技能所在的位置。新的 mode：Claude Code 放 `.claude/skills/<handle>-mode/SKILL.md`，用户要个人技能就放 `~/.claude/skills/<handle>-mode/`，Cursor 对应 `.cursor/skills/` 和 `~/.cursor/skills/`。Codex、WorkBuddy 的个人目录不确定，先写仓库里的 `skills/<handle>-mode/SKILL.md`，并告诉用户按该软件的方式加载。不要假装写进某个没确认过的家目录就会自动生效。
- 代号（handle）：用户的名字，或者他选的标识。
- Frontmatter 的 `description`：在用户的名字 + `/<handle>-mode` + “按他的风格工作” 时触发，而不是在“写代码”“审查 PR”这类通用关键词上触发。
- Frontmatter 至少要有 `name` 和 `description`，`description` 保持为一个 YAML 值；标点或换行需要时加引号。
- Frontmatter 默认写 `disable-model-invocation: true`。只有用户明确希望他的 mode 每一轮都生效时才去掉。

### 5. 反复打磨文字

对每一行都用 [unslop](../unslop/SKILL.md)。把草稿给用户看，接受反馈，做好多次修改的准备，狠心地删。mode 技能不是一本使用手册。

### 6. 落地

写文件、提交和开 PR 都按[commit-pr](../commit-pr/SKILL.md)和已有授权执行，不直接推送到主分支。没有授权就保留工作区修改并报告。

## 防护规则

- **不要只根据一次对话下结论。** 说过一次、另一次又被推翻的偏好是噪音，要多次出现才能写成规则。
- **不要耍小聪明。** 复述其他技能的内容、自造比喻、给智能体读者写“诗意”的文字，只有成本没有好处。保持可操作。
- **引用，不要内嵌。** 用户依赖的其他技能以路径引用的形式出现，不贴摘录；他在别处维护的原则文档也一样。
- **章节越少越好。** 只有用户在某方面有具体的、和默认不同的规则时才加这一节。“沟通要清楚”不算一节，“段落要短。比较选项时用表格。只有各项真正并列时才用圆点列表。”才算。
- **规则里的称呼要通用。** 祈使句里用“用户”，不用作者的名字。
- **不要硬凑对称。** 用户没有值得写下来的流程规则，就整个跳过“流程”这一节。

## 评估

`-mode` 技能是主观的产出，不需要基准测试循环。和用户一起凭感觉检查：读起来像他吗？漏了什么吗？然后就交付。只有这个技能的触发准确度在实际使用中确实成了问题，才去做一轮描述优化。

## 什么时候不用

- 用户想要一个针对具体任务的技能（而不是工作习惯）：不用挖掘，用 [author-skill](../author-skill/SKILL.md)。
- 用户想记录一个很窄的流程（例如“我是怎么写提交信息的”）：那是普通技能，不是 mode 技能。

## 在不同软件里怎么用

提问工具和并行子代理的派法，按当前宿主的工具文件（见[宿主适配](../../HOSTS.md)）和 s-mode「子智能体」一节。找不到工具、类型或模型时，先读 [host-fallback.md](../s-mode/references/host-fallback.md)，用宿主实际支持的替代并说明。
