# 提问写法

怎样写出有依据、能得到可执行答案的澄清问题。改写自 severity1/claude-code-prompt-improver 的 question-patterns（MIT）。

## 写问题的原则

1. **有依据**：每个选项都来自真实发现，不来自假设。
2. **具体**：差的是「换一种做法」，好的是「用 JWT，放 HttpOnly cookie」。
3. **带上下文**：选项描述里写取舍，为什么有这个选项、选了意味着什么、什么时候合适。
4. **一题一个决策点**：差的是「哪个文件、怎么改？」，好的是只问「哪个文件？」，做法另起一题。
5. **能选**：每题 2 到 4 个选项。少于 2 个不是选择，多于 4 个让人无从选。「其他」由宿主自动提供，不用自己写。

## 提问前自查

- [ ] 已做完研究，发现已记下
- [ ] 每个选项都来自研究
- [ ] 每个选项具体、能直接执行
- [ ] 描述里带了取舍
- [ ] 问题之间互相独立，先答哪个都行
- [ ] 总数 1 到 6 个

## 字段

调用宿主的提问工具时（工具名见[宿主适配](../../../HOSTS.md)「向用户提问的工具」），每题包含：

| 字段 | 要求 |
| --- | --- |
| 问题 | 清楚、具体，以问号结尾 |
| 标题 | 短标签，不超过 12 个字 |
| 是否多选 | 默认单选；选项不互斥时才多选 |
| 选项 | 2 到 4 个。每个有简短名称（1 到 5 个词）和一句描述 |

## 按类型的模板

### 目标

用在「不知道改哪个」。选项取自研究里找到的真实文件，带行号。

```
问题：你说的是哪个登录问题？
- 登录认证失败（auth.py:145，try/catch 吞掉了错误）
- 会话超时（session.py:89，超时后没有跳转）
```

### 做法

用在「有多种合理实现」。选项取自项目里已有的写法，并说明哪个与现状一致。

```
问题：缓存用哪种方式？
- Redis（项目已用于会话缓存，与现状一致）
- 进程内存（最简单，但多实例不共享）
```

### 范围

用在「不清楚改多大」。

```
问题：这次重构覆盖到哪？
- 只改 users 模块（3 个文件，风险小）
- 连同调用方一起迁移（14 个文件，需要同步改测试）
```

### 优先级

用在「几件事只能先做一件」。选项写出各自的依赖和影响。

### 配置

用在「依赖环境或开关」。选项写出项目里已有的配置位置和默认值。

## 数量

| 数量 | 场景 | 例子 |
| --- | --- | --- |
| 1–2 | 简单含糊 | 改哪个文件、用哪种做法 |
| 3–4 | 中等复杂 | 范围 + 做法 + 如何验证 |
| 5–6 | 大功能、多个决策点 | 范围、存储、鉴权、测试、迁移；考虑转 brainstorming |

## 生成选项

- **从研究里来**：每个选项能指到文件、文档或提交。
- **给可操作的上下文**：写清选了之后会动哪里。
- **写取舍**：快与稳、简单与灵活。
- **用代码证据**：「项目里有 15 个 try/catch，8 个抛自定义错误」比「错误处理不一致」有用。

## 常见错误

| 错误 | 问题 | 改法 |
| --- | --- | --- |
| 泛泛的选项 | 「换种方式」「其他方案」没法执行 | 换成研究里找到的具体做法 |
| 选项太多 | 超过 4 个让人无从选 | 合并相近的，留最有区分度的 |
| 引导性提问 | 把推荐写成唯一合理的 | 中立描述；要推荐就明说是推荐并给理由 |
| 复合问题 | 一题问两件事 | 拆开 |
| 没研究就问 | 用户一眼能看出你没读代码 | 先研究，问题里带上发现 |

## 提交前清单

- 研究完成并记下发现
- 每个选项有依据、具体、带取舍
- 每题只问一件事
- 总数在 1 到 6 个之间
