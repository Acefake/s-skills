# 用 TDD 修 bug

修一个有清楚、便宜的测试路径的 bug 时，在改正式代码之前，先把出错的行为变成可以运行的检查。目标是一个聚焦的回归测试（regression test，防止同一个 bug 再出现的测试）：修复前失败，修复后通过。

不切实际时不要硬写测试。如果能用的测试需要大范围搭建测试环境、脆弱的模拟对象（mock）、很慢的端到端基础设施、只有生产环境才有的状态、含糊的复现步骤，或者大量无关的测试数据（fixture）改动，就不要新加测试，改用最接近、有用的验证方式。

## 流程

1. **弄懂这个 bug。** 找出预期行为、当前行为、受影响的路径，以及最小的、能观察到的复现方式。
2. **选最窄的可运行检查。** 优先用这段代码路径已经在用的、最接近的单元测试、组件测试、集成测试或回归测试。如果没有明显可行的测试路径，不要只为了走完流程而从零造一个。
3. **先写会失败的测试。** 加一个最小的、聚焦的、本来能抓住这个 bug 的测试。测试应该表达预期行为，而不是照抄当前的实现。
4. **修之前先跑新测试。** 确认它是因为预期的原因失败的。如果它通过了，或者因为无关的原因失败，就在改实现之前先改正测试或复现方式。
5. **修 bug。** 做最小的正式代码改动，满足预期行为，同时保持附近的约定不变。
6. **重新跑回归测试。** 确认测试现在通过了。

## 如果写会失败的测试不现实

改用最接近的可运行回归检查：一个有针对性的脚本、手动复现的命令、浏览器自动化、快照对比、日志断言，或者聚焦的集成检查。

宁可不加新测试，也不要加一个坏测试。坏测试是指：主要在测模拟对象；把当前实现的细节写死；依赖时间先后或无关的全局状态；为了一个小修复需要昂贵的基础设施；或者证明修复有效之后马上就会被删掉。

## 测试文件放哪

1. 项目已经有测试习惯的（比如 xxx.test.ts 放在源文件旁边、已有 tests/ 或 __tests__/），就按原来的放，不另起一套。
2. 新项目或尚无测试约定时，沿用 code-style 的模块就近原则，并遵循语言生态和测试框架要求；不另行强制建立根 tests/ 目录。确认测试工具能够发现测试。
3. 临时验证脚本仍然放在系统临时目录，跑完就删；收尾前用 git status 检查一遍，确认没留下多余文件。

## 防护规则

- 不要只为了迁就错误的实现去改测试。
- 不要削弱已有的断言，除非预期行为确实变了，而且原因清楚。
- 让回归测试聚焦在这个 bug 上。避免大范围改动测试数据，或者扩大无关的覆盖范围。
- 如果 bug 时有时无（flaky），尽可能让测试结果稳定可重复，并写明要锁定的是哪个信号。
- 如果这个 bug 暴露出一整类问题，先把聚焦的回归测试落地，再考虑给同类情况加测试。

## 最后的回复

报告证据，而不只是结果：

- 说出修复前失败的那个测试或可运行检查，以及它产生的失败。
- 说出修复后通过的那次测试运行，以及做过的其他相关验证。
- 如果没能展示“修复前失败”的证据，说明原因，并描述改用的最接近的回归检查。
