# 设计词汇

设计**深模块**：小接口后面藏大量行为，放在干净的接缝上，通过这个接口就能测。凡是设计或重组代码，都用这套语言和原则。目标是给调用方杠杆、给维护者局部性、让所有人都好测。

## 词表

严格用这些词，不要换成「组件」「服务」「API」「边界」。用词一致就是全部意义所在。

**模块（module）**：任何有接口和实现的东西。刻意不分尺度：一个函数、一个类、一个包，或者一个跨层的切片。_避免_：单元、组件、服务。

**接口（interface）**：调用方要正确使用这个模块所必须知道的一切：类型签名，还有不变量、调用顺序约束、错误情形、必需的配置、性能特征。_避免_：API、签名（太窄，只指类型层面）。

**实现（implementation）**：模块内部的代码。和**适配器**不同：一个东西可以是小适配器、大实现（Postgres 仓储），也可以是大适配器、小实现（内存假实现）。讨论接缝时说「适配器」，其他时候说「实现」。

**深度（depth）**：接口处的杠杆。调用方（或测试）每学一份接口，能用上多少行为。大量行为藏在小接口后面就是**深**；接口几乎和实现一样复杂就是**浅**。

**接缝（seam）**_（Michael Feathers）_：不改这个地方的代码也能改变行为的位置；模块接口所在的*位置*。接缝放哪是一个独立的设计决定，和接缝后面放什么分开考虑。_避免_：边界（和 DDD 的限界上下文撞词）。

**适配器（adapter）**：在接缝上满足接口的具体东西。说的是*角色*（填哪个槽），不是内容（里面有什么）。

**杠杆（leverage）**：调用方从深度得到的好处。每学一份接口能用上更多能力。一份实现回报给 N 个调用点和 M 个测试。

**局部性（locality）**：维护者从深度得到的好处。改动、bug、知识、验证都集中在一处，不散到调用方。修一次，处处都修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│       小接口        │  ← 方法少、参数简单
├─────────────────────┤
│                     │
│      深的实现       │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 很少实现（避免）：

```
┌─────────────────────────────────┐
│            大接口               │  ← 方法多、参数复杂
├─────────────────────────────────┤
│  薄实现                         │  ← 只是转手
└─────────────────────────────────┘
```

设计接口时问：

- 能不能少几个方法？
- 能不能简化参数？
- 能不能把更多复杂度藏进去？

## 原则

- **深度是接口的属性，不是实现的属性。** 深模块内部可以由小的、可 mock、可替换的部件组成，只是它们不属于接口。一个模块可以有**内部接缝**（实现私有，给自己的测试用），也有接口处的**外部接缝**。
- **删除测试。** 设想把这个模块删掉。复杂度消失了，它就是个转手；复杂度在 N 个调用方那里重新冒出来，它就是有价值的。
- **接口就是测试面。** 调用方和测试走同一个接缝。如果你想*绕过*接口去测，模块的形状多半不对。
- **一个适配器是假想的接缝，两个适配器才是真的。** 接缝两侧真有东西会变，才引入接缝。

## 为好测而设计

好接口让测试顺理成章：

1. **接收依赖，不要自己创建。**

   ```typescript
   // 好测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 好测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面积小。** 方法少，要写的测试就少；参数少，测试准备就简单。

## 关系

- 一个**模块**恰好有一个**接口**（它对调用方和测试呈现的表面）。
- **深度**是**模块**的属性，以它的**接口**来衡量。
- **接缝**是**模块**的**接口**所在之处。
- **适配器**位于**接缝**上，满足**接口**。
- **深度**给调用方带来**杠杆**，给维护者带来**局部性**。

## 不采用的说法

- **把深度当作实现行数和接口行数之比**（Ousterhout）：会奖励把实现写胖。这里用「深度即杠杆」。
- **把「接口」当成 TypeScript 的 `interface` 关键字或类的公有方法**：太窄。这里的接口包括调用方必须知道的每一条事实。
- **「边界」**：和 DDD 的限界上下文撞词。说**接缝**或**接口**。
