# 实体关系渲染器

将 `diagram_type: "erd"` 的 JSON 文件渲染为标准 Archify HTML 模板。

```bash
node archify/renderers/erd/render-erd.mjs input.erd.json output.html
```

渲染器使用内置的独立校验器，按 `archify/schemas/erd.schema.json` 校验
输入。无需安装任何依赖。

若省略 `output.html`，渲染器使用 JSON 文件中的 `meta.output`，
否则回退到当前工作目录下的 `erd.html`。

渲染完成后，运行产物检查器：

```bash
node archify/scripts/check-render-output.mjs output.html
```

## 输入

ERD JSON 文件必须设置：

```json
{
  "schema_version": 1,
  "diagram_type": "erd",
  "meta": { "title": "Order management schema" },
  "entities": [],
  "relationships": [],
  "cards": []
}
```

实体在 `label` 中携带表名，在 `attributes` 中携带其属性，并在
带状网格中占据一个 `row`/`col` 单元格。框的高度随声明的属性
数量变化，因此布局从不需要手工测量尺寸。属性的 `key` 接受
`pk`、`fk` 或 `uk`，或由它们组成的列表：关联表（junction table）的某列常常既是
主键的一部分，又是指向同一父表的外键，只声明一个角色会
掩盖另一个。每个角色绘制自己的徽标，按其图例所属色系着色；
同一角色写两次只绘制一次；键列宽度按表中最宽的一串徽标
测量 — 绝不窄于共享宽度，徽标需要时则更宽。每个 `fk`
角色 — 无论单独出现还是位于列表中 — 还必须在 `references` 中以 `"entity.attribute"`
指明其目标，并且该目标会对照已声明的实体和
属性进行检查。

关系按 `from` -> `to` 读取，并在两端用鸦脚（crow's foot）记法绘制。
鸦脚朝向其所描述基数的那个实体张开：脚趾立在该表的边上，
顶点沿连线后退一个脚长，
因此该字形不会被误读为指向表的箭头。两端都
声明各自的最大值：`fromCardinality`/`toCardinality` 取 `one` 或
`many` 且为必填，因为作者从未声明的最大值就是
图在凭空捏造的事实；`fromOptional`/`toOptional` 在顶点之外添加
可选圆圈，并把该端的最小值从一降为零。
`identifying: false` 绘制非标识性的虚线，并且由它独占虚线：
会把关系同时画成实线的 `variant` 会被
schema 拒绝，因为实线会陈述与事实相反的内容。对于每条标识性关系，
variant 仍用于选择强调色。

## 布局与路由

`layout.mode: "grid"` 按 `row`/`col` 放置每个实体。每个原始属性索引
拥有其最宽实体的宽度，每个原始行索引拥有
其最高实体的高度，因此同一带中的框无需手工测量即可对齐，空的
索引会留出一条路由通道。`pos` 可为有界的
例外覆盖单元格。

关系通过其他类型化渲染器所用的正交路由器进行路由
（`../architecture/routing.mjs`），因此适用相同的契约：共享实体上的自动端口
分散、端点侧契约、路由节奏
下限，以及通用的 Clean Flow 关卡。ERD 是调用方，而不是分叉：它
传入 `sideFor`、`maxPortSpacing`、`preferredCandidates` 和
`compositionFloors: false`，并读取无需规划的 `inferredSides` 和
`ports` 映射。每个选项在省略时都不起作用，architecture 和
lifecycle 正是借此逐字节保持其路由不变。有五点差异是此
渲染器特有的：

- 端点按水平优先解析，与其他所有非 architecture 类型一样：只要两表
  左右并列，关系就从左/右离开和进入，只有当它们共处一列时才回退到
  上/下端口。共享
  路由器的默认行为是 architecture 的主导轴推断，每当某个目标恰好在
  垂直方向上比水平方向离得更远时，它就会把一次扇入拆成两组。
- 同一侧上的自动端口最多分散 24 个单位，因为基数
  字形高 14 个单位：按共享的 14 单位分散，同一表边上的两个鸦脚
  看起来就像一团污迹。该间距是上限而非下限 — 一侧只能
  容纳 `(extent - 32) / (ends - 1)` — 因此若一张表的关系端数量超过
  其一侧所能容纳的数量，会以 `layout/marker-capacity` 失败，该诊断会指出
  表、侧、间距以及三种解决办法。
- 会共用一条走廊的关系获得确定性的泳道偏移，
  因此平行的外键绝不会落在完全相同的通道线上。
- 共用一个实体侧（外键的扇入，或扇出的
  父表）且标记样式相同的关系，会捆绑到紧贴该侧外部的单一主干上：
  一条总线，每条关系一段短分支，而不是
  一束平行泳道。主干会桥接总线上一个端口步长的未覆盖段，因此
  上述端口分散仍读作一条线。主干只是首选
  路由 — 会破坏端点契约或切到实体的分支会回退
  到普通路由族并保持不捆绑，任何作者编写的内容
  （`route`、`via`、`labelAt`）都保留各自的线。逻辑路由仍会经过
  主干，因此每道关卡、每个标签以及布局报告都能看到完整几何。
  自动补出的主干桥接还会检查无关关系及已接受的其他桥接；出现交叉、接触或
  重叠时保留分离的主干段，避免把独立关系画成同一条总线。检查按双方描边的
  半宽之和留出间隔，并计入无关关系的显式 `width`；中心线未相交但描边接触
  也会阻止桥接。这个回退不移动
  实体、显式途经点或端口，也不改变关系基数；无障碍的同簇分支仍可共享主干。
- 实体框是不透明障碍。当第三个实体位于两个
  对齐的锚点之间时，共享的障碍网格会绕开它路由，而仍无法避开无关实体的路由会以
  `clean-flow/edge-through-node` 失败，而不是从框中穿过。

渲染器还会报告 ER 特有的诊断：`from`/`to` 中的未知实体、
未知属性名和无法解析的 `references`、重复的属性
名、自引用关系、重叠的实体框，以及
文本无法容纳在声明的实体宽度内的行。

## 领域带

`tag` 命名一张表所属的功能领域；当带有该标签的
表填满一个由网格单元格组成的实心矩形时 — 其包围盒的每个单元格都容纳其中一张表 — 该领域会被绘制为一条带。单行、单列和一个填满的
矩形块都属于同一种情形（L 形或对角线则不是）；单表
领域是这种情形的最小形式。
带依据已放置的框测量，并以标签作为其标题，
正是这一点让分组后的 schema 一眼可读：读者看到的是若干块，
而不是六个同等权重的框。

成员未填满一个矩形的标签不会获得带，因为围绕它们的带
会圈进不属于该领域的单元格，并声称一种与
摆放相矛盾的分组。带是绘制领域名的唯一位置，因此
渲染器返回 `erd/domain-not-drawn`，而不是发布一张表格
齐全却无法命名其领域的图。把成员移入同一个
矩形、拆分该标签，或删除它。同一诊断还涵盖名称
可能缺失的其他情形：某个成员放在网格之外，因为带是依据
单元格测量的，而绝对坐标没有单元格；两个成员位于同一单元格，这种情况改由
网格摆放检查报告，以便作者得知必须移动的那一对；
带的留白会覆盖一张无关的表，这发生在
`layout.gapX`/`gapY` 小于留白时；以及画布
够不到的标题，这由比留白更靠近边缘的 `layout.origin` 导致。

表头只承载表标题。标题以表自身的
中心线居中，并被限制在其测量所依据的区间内 — 左侧是印记门廊（sigil porch），
右侧是留白 — 因此只要共享文本模型的步进估算成立，它就不会越过任一侧。
在可读字号下无法放入表头的标题会触发
`erd/header-text-capacity`；请加宽表或缩短
标题。除非作者修改，现有的表头和实体尺寸会被保留。作者编写的
`sublabel` 不会被绘制：它作为 `data-node-sublabel` 保留在节点上，
并保留在可访问名称中。

## 基数墨色

鸦脚、单竖线和可选圆圈以主题的
弱化文本墨色绘制，而不是共享的箭头色值：在浅色主题的箭头
颜色下，覆盖在表填充色上的字形对比度接近 2:1，看起来像一团污迹，
而弱化文本墨色在两种主题中都能达到 3:1 的非文本下限。图例
沿用相同的墨色和描边粗细，其标签比共享图例默认值
大一级、粗一级，因此图例向读者展示的正是图中绘制的
字形。

## 图例带

默认图例是生成内容的一部分，因此自动画布会
调整尺寸以容纳它：共享测量决定预留条带是否
放得下，绘制区域每次增长一条带，直到放下为止。仍与已放置的带
碰撞的路由或关系标签属于真正的容量
失败，会触发诊断而不是丢弃图例，而作者编写的
`meta.viewBox` — 一个固定的绘制区域 — 会指出其所欠缺的容量
（`legend/vertical-overflow`、`legend/label-too-wide` 或 `legend/content-overlap`，
每个都附带能解决它的修复方式）。

图例有两组，以分隔线隔开。键条目绘制与
字段行相同的徽标；关系条目绘制一段与表边相接的短路由，
带有该标记自身的字形。ERD 的种类是列键和关系端，
而不是节点种类，因此这些条目不进入查看器的计数节点视图，
否则每一项都会被标上一个错误的零。悬停或用键盘聚焦某个条目
会在 SVG 本身中高亮其匹配项：键会淡化其他字段行并
勾勒匹配的徽标；关系端会在该字形出现的每处重新着色，
并淡化不携带它的路由。静态导出保留普通
图例。

高于一屏的画布是正常的 schema，而不是缺陷。自动
画布会声明 `data-reader-fit="intrinsic-height"` 和
`data-reader-min-text="7.5"`，这是允许 Reader 把高
schema 缩窄到页面放得下为止 — 绝不低于所声明的最小值，
从而字段行保持可读，超出部分则滚动；作者编写的
`meta.viewBox` 保留作者的适配契约。字段行、其类型
以及键字形在文本本身上携带 `data-detail="context"`，因为
Reader 依据声明了层级的文本来确定图的尺寸 — 仅在行组内作为
上下文的字段，在高 schema 上会被缩小到可读下限以下。

缩窄是下限，而不是目标。内置的十一表示例在
1440x900 下、以相同的表和排版测量，是一块 1230x678 的画布，Reader
以完整的 1346px 渲染（缩放 1.09），因此其字段类型落在 11.5px。
同样的表改为分成四个水平领域时，形成一块 910x874 的画布，
Reader 将其缩窄到 777px（缩放 0.85），使同样的类型落在 9.0px。
达到读者宽度而不被缩窄的水平排列，
仍是在用文字大小换取所需的列，这就是为什么此处的测量
是这一对数据，而不是关于哪个轴才正确的规则。

## 排版

表行是读者扫视的文本，因此 ERD 的节奏比通用
图的节奏更宽松：30 单位的表头、20 单位的行、13 单位的表名、11 单位的
字段名，以及 10.5 单位的类型。类型与字段名保持相同的墨色，
因为它是数据而不是旁注：使用弱化色值时，它相对表填充色的测量值为 3.98:1，
低于 4.5:1 的文本下限，这就是它在评审中显得很淡的原因。
无法容纳文本的行会给出诊断，而不是被静默截断的
单元格，因此窄表会指出它无法显示的字段并要求更宽的框。

字段行、其类型以及键字形各自在
文本本身上携带 `data-detail="context"`，而不仅仅在行组上：查看器的 reader 依据
声明了层级的文本来确定图的尺寸，否则高 schema 会被缩小到
可读下限以下。自动画布还会声明
`data-reader-fit="intrinsic-height"`，正是它让高于一屏的 schema
以可读尺寸滚动，而不是被挤压到放得下；作者编写的
`meta.viewBox` 保留作者的适配契约。

关系标签以 9 单位、采用该关系自身的强调色设置，
遮罩也按同一系数测量，因此带标签的 schema 能让其语义文本保持在
可读下限之上。它们是图中最小的文本，并且
是语义数据：碰撞需要修复（移动标签、加宽
走廊），绝不能成为删除文字的理由。

## 阅读 schema

ERD 同时也是表目录。对于超过 8 张表或 50 个
字段的 schema，从 `meta.quality_profile: "standard"` 开始，使完整的字段
可见性保持优先；只有在分组布局真正可读之后，才提升到 `showcase`。把每个物理列都写入
`entities[].attributes`，保留其 SQL 类型，并且当 schema 没有单独的注释字段时，
把源注释以 `SQL_TYPE｜中文备注` 的形式保留在类型字符串中。
渲染器以默认的 `read` 层级显示 ERD 属性行，因此字段不
依赖悬停或聚焦。卡片只用于补充约束、
推断出的关系和领域规则；绝不要用它们来隐藏完整的表。

在分配网格单元格之前，先按功能领域对表进行分组。给同一
领域的成员相同的简洁 `tag`，并让它们处于一段连续、不交错的序列中
— 一行中相邻的列，或一列中相邻的行；带正是依据这段序列测量的。当整个 schema
必须一次性全部可见时，给每个领域单独一列：这样领域自上而下阅读，相邻领域
之间的关系从左向右延伸，画布也保持足够宽，
让 Reader 能以完整文字大小显示它。宽实体对路由器来说是一堵更高的、
需要绕过的墙，而投影后的文本最小值在 1440x900 下仍然适用，
因此优先选择紧凑的分组网格，而不是缩小或隐藏字段。
