# 交付契约

## 定稿失败与候选稿修复 <a id="failed-finalize-and-candidate-repair"></a>

`finalize` 在第一个未通过的关卡处停止。使用紧凑的 stdout 或 `evidence.summaryReceipt`；只有当摘要缺少进行连贯修复所需的证据时，才读取其完整的旁挂文件。含四项产物检查的回执只是基础校验，而不是 showcase 验收：必须要求全部九项检查、零个构图错误、零个警告。先修复 `meta.quality_profile` 和 schema 错误，再处理几何问题。一个密集的全 schema ERD 在其第一次完整字段轮次中可以保留 `standard`：要求零个结构错误、没有连线穿过节点的失败、完整的字段行以及可读的分组网格，并记录构图警告，而不是在它们上面花费无上限的时间。

对于校验失败，在重新运行命令之前，先在诊断所指出的相连邻域内编辑现有 JSON。保留所请求的语义、有意义的标签、来源证据以及固定的或已商定的拓扑。多条共享节点的路由需要一次整体的布局修复；这种情况请阅读 [Architecture layout repair](architecture-layout-repair.md)。对被阻挡的主路径要重新排布，而不是去挪动不相关的标签。当不相关几何的构图已经清晰可读时，保持其不变。只有当紧凑证据缺少所需测量值时，才在编辑前使用 `--layout-json`。Workflow v2 使用其稳定的编译器回执作为编写证据，而不是求解器内部数据。

在进行视口修复之前，保留已通过路由检查的最佳候选稿。如果该修复引入了新的路由碰撞，则恢复已测量的布局，转而处理其剩余的画布或文本约束。

编辑之后，带上 `--quality showcase` 重新运行完整的 `finalize` 命令；对于基于仓库的工作，还要带上 `--repo-root <repo-root>`。如果输出路径已有来自另一个候选稿的浏览器证据，则对新的 `finalize` 以及任何 `visual-check` 都使用一个全新的 `--out-dir <output-stem>.review-<revision>`。编辑后要省略先前的 `--candidate-sha256`，因为它绑定的是上一个候选稿。按代码、对象、阶段和证据比较诊断，绝不能仅凭错误数量下降来判断。按每个持续存在的问题（使用其代码、对象、阶段和证据）分别跟踪修复上限：新暴露的问题开始它自己的修复序列。如果某个问题在两次有针对性的修复后仍然存在，就检查已测量的几何或相关契约；在一次基于证据的重试之后，报告具体差距。

只在有针对性的诊断时使用独立的 `validate`，基于仓库的工作要传入 `--repo-root`。它的通过回执会标记 `candidateFrozen: true`；运行 `nextAction.arguments`，只替换 `<output.html>`，不要编辑、重新校验或重新读取候选稿。之后出现的环境或证据失败，针对这些已冻结的字节重试。有测量依据的编辑理由会产生一个新的候选稿，此时需要不带旧哈希运行完整的 `finalize`。

## 校验与交付 <a id="validate-and-deliver"></a>

`render` 和直接的渲染器入口会把已分类的编写失败以可读诊断的形式打印到 stderr，并以 1 退出。输入读取/JSON 解析失败使用 `input/read` 或 `input/json-parse`；输出文件系统失败使用 `output/write` 并标明输出路径。schema 和布局失败保留其现有的规则码。需要机器回执时，使用所公布的 `validate --json` 或 `deliver --json` 接口；`render` 没有 `--json` 参数。意外的实现失败在人类可读模式下保留调试信息，在机器回执中仍为 `internal/unclassified`。

每个已交付的输出都有两个产物专属的元数据路径。当输出主名过长、无法用于这些派生文件名时，Archify 会将其缩短并附加一个稳定的哈希：

- `<output-stem>.delivery.json` 记录最近一次已完成的尝试。
- `<output-stem>.delivery-pending.json` 是进行中尝试的恢复日志。

对于一个字面上已经匹配 Archify 保留的有界名称标记的产物主名，当编码后的旁挂文件不存在时，命名空间引入之前的原始溯源旁挂文件仍作为读取回退。命名空间引入之前的原始待处理日志是一个独立的失败即关闭屏障：即使同时存在编码后的待处理日志，它也会阻止检查和重新交付，且两个日志都不会被静默替换。

一个目录级的 `.archify-delivery-lock.json` 会串行化所有解析到同一物理输出目录的交付。这刻意防止大小写、Unicode 规范化、Windows 短文件名和符号链接别名为同一文件系统位置创建相互独立的所有者。代价是同一目录中不同产物名的交付也会串行运行；溯源文件和待处理日志仍是产物专属的。

为保证迁移安全，Archify 还会检测并保留所请求产物旁边的旧版 `<output-stem>.delivery-lock.json`。已存在的旧版条目是一个失败即关闭的恢复屏障。当一次新交付持有目录互斥锁时，它还会为所请求的拼写以及已有产物的物理目标拼写持有临时的旧格式围栏。它先获取目录锁，再在写入日志或产物之前获取所有必需的兼容围栏，并在释放时先移除目录锁、再移除这些围栏。这会阻止使用任一已知拼写的旧版 Archify 二进制进入交付。若某个旧版围栏的原始 HEAD 时代文件名超出主机的路径组件长度限制，则省略该围栏，因为旧二进制在该主机上同样无法创建那个锁或交付那个产物。

`deliver` 在创建或替换恢复日志之前，通过独占的 `open(..., "wx")` 获取锁。独占创建成功会产生一个绑定到该次尝试的内部不透明所有权凭据。日志创建、失败溯源记录、成对提交、回滚、日志定稿和锁释放，各自都会在将要修改共享状态的操作内部校验当前凭据。被拒绝的竞争者不会创建日志，也不会写入失败溯源。

已存在的目录锁或旧版锁不做自动恢复处理：

| 观察到的锁状态 | `deliver` 必须给出的结果 |
| --- | --- |
| 不存在目录条目 | 尝试独占创建；只有创建成功才授予所有权。 |
| 有效的 schema-v1 锁，其 PID 正在运行，或无法确定其已死亡 | 以 `delivery/concurrent-attempt` 退出 1；保留每一个共享路径。 |
| 有效的 schema-v1 锁，已知其 PID 已退出 | 以 `delivery/lock-stale` 退出 1；原样保留锁、产物、日志和当前溯源。 |
| 不可读、格式错误、符号链接、悬空符号链接、目录或其他非常规文件的锁条目 | 以 `delivery/lock-invalid` 退出 1；保留该条目及其他所有共享路径。 |
| 已获取的凭据不再与当前锁或日志匹配 | 以 `delivery/ownership-lost` 退出 1；停止所有共享路径修改。 |
| 匹配的所有者无法移除其锁 | 以 `delivery/lock-release` 退出 1；保留该锁。 |

`delivery/lock-stale` 诊断会给出输出和锁的绝对路径，以及原始 PID 和回执 ID。恢复刻意设计为显式且串行：停止针对该物理输出目录的所有交付尝试，确认没有活动的交付持有它、且所报告的陈旧条目未被替换，只移除所报告的锁，然后重新运行 `deliver`。不要在陈旧锁恢复过程中移除产物、当前溯源或待处理日志。

锁协议面向本地文件系统上的 Node.js 18 或更高版本，以及相互配合的 Archify 进程。PID、回执和文件身份比较是防御性检查，而不是原子的比较并交换。兼容围栏覆盖所请求的拼写和已有的物理目标拼写；它们无法枚举任意硬链接名或此前未知的文件系统别名，因此通过这类别名进行的混合版本交付不在范围内。本契约不声称在 NFS、SMB 或其他网络文件系统上具有分布式锁的正确性，也无法阻止无视该协议的外部进程替换共享路径。

每个不覆盖既有文件（no-clobber）的 HTML 发布器（`render`、`deliver`、`compare` 和 `preview`）都会在暂存之前捕获所请求的目录条目、规范写入槽、物理父目录，以及已有目标的类型、设备/inode 身份和模式，然后在替换前一刻重新校验该快照。已有的写入目标必须是恰好只有一个硬链接名的常规文件。拥有多个硬链接名的目标会以 `output/target-hardlinked` 失败即关闭：替换所请求的名称无法把未知的兄弟名称作为同一次发布一并更新。硬链接在读取身份以及输入/别名冲突检查中仍受支持；只有作为写入目标时才不受支持。指向单链接常规文件的符号链接仍受支持：发布会保留该符号链接条目，并对其解析后的目标应用相同协议。目录、FIFO、套接字、设备、模式变化、新的占用者以及身份不确定的情况都会在替换前失败。

发布是不覆盖且可恢复的，而不是对已有目标的崩溃原子替换。为避免覆盖在最后一次身份检查之后出现的占用者，Archify 先把已绑定的旧文件保留在私有恢复备份中，通过与身份绑定的隔离移除公开名称，然后用独占硬链接创建新的公开名称。被捕获的失败会在公开槽位和恢复绑定仍然允许时回滚。若进程在这些命名空间操作之间被中断，则可能导致公开路径缺失，而已校验的旧字节仍留在相邻的私有恢复备份中。单产物发布会在私有的 `.archify-remove-*/publication-recovery-v1.json`（位于 `previous` 旁边）中记录原始槽位/别名身份以及备份的 inode、模式、SHA-256 和字节数。要让某次被中断的特定发布重新可见，请停止并发写入者并运行：

```bash
node bin/recover-output.mjs /absolute/path/to/.archify-remove-<id> --json
```

这是显式恢复，不是目录扫描器。在创建链接之前，该辅助工具会检查父目录或别名是否改变、记录或备份是否被篡改/硬链接、摘要或 inode 是否不匹配，以及是否已存在任何公开目标。它只通过不覆盖的硬链接进行恢复，因此新的占用者会被保留而不是被覆盖；它绝不递归移除未知条目。已完成的恢复是幂等的。该记录是需要独立核实的证据，而不是恢复任意私有字节的授权：辅助工具只接受来自原始物理目标父目录中、所记录的生成子目录且目录身份相同的记录。请指明被中断进程所报告的确切目录，并手动检查不确定的记录。不配合的进程仍可能在这些检查之后、Node.js `linkSync` 之前交换路径名；Node 没有提供与描述符绑定的链接操作。此时链接后的身份校验会失败即关闭并保留恢复证据，而不是声称已恢复或删除不确定的名称。如果恢复本身在链接之后被中断，旧的公开字节和私有备份可能同时留存；之后的恢复运行会保留公开目标，需要操作者显式处理。在支持目录同步的平台上，记录会在旧公开名称退役之前被 fsync，经过测试的保证是进程被杀后可恢复；这并不声称能抵御断电、存储控制器、NFS 或 SMB 层面的持久性问题。成对流程会把其备份保留在私有事务暂存区中。对于 `deliver`，待处理日志和锁会让严格检查器保持失败即关闭。可移植的 Node.js 文件系统 API 没有一种路径名比较并交换操作，能够既原子地替换已有名称、又拒绝覆盖迟到的占用者：`rename` 只能通过覆盖该占用者来消除可见性空窗。

所有权确立之后，`deliver` 在渲染前创建日志，并在可恢复的 HTML/旁挂文件成对提交期间一直保留它。只有在该提交完成后才会移除日志。因此，校验、渲染或成对提交失败，或进程中断，都可能留下日志。日志是一道安全屏障：只要日志或锁路径上存在任何目录条目（包括不可读文件、符号链接或悬空符号链接），`check`、`browser-check` 和 `visual-check` 都会失败即关闭。针对同一物理输出目录的交付要串行运行；一次尝试必须完成或被恢复后，另一次才能开始。

成功的旁挂文件包含 `schemaVersion: 1`、`status: "current"`、`command: "deliver"`、唯一的 `receiptId`、图的 `type`、绝对路径的 `input`、与被检查产物相匹配的绝对路径 `output`，以及规格/产物的 SHA-256 和字节数。检查器将缺失、格式错误、不受支持或不一致的字段视为无效。它们还会拒绝作为符号链接的旁挂文件，包括悬空的符号链接。检查器会把溯源绑定到它实际检查的产物字节，并在报告成功前再次校验该绑定；并发的字节变化会导致失败。溯源目录条目本身必须是单链接的常规文件：当它还有另一个硬链接时，`deliver` 和严格检查会以 `delivery/provenance-hardlink-unsupported` 失败即关闭，不会去扫描或猜测兄弟名称。

如果当前已校验的所有者在旧 HTML 已存在之后失败，Archify 会写入一个新的 `status: "failed"` 旁挂文件，并保留日志直到恢复完成。旧 HTML 不可读并不妨碍写入该标记；其产物哈希和字节数可能缺失。如果旁挂文件被锁定或因其他原因不可写，Archify 会保留先前的旁挂文件而不是删除证据，而日志会阻止检查器信任它。被拒绝的并发、陈旧或无效锁尝试不会写入失败溯源。如果所有权丢失，Archify 报告 `delivery/ownership-lost`，不会覆盖或移除后继者的产物、溯源、日志或锁，也不会声称已记录失败溯源；失败回执可能报告 `provenance: "unrecorded"`。如果所有元数据路径都不可用，同样适用该未记录状态；没有任何工具能跨进程保留这一事实。请恢复元数据路径的访问并完成一次成功的 `deliver`，然后才能信任该输出。

没有旁挂文件、日志或锁的产物仍受支持，以保持向后兼容，并供更底层的 `render` 命令使用。它们的检查器回执报告 `provenance: "unknown"`；当工作流要求产物必须经过成功交付时，使用 `--require-provenance` 将该状态变为非零失败：

```bash
node bin/archify.mjs check <output.html> --require-provenance
node bin/archify.mjs browser-check <output.html> --json --require-provenance
```

## 输出路径契约 <a id="output-path-contracts"></a>

Archify 有意把持久的编写路径与命令行路径分开：

- 必填的编写字段 `meta.output` 是可移植的 POSIX 相对路径，例如 `reports/diagram.html`。它使用 `/`，以非空的 `.html` 文件名结尾，且不能包含绝对或驱动器相对前缀、URI、反斜杠、空段或点段、控制字符、未配对的 UTF-16 代理项、Windows 备用数据流分隔符或非法文件名字符、末尾的点或空格、DOS 设备名，也不能包含超过 255 字节 UTF-8 或 255 个 UTF-16 码元任一限制的路径组件。它从当前工作目录解析，并且在跟随符号链接之后，必须在物理上仍位于该目录内、且目标为 `.html`。持久的输出/归档配置还会保守地拒绝 Windows 8.3 短文件名形态，例如 `PROGRA~1`；描述性的仓库/Git POSIX 路径使用单独的配置，不受此限。
- 显式的 CLI 输出参数使用当前主机的原生语法。它们可以是相对或绝对路径，使用原生分隔符，并可解析到当前工作目录之外。在 Windows 上，支持普通的驱动器绝对路径、UNC 路径和相对路径（包括普通的 `.` 和 `..` 导航）。当 Archify 能证明其物理身份时，接受系统解析出的现有文件或目录的 8.3 拼写；这种原生别名支持并不放宽持久输出/归档配置对 8.3 形态名称的拒绝。扩展长度路径仅限于不含点段、只用反斜杠的原始 `\\?\C:\...` 和 `\\?\UNC\server\share\...` 形式；设备命名空间、格式错误的根、`C:file.html` 这样的驱动器相对路径、`\file.html` 这样的当前驱动器根路径、备用数据流、保留设备名、非法或末尾文件名字符以及超长组件都会失败即关闭。POSIX CLI 路径保留 POSIX 文件名规则，而不继承 Windows 的拼写限制。每个主机都会拒绝 NUL、未配对代理项以及超出其支持上限的组件。

这两种契约不可互换：显式的 CLI 输出不会掩盖无效的持久 `meta.output`（包括缺失该值），而且即使 `validate` 不向该路径发布，它也会检查编写的输出。workflow v1 到 v2 的迁移可以通过 `migrate workflow old.json new.json --to-schema 2 --output
reports/diagram.html` 显式接收一个可移植的持久替换值；该值只会写入其单独的、已校验的 v2 目标。这一迁移候选稿例外不会修复源文件，也不会绕过任何非输出类的 schema 或编译器错误。对于其他所有修复，请向 `meta.output` 添加一个可移植的 POSIX 相对 `.html` 路径；除此之外不需要更改 schema 版本。

对完整的首个候选稿以及每次修复编辑之后，直接运行 `finalize`。它内嵌的校验会在交付前检查候选稿；只在有针对性的诊断时使用独立的 `validate`。编辑后，省略任何先前的 `--candidate-sha256`，它绑定的是上一个候选稿。CLI 的 HTML 输出路径必须以 `.html` 结尾，包括在符号链接解析之后。比较回执路径必须以 `.json` 结尾。类型不匹配会在写入前以 `output/cli-extension` 或 `output/cli-resolved-extension` 失败。这些检查用于防止意外覆盖其他类型的文件；它们不会把显式的 CLI 目录沙箱化，也不会阻止替换预期类型的已有产物。

只有在候选稿冻结之后，才使用最终的已校验交付：

```bash
node bin/archify.mjs deliver <type> <candidate.json> <output.html> --quality showcase --json
```

Deliver 只读取一次规格，把这些确切字节写入同目录下的私有候选稿快照，渲染该快照，运行完整的产物检查器，并且只有在所有产物检查通过后才替换目标。JSON 回执包含 `specification` 和 `artifact` 两者的 SHA-256 和字节数。

对于普通的代理交接路径，优先使用定稿器：

```bash
node bin/archify.mjs finalize <type> <candidate.json> <output.html> --quality showcase --json
```

`finalize` 调用一次已校验的 `deliver`，复用其内嵌的 showcase 校验结果，然后运行严格的 `check --require-provenance` 和 `browser-check --require-provenance`。它在第一个失败或跳过的阶段停止，并保留该阶段的完整回执。它的 stdout 是一个紧凑的 JSON 对象，包含关卡状态、有上限的可操作诊断、产物身份和证据路径。同一个紧凑对象会被原子地写入 `<output-stem>.finalize-summary.json`；常规的失败修复请使用该文件。当诊断被截断时，`diagnosticSummary.omittedByCode` 按诊断代码统计未显示的条目，而完整回执中仍保留它们的完整对象和修复证据。完整的阶段回执和耗时保留在 `<output-stem>.finalize.json` 中以供审计。使用 `--out-dir` 时，这两个文件都写到该目录（除非显式的 `--receipt` 覆盖了定稿回执路径；产物 HTML 仍位于所请求的输出路径）；`--receipt <path.json>` 覆盖完整回执路径，并派生出一个不同的 `<path>-summary.json`。只有当紧凑摘要被截断、且其显示的对象和证据无法确定一个连贯的局部修复时，或者明确要求完整审计证据时，才读取完整回执。紧凑回执报告 `visualReview: "not-requested"`；自动化关卡不会生成图像，也不需要感知评审者。紧凑的 `visualReviewRecommendation` 保留了严格检查中为正值的交叉和路由绕行指标，以便作者无需读取完整回执即可应用下文的评审升级。建议不会改变机器退出码，也不声称评审已经发生。其 `affectedRoutes` 标识交叉对和绕行（每类最多八个，并带有截断标志）；完整的严格检查 `composition.routeReview` 保留所有受影响的关系。使用这些 ID 在捕获的默认视口中追踪路由。绕行可能包含 `directCorridorBlockers`，标识位于对齐端点之间的节点。这些是几何上的评审线索，不是新的校验失败，也不是推断出的主路径语义。对于被阻挡的主路径或多条纠缠的路由，请遵循 [Architecture layout repair](architecture-layout-repair.md)，先重新排布相连的场景，再调整单个边或标签。保留每一个语义事实；只有当周围构图已被接受时，才保留不相关的位置。

对于一个经过测量、带有大片未使用前导区域的自动 Architecture，紧凑回执可能包含 `layoutReviewRecommendation`。其 `composition.leadingSpace` 证据计入了节点、边界标题、路由和标签。检查该空白是否有意为之；若不是，在保留含义和用户固定几何的前提下重新定位相连的场景，然后再次定稿。该建议不改变任何关卡或退出状态，也不需要截图。固定画布或测量不确定的情况不会收到该建议。

通过的定稿器回执足以作为全部四个关卡的证据。仅仅点名这些关卡或要求每个关卡都通过，并不需要重放它们的独立命令。只有当请求明确要求分别执行，或有针对性的失败诊断需要时，才重放单个命令。

各个单独命令仍然是权威的，并保持向后兼容。在有针对性的诊断、恢复，或只需要一个关卡时，直接使用它们。定稿失败不会放宽任何关卡，也不会把保留下来的旧产物变成当前的成功交付。

`finalize` 只有在交付和严格检查通过之后，才会发现并启动私有 Chrome。因此，输入、仓库证据、交付或产物检查失败都不会启动浏览器。它只在当前溯源校验通过后才加载产物。浏览器关卡保留每一项视口、主题和稳定性检查；浏览器在完成时或浏览器阶段失败时关闭。其完整阶段回执记录 `execution: "in-process"` 以及用于重放的等效独立 `command`。Chrome 启动不再与之前的阶段重叠，因此成功的运行可能会稍慢一些。这避免了在无效候选稿上进行不必要的启动；它并不能解决主机沙箱对 Chrome 启动的限制，也不会放宽浏览器关卡。

成对提交是可恢复的，并不声称两个文件系统路径会原子地改变或能在断电后持久。日志定稿是该提交的一部分：在校验或移除日志时被捕获的失败，会在可能且所有权仍为当前时回滚被替换的文件。如果所有权丢失，旧的尝试会立即停止重命名、回滚、定稿日志、记录失败溯源或清理共享路径。任何私有暂存或可恢复备份都会保留，并由失败诊断标明。如果因其他原因恢复失败，失败回执同样会标明保留的备份以供恢复。进程中断可能留下日志、备份或私有暂存；此时检查器会失败即关闭。请先按所报告的恢复证据处理，再对同一输出串行地重新运行 `deliver`。失败的尝试以非零状态退出，且绝不调用打开器；它也绝不授权收集视觉证据。

如果独占创建成功但锁初始化失败，Archify 只有在其凭据仍标识那个确切条目时，才可能记录失败溯源并移除不完整的锁。替换后的条目会被保留。文件系统和清理错误与活动的并发交付分开报告。活动的、陈旧的、无法识别的或其他被保留的锁，都会独立地阻止检查器接受先前的产物。重试前请先修复所报告的文件系统错误；如果锁路径中包含无关数据，请改用另一个物理输出目录。

锁释放是交付完成的一部分。如果产物/溯源对已提交、日志已定稿，但匹配的锁无法移除，`deliver` 会以 `delivery/lock-release` 退出 1，保留该锁，不打印成功回执，也不调用打开器。被保留的锁会让严格检查器保持失败即关闭。只有在成对提交、日志定稿和锁释放全部成功之后，`deliver` 才可以以零退出、打印其成功回执或运行 `--open`。

在 `deliver` 以零退出之后运行严格的 `check`。只有在该严格检查以零退出之后，才运行 `browser-check` 或可选的 `visual-check`。失败标记、恢复日志或交付锁会让每个检查器在接受被保留的 HTML 之前就失败；请报告诊断，并在收集新的浏览器证据之前完成一次成功的恢复交付。

静态 `check` 对受检的关系和结构框使用同一套 SVG 路径分析。它支持 `M/L/H/V/Q/Z`、它们的小写相对形式、重复参数和有限数值。每个 `M` 开始一个独立的子路径；`Z` 只闭合当前子路径。不同子路径之间绝不会生成图中不存在的连接线段。被非共线 `Q` 隔开的直线段在路由分析中也保持分离；曲线采样点不会在直线路由预算或节奏检查中变成微线段。线段长度和伸长按每个连续片段测量，而实际转弯数按关系汇总。超出预算的关系只计一次，内部片段边界不享有为语义端点保留的短共享主干例外。

这并不承诺完整支持 SVG 命令：`A/C/S/T` 会产生 `artifact/svg-path-unsupported`；缺少参数、非法数值及其他语法错误会产生 `artifact/svg-path-malformed`。检查器会以非零状态退出，而不是跳过坏路径或无限等待。路径失败会追加一项 `svg_path_data` 检查；普通的有效产物仍保留现有的九项检查。诊断携带受检的 `pathIndex`、`role`、可用的关系/框 `id`、解析的 `tokenOffset`、可用的 `command` 和 `reason`，以便定位并修复生成路径的来源。`pathIndex` 从 1 开始；`tokenOffset` 是数字字符引用解码后 `d` 中从 0 开始的 UTF-16 偏移。注释、CDATA 和属性文本中看似标签的内容会被忽略。静态路径检查通过并不代表浏览器或感知视觉验收通过。

交付接口提供四种相互独立的声明：

1. `deliver` 证明确定性的产物检查与字节身份。
2. `browser-check` 从该确切产物收集必需的自动化浏览器证据，不截取图像。
3. `visual-check` 可选地添加与产物绑定的截图和一张联系表（contact sheet）。
4. 感知视觉评审记录人类或具备图像能力的评审者的判断。

## 恢复失败的比较 <a id="recovering-a-failed-comparison"></a>

`compare` 将一个 HTML 产物及其 JSON 回执作为一对提交。如果该提交失败，它会尝试恢复先前的文件。完整回滚会像平常一样移除临时目录。

如果某个先前文件无法恢复，compare 会以 `delta/commit-rollback-failed` 非零退出，并保留恢复目录。在 JSON 失败回执中，`diagnostics[].evidence.recoveryDirectory` 标明该目录，`recoveryFiles` 列出恢复失败的文件的 `{ backup, target }` 路径。人类可读的诊断也会打印这些恢复路径。

重试之前，先解决文件系统错误，检查当前目标，并把列出的每个备份恢复到其对应的目标。保留恢复目录，直到两个先前文件都已恢复并校验；该目录还可能包含被拒绝的候选稿文件，绝不能将它们误认为备份。成功的比较以及提交前发生的失败会保留其常规清理。

## 自动化浏览器证据 <a id="automated-browser-evidence"></a>

`finalize` 针对确切的受信任 HTML 运行必需的浏览器关卡，不会重新渲染或修改它。用于有针对性诊断时，等效的独立命令是：

```bash
node bin/archify.mjs browser-check <output.html> --json --require-provenance
```

这个零依赖命令通过 DevTools 管道使用 Chrome/Chromium（或 Microsoft Edge）。设置了 `ARCHIFY_CHROME` 时它具有权威性，即使路径无效也是如此：Archify 不会静默回退到其他浏览器。Windows 上的自动发现会先检查每个 Chrome/Chromium 安装位置和 PATH 命令，然后检查 `%ProgramFiles(x86)%`、`%ProgramFiles%` 和 `%LocalAppData%` 下的 Edge，最后是 PATH 上的 `msedge`。在 macOS 和 Linux 上，发现过程同样先检查 Chrome/Chromium，然后是 Edge 应用程序包（macOS）以及 PATH 上的 `microsoft-edge`/`microsoft-edge-stable`。它在 1440×900、1600×1000、1920×1080 和 2048×1320 下测量浅色主题的容纳情况，并在全部四个视口验证所请求的浅色主题、在两个端点视口验证深色主题，以及 READ/Still 运行时状态。所请求的主题若解析为不同的主题，会带着测量证据失败。它创建一个 `<output-stem>.browser-check.json` 回执，不生成截图或联系表。传入 `--out-dir <dir>` 可把回执放到单独的证据目录。回执绑定产物的 SHA-256 和字节数，标明 `evidenceKind: "automated-browser"`，并报告 `visualReview: "not-requested"`。

水平溢出一律失败。正常的文档级垂直滚动只有在渲染器声明了契约且文本测量可读时才被接受。自动画布声明 `data-reader-fit="intrinsic-height"`（高度适配）或 `data-reader-fit="width-first"`（Sequence 和 Waterfall 的阅读宽度）；它们的自适应 Reader 必须达到其可读宽度并暴露 `data-reader-overflow="authored"`。带有显式 `meta.viewBox` 的 Architecture 则声明 `data-diagram-type="architecture"` 和 `data-reader-fit="authored-height"`：其 SVG 坐标、宽高比和现有的 Reader 宽度行为保持不变。其完整 SVG 必须留在图面板之内，不得有内部滚动或裁剪，并且文档必须允许垂直滚动。回执记录 `verticalScrollAccepted: true` 和 `overflowDisposition: "readable-vertical-scroll"`。缺失或未知的声明、其他模式下的显式 viewBox、不可读文本、水平溢出、裁剪以及与查看器外框（chrome）的碰撞仍然是失败。不要添加内部的图滚动容器，也不要隐藏溢出。

交接中的 `browser_evidence` 只记录该自动化命令的结果：

- `passed` 对应退出码 0 且回执 `status: "pass"`，前提是每一项必需测量都已完成并通过。
- `failed` 对应退出码 1 且回执 `status: "fail"`，适用于检查发现缺陷、命令失败，或运行时错误导致证据不完整的情况。
- `skipped` 只对应退出码 2 且回执 `status: "skipped"`，适用于没有可用的受支持浏览器、检查未运行的情况。

运行时失败会留下不完整的证据，绝不能被归一化为 `skipped`。它们不会使已经成功的确定性交付失效。在可行时，于具备浏览器能力的执行环境中重试环境类失败。除非该失败在具备能力的环境中通过该接缝复现，否则保持打包的传输层不变。

在 Windows 上，Chrome/Edge 的启动重启可能在任何响应到达之前丢失继承的 DevTools 管道。Archify 只从浏览器子进程的环境中移除单独存在的 `__COMPAT_LAYER=DetectorsAppHealth`（名称和值不区分大小写）；父进程环境、未知层、组合层以及与权限相关的兼容性设置保持不变。这针对的是已报告的非提权 Git Bash 应用健康（app-health）情况，而不是所有 AppCompat 模式。提权 shell 下的重启仍不受支持：请从正常打开的非提权 PowerShell 中重新运行，不要在提权或兼容模式的父进程中运行。Archify 不会以抑制浏览器降权或禁用沙箱作为重启的变通方案。零响应的启动诊断会建议这一补救措施，但不声称每次管道失败都是由提权或 AppCompat 引起的。

溯源失败会在浏览器检查之前退出，并持久化一个绑定到所尝试产物的失败 browser-check 回执。如果失败回执无法写入，诊断会指明这份不完整的证据。

两个浏览器命令都检查确切的已交付 HTML，不会修改或重新渲染它。

## Sequence 宽度评审 <a id="sequence-width-review"></a>

通过的 `finalize` 可能报告 `layoutReviewRecommendation.action: "inspect-sequence-width"`。其 `evidence` 在计入消息标签、注释和分段标题之后，测量固定参与者列右侧未使用的空间。该建议不会增加警告、失败、截图要求或自动几何更改。

通过的 `validate --json`、`deliver` 或 `finalize` 回执可能带有 `severity: "warning"` 的 `diagnostics[]` 条目，用于查看器的语言区域回退（`i18n/*`）。它们不会使任何关卡失败。当产物需要完全本地化时，根据其 `evidence` 修复所列出的键，并重新运行 `finalize`。

省略 `meta.column_fit` 的 Sequence 画布使用 `spread`，无论是否提供了 `meta.viewBox`。编写的 viewBox 仍具有权威性；参与者容量不可行时会直接失败，而不会静默地将其放大。显式的 `meta.column_fit: "fixed"` 保留历史上的固定列。对于固定列宽度建议仍然存在的候选稿，首先检查该固定几何是否有意为之。只有当该几何的更改获得授权时，才保存候选稿，只把 `meta.column_fit` 设为 `"spread"`，并带上 `--out-dir <folder>/width-review` 重新运行一次完整的 `finalize`。保持参与者顺序、消息及其 y 位置、标签、注释、来源和画布尺寸不变。如果这次尝试失败，恢复候选稿并带上 `--out-dir <folder>/width-restore` 对其定稿；报告剩余的布局建议，而不是继续迭代。当更改未获授权时，保留有意的固定几何并披露该建议。若要为省略了 fit 的旧输入保留历史上的固定坐标，请显式设置 `meta.column_fit: "fixed"`。此评审针对的是水平构图；通过的回执仍不声称获得了感知认可。

## 可选的截图证据 <a id="optional-capture-evidence"></a>

对于被请求或升级的感知评审，`visual-check` 保持向后兼容：

```bash
node bin/archify.mjs visual-check <output.html> --summary --require-provenance
```

`--summary` 返回紧凑 JSON，包含全部诊断以及完整回执、联系表和每张截图的绝对路径。对于选定的视觉评审，检查相关的截图；截图成功并不是感知认可。`--json` 为现有使用方保留完整回执输出。两种模式运行相同的检查并保持相同的退出状态。如果发布后清理失败，摘要会保留最终的失败诊断和 `publication` 恢复详情；所链接的回执记录的是先前已提交的证据。

它执行相同的自动化浏览器测量，在 1440×900 和 2048×1320 下截取浅色/深色截图，并写入四个视口 PNG 旁挂文件、一个使用相对路径的 HTML 联系表和一个 JSON 回执。`--out-dir <dir>` 会把这些旁挂文件一起移动。在浏览器中打开 HTML 联系表，或用图像阅读器检查视口 PNG。它的回执报告 `visualReview: "pending"`，因为截图本身不构成感知判断。截图和溯源失败遵循下文的所有权规则。

回执、联系表和四张 PNG 构成一个归属明确的证据集。截图之前，`visual-check` 会冻结每个被请求的目录条目、其规范写入槽和物理父目录，以及目标的缺失/文件状态、类型、设备/inode 身份和模式。被硬链接的证据目标不是安全的写入目标。所有候选文件都在物理证据目录下的一个随机私有暂存目录中独占创建；回执最后发布。每个暂存候选文件在发布前必须恰好只有一个硬链接名。不覆盖的发布链接会暂时让暂存名和最终名的链接数为二；解除已校验暂存名的链接后，最终条目的链接数必须为一。意外的外部硬链接会失败即关闭，且其别名绝不会被移除。

Chrome 在私有的本地临时目录中检查被截图产物的一份经过身份和内容校验的副本，因此浏览器的文件加载不依赖 UNC 或长路径支持。六个发布候选文件仍保留在证据卷上。两个临时目录都会被清理，但不会递归删除未知内容；保留下来的条目会附带其恢复位置。

在提交任何内容之前的一刻，`visual-check` 会重新解析并校验完整的六路径集合。缺失路径上出现占用者、已有路径被替换、符号链接或悬空链接被重定向、父目录拓扑变化、硬链接或身份不确定，都会以 `viewer/evidence-path-conflict` 失败即关闭。占用者以及其他所有最终证据路径都保持不动。清理只会在重新检查其捕获的身份之后，移除本次运行暂存或发布的条目；已改变或未知的条目会被保留。

只有当一个常规的 `visual-check` 回执证明其对同一产物和证据目录的所有权，且其确切的旁挂清单与每个已有联系表或 PNG 的字节数和 SHA-256 摘要都匹配时，已有的视觉证据集才可被替换。缺失、格式错误、未知、不匹配或不完整的所有权记录绝不授权删除。失败和跳过的运行只有在该所有权证明成功时，才会作为同一个已校验事务的一部分让先前的截图/联系表退役；否则它们会保留所有未知证据并报告 `viewer/evidence-path-conflict`。

当 Chrome 不可用或溯源在浏览器检查之前失败时，此规则同样适用：这两条路径都不得盲目删除看似陈旧的证据。已校验且归属明确的证据集可以在发布跳过或失败回执之前被可恢复地退役；不归属本次的证据保持完好。这些结果不会使已经成功的确定性交付失效，也不会把感知视觉评审变为通过或失败。在可行时，于具备浏览器能力的执行环境中通过受支持的命令重试环境类失败。除非该失败在具备能力的环境中通过该接缝复现，否则保持打包的传输层不变。

`browser-check` 对其单个 JSON 回执应用相同的私有快照、身份、所有权和不覆盖规则。它的命名空间与 `visual-check` 分开，因此仅浏览器的重新运行无法移除截图证据。

## 已有输出路径上的新候选稿 <a id="a-new-candidate-at-an-existing-output-path"></a>

浏览器证据属于确切的产物字节。编辑一个其先前 HTML 已有浏览器证据的候选稿之后，在运行下一次 `finalize` 之前选择一个全新的证据目录；这样可以保留旧的回执和截图，避免一次本可避免的所有权冲突重试。`--out-dir` 会重新安置新的 browser-check 回执，默认还包括定稿回执和摘要。显式的 `--receipt` 会覆盖定稿回执路径；其摘要跟随该路径。成功的交付仍会重写所请求的 HTML 及其同级的 `*.delivery.json`。先前的浏览器或视觉证据仍绑定到其原始产物字节，绝不能被当作已更改 HTML 的证据：

```bash
node bin/archify.mjs finalize architecture candidate.json diagram.html --quality showcase --repo-root <root> --out-dir diagram.review-2 --json
node bin/archify.mjs visual-check diagram.html --out-dir diagram.review-2 --summary --require-provenance
```

证据目录不是 HTML 的归档。仅把 HTML 复制到那里并不会重新绑定回执路径或溯源。如果需要历史快照，请在覆盖之前分别保存候选稿和产物；不要假设复制过去的回执能够校验一个被搬移的产物。

保持所请求的 HTML 路径稳定。每个已更改的候选稿使用一个新的修订目录，对未更改字节的重试则沿用同一目录。对于没有仓库证据的图，省略 `--repo-root`。让命令自己创建其输出目录。先前未产生 HTML 或浏览器证据的校验失败不需要新目录。绝不要为了让重试通过而移除未知证据。

## 可选的打开 <a id="optional-opening"></a>

只有当用户想要立即进行本地预览时，才添加 `--open`。它在已校验的成对提交完成、恢复日志已移除且交付锁已成功释放之后运行。它使用一个参数数组形式的操作系统打开器，在 macOS 和 Linux 上限时五秒，在 Windows 上为 PowerShell 启动限时十五秒。回执记录 `open.status`；失败或不可用的启动尝试还包含归一化的 `open.failure` 详情。在 CI、无人值守代理和非交互环境中保持关闭。打开失败或不受支持不会使交付失效；其状态只证明本地打开器调用是否成功。

## 最后有效版本实时预览 <a id="last-good-live-preview"></a>

仅用于活跃的桌面编写循环：

```bash
node bin/archify.mjs preview <type> <input>.json <output>.html --quality showcase
```

Preview 在回环地址上监视一个显式指定的输入，将每个稳定摘要绑定到一个私有快照，并且只有在现有的已校验交付流水线通过后才前进。无效、写了一半、被删除或被取代的输入会让上一个已校验修订继续留在屏幕上和磁盘上。相同的字节不会重新构建或重新加载。

预览运行时随零依赖的 Skill ZIP 一起分发，必须在没有 `node_modules` 的情况下工作。

绝不要默认启动它。不要将它用于 CI、无人值守代理、远程分享或移动端使用。`--no-open` 只用于将要自行打开所打印本地 URL 的用户或循环测试。交接前用 Ctrl-C 停止它。第一次 Ctrl-C 会排空活动的交付而不发布它；第二次 Ctrl-C 会强制关闭两个交付进程和 HTTP 连接，包括未完成的请求。关闭会保留最后一个已校验的产物，只移除所有权可以被校验的暂存文件。如果交付在其回执到达 Preview 之前被中断，未确认的文件和恢复材料可能留在私有暂存目录中；关闭不会递归删除未知内容。服务器状态、端口、源路径、诊断、错误文本和重新加载令牌绝不能进入生成的产物或任何导出。

## 感知评审 <a id="perceptual-review"></a>

自动化路径以确定性的浏览器关卡结束，并报告 `visual_review: not_requested`。普通生成不需要截图或读图步骤，包括新编写或重新定位的 Architecture。感知评审是可选的；在有明确请求或具体的视觉调查时使用。可能的原因包括：

- 紧凑定稿器包含针对交叉或绕行的 `visualReviewRecommendation`（仅为建议，不是交付关卡）；
- 用户明确请求审美或视觉评审；
- 模板、渲染器或查看器的变更需要视觉回归证据；
- 新颖的布局或浏览器诊断导致信心不足；
- 本次运行被选中进行抽样审计或内部试用（dogfood）。

对于默认的独立桌面查看器，测量 1440×900、1600×1000、1920×1080 和 2048×1320。在每个检查尺寸下都要求 `document.documentElement.scrollWidth <= window.innerWidth`。优先满足 `scrollHeight <= window.innerHeight`；只有通过上文定义的 Reader 声明的可读例外，才接受页面级垂直滚动。在检查的最大视口下，检查渲染出的构图是否存在明显的空白下部带状区域：主面板和必要的结论卡片应作为一个均衡的整体利用可用高度，而不是塌缩成一条浅浅的窄带。对于意外的溢出，修复编写的构图，方式是只移除真正冗余的内容或压缩间距，然后才考虑缩小节点、标签或主面板。不要隐藏溢出、裁剪内容、引入内部的图滚动容器，或为了让测量通过而缩小节点/标签的字号。窄屏/移动端的容纳可以保留页面垂直滚动。

对于升级的评审，在当前已定稿的产物上运行 `visual-check`，用有能力的图像阅读器或由人检查其联系表，并检查两个端点主题、默认 READ 视图、线条交叉/通道、标签遮罩、节点/卡片适配、焦点/搜索/护照（passport）的关闭，以及导出的整洁性。此评审是补充性的，绝不改变 `browser_evidence`。不受约束的浏览器一瞥只能用于支持感知评审。

在诊断性或结构化交接中，报告一个如实的可选评审状态：

- `visual_review: not_requested` — 没有适用的评审触发条件；这不是视觉验收声明。
- `visual_review: passed` — 只有在检查过渲染后的产物之后才可使用。
- `visual_review: skipped (image reader unavailable)` — 被请求或被触发的评审无法运行。
- `visual_review: failed` — 附上具体的可见缺陷。

对于升级的评审，使用 `correction_rounds: 0`、`correction_rounds: 1` 或 `correction_rounds: 2`；绝不能超过两轮有针对性的修正。未请求评审时，使用 `correction_rounds: 0`。绝不能在未检查产物的情况下报告 `visual_review: passed`。如果感知评审改变了候选稿，请重新运行 `finalize`，因为先前的规格和产物回执已不再是当前的。

## 交接回执 <a id="handoff-receipt"></a>

对于被请求的诊断性或结构化交接，从现有回执中推导以下详情。普通的面向用户回复遵循 [Output](../SKILL.md#output)；此清单不是默认的聊天回复。

```text
diagram_type: <actual diagram type>
output: /absolute/path/to/file.html
specification_sha256: <receipt value>
artifact_sha256: <receipt value>
validation: <actual quality profile, check counts, errors, and warnings>
browser_evidence: passed|failed|skipped
visual_review: not_requested|passed|skipped (image reader unavailable)|failed
correction_rounds: 0|1|2
```

只能从最新的、与产物绑定的 `browser-check` 回执（通常是 `finalize` 内嵌的阶段）推导 `browser_evidence`。可选的截图或手动浏览器工作要单独记录，并附上其产物绑定、视口/主题范围和观察结果；绝不能用它或 `visual_review` 覆盖自动化状态。

打开、预览状态、分享卡片（Share Cards）以及其他查看器导出都不是校验声明。

定稿回执的发布使用上文所述的同一个与身份绑定、不覆盖的发布器和显式恢复记录。完整回执和摘要回执必须与候选稿、产物、交付元数据和浏览器回执各不相同。它们的目标必须不存在，或是单链接的常规文件；作为符号链接的回执条目和被硬链接的目标会失败即关闭。之后出现的占用者或父目录变化会停止发布，并保持不动。默认回执名与物理产物共享命名空间，并受主机文件名长度限制约束。两个回执是分别发布的，而不是崩溃原子的一对；只有完整执行并通过的命令才算成功交接。
