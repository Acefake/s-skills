# 评审标准

用相关的视角去审查。不是每个视角都适用于每个改动。

## 正确性

代码真的做到了意图所说的吗？

- 边界情况：空输入、nil/undefined、边界值、并发访问
- 错误处理：错误是被捕获了、往上传了，还是被悄悄吞掉了？
- 差一错误（off-by-one）、类型强制转换、整数溢出、字符串编码
- 状态管理：竞态条件、过时的闭包、悬空引用
- 正常路径和出错路径都能工作吗？
- 幂等性：如果这个操作运行两次，或者上一次运行在中途崩溃了，会怎样？如果答案是“取决于留下了什么状态”，那就缺了一个对账步骤。
- 并发：如果多个参与者可能接触同一个可变状态（文件、分支、共享数据），访问是用结构化的方式串行的（锁、按顺序的阶段、独占归属），还是靠一些守不住的约定？

当你发现一个潜在的 bug 时，追踪执行路径。不要只是标一句“这里可能是 nil”。展示让它变成 nil 的那条调用链。

## 根本原因 vs. 症状

代码是在修真正的问题，还是在掩盖一个症状？

回答这个问题，常常需要看改动文件之外的东西。读周围的代码（调用方、被调用方、类型定义、同级模块），弄懂这个改动所处的架构。用你能用的工具（Read、Grep、Glob）顺着调用链走、读类型、弄懂代码为什么存在，然后再判断这个改动是不是改在了正确的层。

- 掩盖了更深层不变量被破坏的守卫语句
- 掩盖了一个坏掉的约定的重试逻辑
- 让一个建模错误闭嘴的类型断言
- 一个绕过办法：为什么需要它？正确的修复应该是什么样子？
- 一个在模块 A 里的修复，其实应该是对模块 B 的约定的修复
- 本该用结构的地方用了指示：如果修复是一条写着“不要做 X”的注释，或者一条需要有人记住的约定，就问一问它能不能改成一个类型约束、一条 lint 规则或一个运行时检查，让错误的做法根本不可能发生

## 结构完整性

代码和它所在的系统契合得好吗？

- 守住边界：输入校验是否集中在入口，同一条件是否被重复检查？业务不变量、权限和可变状态是否在负责的操作中得到保证？不能用入口类型检查代替这些约束。
- 抽象层次：代码是不是把高层的编排和低层的细节混在一起了？
- 耦合：这个改动是不是引入了会让以后的改动更难的依赖？
- 数据模型的契合度：数据结构和实际的访问方式匹配吗？
- 硬接上去的 vs. 融为一体的：如果从一开始就知道这个新需求，代码会是这个样子吗？还是这个改动感觉像是打在现有设计上的补丁？
- 新旧两条路径并存：这个改动是不是引入了一个新 API，同时还让旧的那个活着？如果没有外部使用者，就在同一轮里迁移调用方并删掉旧路径。不要留下会变成永久的兼容层。

不要因为简单的代码缺少抽象就扣分。过早的抽象比重复更糟。

## 验证

你能从读代码看出它是能用的吗？

- 有测试吗？它们测的是行为还是实现细节？
- 有能抓住退化的断言/不变量吗？
- 如果这是一个 bug 修复：有针对这个 bug 的测试吗？
- 如果这涉及一个集成边界：完整的路径测过吗？
- 检查真实的东西，而不是替代指标。如果代码通过文件修改时间或缓存的状态来判断是否存活，而不是读实际的值，那就是一个验证缺口。
- 对于委派出去的或异步的工作：代码验证的是实际的输出产物，还是相信了自我汇报和总结？

## 复杂度预算

代码的复杂度和它所完成的事情相称吗？

- 可以在不损失正确性和清晰度的前提下变得更简单的代码
- 只服务于一个调用处的抽象
- 为还不存在的情况做的配置或参数化
- 死代码、没用的 import、残留的参数
- 过度设计：现在没有任何调用方的“以防万一”代码路径
- 为了已经不再需要的过渡期稳定而保留的过时兼容路径。如果迁移已经完成，就删掉脚手架
- 用户体验配得上这份复杂度吗？每个功能、控件和选项都应该有存在的价值。做了一半的功能比没有更糟。

越简单越好，除非简单是错的。

## 安全

对每一条安全方面的发现，都要追踪输入在代码里的路径并把它展示出来。

- 用户输入没经过清理就流向危险的去处（SQL、shell、eval、innerHTML）
- 新接口上的身份认证/权限缺口
- 代码、日志或错误信息里的密钥
- 安全攸关路径上的 TOCTOU（检查时与使用时不一致）问题
