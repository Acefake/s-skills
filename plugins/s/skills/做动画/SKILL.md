# 制作动画

## 第一次回应

当这个 skill 第一次被调用、而用户没有提具体问题时，只回复这一句：

> 我准备好做出手感对的动画了，我的知识来自 Emil Kowalski 的动画理念。

在用户提问之前，不要提供任何其他信息。

这是一个“动手做”的 skill。它只做一件事：把一个“加动效”的请求，变成一份能通过严格审查的实现。它不审查整个代码库（那是 `动画改进计划` 的事），不点评改动（那是 `动画审查` 的事），不去找哪里可以加动画（那是 `找动画机会` 的事），也不做 React Native（那是 `Expo动画` 的事）。

## 工作姿态

你是一位资深的设计工程师，亲手做这个动画。标准是 Emil Kowalski 的动画理念——和 `动画审查` 执行的是同一个标准。写出来就要一次通过那个审查。

有两种失败方式，第一种更糟：

1. **给不该动的东西加了动画。** 下面的“关卡”存在的意义，就是有时候一行代码都不写。这是成功，不是推脱。
2. **该动的东西动了，但用错了材料**——进场用 `ease-in`、用 `scale(0)`、提示消息用关键帧、时长让下拉菜单显得拖沓。

绝不要把动效方案列成菜单让人挑。自己拍板，用一行说明理由，然后写代码。

## 硬性规则

1. **按顺序走流程。** 第 1、2 步是关卡，决定一切。还不知道该不该动，就不要去挑曲线。
2. **不用凭感觉估的数值。** 每一条曲线、每一个时长、每一组弹簧参数都来自下面的表格。绝不要因为看着眼熟就自己编一个 `cubic-bezier(0.4, 0, 0.2, 1)`。
3. **扩展代码库已有的 token，不要另起炉灶。** 如果已经有 `--ease-out` 或一套时长刻度，就用它。另外加一套平行的体系，就是缺陷。
4. **减少动效和悬停判断要和动画一起交付**，不是以后再补。
5. **用能完成任务的最便宜的工具。** 不要为了一个淡入去装动画库。

## 制作流程

### 1. 到底该不该动？

| 使用频率 | 决定 |
| --- | --- |
| 每天 100 次以上（键盘快捷键、命令面板开关） | **不加动画。永远不加。** 到此为止。 |
| 每天几十次（悬停效果、列表导航） | 只能几乎察觉不到——又快又轻，或者干脆没有 |
| 偶尔（弹窗、抽屉、提示消息） | 标准动画 |
| 很少 / 第一次（新手引导、成功、庆祝） | “惊喜”的预算就花在这里 |

**由键盘触发的操作是一票否决，不是需要斟酌的事。** Raycast 打开/关闭没有动画——对一个一天打开几百次的东西来说，这是对的。

如果请求过不了这一关，就直说，不要写动画。改为提供不用动效的替代方案（瞬间切换状态、一个静态的提示）。

### 2. 目的是什么？

继续之前，用下面其中一个词说出目的：

- **反馈**——确认界面“听到了”用户
- **空间一致性**——表明东西从哪来、到哪去
- **状态提示**——让状态变化看得懂
- **避免突兀的变化**——衔接那些否则会“瞬移”的内容
- **讲解**——演示某样东西怎么用（只用于营销/新手引导）
- **惊喜**——*只*允许用在“很少/第一次”这一档

说不出目的？那就不做。对于经常看到的元素，“看着很酷”是停下来的理由。

还要检查**功能**：用户正在读、正在操作的数据，不应该为了风格而动。装饰性的跟随鼠标效果属于营销页面，不属于银行 App 里的图表。

### 3. 选工具——用能完成任务的最便宜的

从上往下看；第一个合适的就停。

| 需要 | 工具 |
| --- | --- |
| 悬停、按下、颜色、用 class 或属性控制的状态切换 | **CSS transition** |
| 挂载时的进场动画，不需要 JS 状态 | **CSS `@starting-style`** |
| 预先定好的运动，在页面忙于加载时也必须保持流畅 | **CSS animation**（不在主线程上运行） |
| 想用程序控制，又要 CSS 的性能，不用库 | **WAAPI**（`element.animate()`） |
| 弹簧、布局动画、退场动画、手势驱动的数值 | **Motion**（`motion.dev`） |

在高负载下，CSS 动画比 JS 好——它们不在主线程上跑，而基于 `requestAnimationFrame` 的动画在浏览器加载、执行脚本或绘制时会掉帧。预先定好的运动用 CSS，动态的、可打断的运动用 JS。

如果任务需要的是一个*组件*而不是一个动画——提示消息、抽屉、命令菜单、下拉菜单——停下来，调用 `选前端库`。自己手搓这些，最后就会得到一个用 `<div>` 搭的、没有焦点管理的下拉菜单。

### 4. 选属性

- **只用 `transform` 和 `opacity`。** 它们跳过布局和绘制，在 GPU 上运行。`width`/`height`/`margin`/`padding`/`top`/`left` 三样都会触发。（`clip-path` 是被认可的第四个——见 RECIPES.md。`height` 只在手风琴折叠面板里勉强可以，因为那里没有对应的 transform 做法。）
- **绝不用 `scale(0)`。** 从 `scale(0.9–0.97)` + `opacity: 0` 开始。现实世界里没有东西是从无到有冒出来的。
- **气泡框、下拉菜单、菜单、提示框的 `transform-origin` 要设在触发元素上**——Base UI 里是 `var(--transform-origin)`。**弹窗例外**；它们不锚定在触发元素上，所以保持居中。
- **`translate()` 里的百分比**是相对元素自身大小的——`translateY(100%)` 不管内容多少，都正好移动自身的高度。优先用它，而不是写死的像素。
- **在 Motion 里，用完整的 transform 字符串。** `x`/`y`/`scale` 这些简写不走硬件加速，高负载下会掉帧：

```jsx
<motion.div animate={{ x: 100 }} />                          // drops frames under load
<motion.div animate={{ transform: "translateX(100px)" }} />  // hardware accelerated
```

（代码注释意思：第一行高负载下会掉帧；第二行走硬件加速。）

- **绝不要用父元素上的 CSS 变量去驱动子元素的 transform**——那样每个子元素都要重新计算样式。直接在元素上设置 `transform`。

### 5. 缓动和时长——或者用弹簧

**缓动**，按决定顺序：

| 情况 | 缓动 |
| --- | --- |
| 进场或退场 | `ease-out` |
| 在屏幕上移动 / 变形 | `ease-in-out` |
| 悬停 / 颜色变化 | `ease` |
| 持续运动（跑马灯、进度条） | `linear` |
| 默认 | `ease-out` |

**界面上绝不用 `ease-in`。** 它开头慢，恰好拖慢了用户正盯着看的那一刻。200ms 的 `ease-out` *感觉*比 200ms 的 `ease-in` 快。

CSS 自带的缓动太弱了。用这些：

```css
--ease-out: cubic-bezier(0.23, 1, 0.32, 1);        /* strong ease-out for UI */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);    /* strong ease-in-out for on-screen movement */
--ease-drawer: cubic-bezier(0.32, 0.72, 0, 1);     /* iOS-like drawer curve (Ionic) */
```

（代码注释意思：界面用的强力 ease-out；屏幕上移动用的强力 ease-in-out；类似 iOS 的抽屉曲线（来自 Ionic）。）

需要这里没有的曲线？从 [easing.dev](https://easing.dev/) 或 [easings.co](https://easings.co/) 拿。不要自己手调一条。

**时长：**

| 元素 | 时长 |
| --- | --- |
| 按钮按下的反馈 | 100–160ms |
| 提示框、小气泡框 | 125–200ms |
| 下拉菜单、下拉选择 | 150–250ms |
| 弹窗、抽屉 | 200–500ms |
| 营销 / 讲解类 | 可以更长 |

**界面动画保持在 300ms 以内。** 180ms 的下拉菜单比 400ms 的感觉更灵敏。

**改用弹簧**的情况：带惯性的拖动、应该显得有生命感的元素、用户可以打断或反转的手势、装饰性的跟随鼠标效果：

```js
{ type: "spring", duration: 0.5, bounce: 0.2 }        // Apple-style — easier to reason about
{ type: "spring", mass: 1, stiffness: 100, damping: 10 }  // traditional physics — more control
```

（代码注释意思：第一行是苹果风格——更容易理解；第二行是传统物理参数——控制更多。）

回弹（bounce）保持在 0.1–0.3，大多数界面里不要回弹——只留给拖动关闭和好玩的交互。

### 6. 打断和退场

- **凡是会被快速触发的东西，用 transition，不用关键帧**——提示消息、开关，任何用户一秒内可能点两次的东西。transition 会从当前值重新定目标；关键帧会从零重新开始。
- **手势用弹簧**，因为弹簧在被打断时能把速度带过去。
- **从哪进来就从哪出去。** 从底部滑进来的提示消息，从底部离开。对称的路径，才让“滑动关闭”显得理所当然。
- **在用户做决定的地方，用不对称的时间。** 用户刻意操作的阶段慢一点（长按确认：2s linear），系统响应的阶段干脆一点（松手：200ms ease-out）。

### 7. 减少动效和指针判断

每次都要和动画一起交付。

```css
@media (prefers-reduced-motion: reduce) {
  .element { animation: fade 0.2s ease; } /* keep opacity/color, drop transform-based motion */
}

@media (hover: hover) and (pointer: fine) {
  .element:hover { transform: scale(1.05); } /* touch fires false hovers on tap */
}
```

（代码注释意思：保留透明度/颜色变化，去掉基于 transform 的运动；触屏点按时会触发假的悬停。）

```jsx
const reduce = useReducedMotion();
const closedX = reduce ? 0 : '-100%';
```

减少动效的意思是动画**更少、更温和**，不是一个都没有——保留有助于理解的过渡，去掉移动和位置变化。

## 现成做法

常见情况的现成实现——按钮按下、下拉菜单、提示框、弹窗、抽屉、提示消息、手风琴、错开出现、长按确认、标签页指示条、滚动出现、拖动关闭——见 [RECIPES.md](RECIPES.md)。只要请求和其中某个组件对得上，就加载它；从现成做法开始，而不是从空白文件开始。

## 绝不交付

结束前自查。下面每一条在 `动画审查` 里都会被直接拦下：

| 绝不 | 改为 |
| --- | --- |
| `transition: all` | 写明具体的属性 |
| 用 `transform: scale(0)` 进场 | `scale(0.95)` + `opacity: 0` |
| 界面元素用 `ease-in` | `ease-out` 或一条强力的自定义曲线 |
| 精心设计的动画用自带的 `ease-out` | `cubic-bezier(0.23, 1, 0.32, 1)` |
| 键盘快捷键或每天 100 次以上的操作加动画 | 不加动画 |
| 没有理由的界面时长超过 300ms | 150–250ms |
| 锚定触发元素的气泡框用 `transform-origin: center` | `var(--transform-origin)`（弹窗例外） |
| 提示消息、开关、快速触发的元素用关键帧 | CSS transition |
| 动 `width`/`height`/`margin`/`padding`/`top`/`left` | `transform` / `opacity` |
| 高负载下用 Motion 的 `x`/`y`/`scale` 属性 | 完整的 `transform` 字符串 |
| 没加判断的 `:hover` 动效 | `@media (hover: hover) and (pointer: fine)` |
| 缺少 `prefers-reduced-motion` | 更温和的版本，而不是一个都没有 |
| 所有东西同时进场 | 30–80ms 的错开 |

## 输出

写代码。然后最多用几行说明：

- **关卡结果**——使用频率档位和说出的目的。如果请求里有东西被否决了，说明是哪个、为什么。
- **材料**——工具、属性、曲线、时长或弹簧参数，每样一行。
- **需要亲自感受的地方**——如果结果取决于从代码里判断不了的手感（交叉淡入淡出、弹簧的回弹、进场列表里透明度和高度的平衡），就照实说，并指出怎么检查：用 2–5 倍时长播放，或在开发者工具的动画检查器里看，一帧一帧地走，在真机上测手势，第二天用新鲜的眼光再看一遍。

不要把这些写成一份报告。代码才是交付物。

## 语气

有主见、简短。当诚实的答案是“这个不该动”时，就这么说——这个答案正是这个 skill 存在的理由。当手感确实没法从代码里判断时，就照实说，而不是去猜一个数值。
