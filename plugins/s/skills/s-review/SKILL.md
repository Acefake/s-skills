# s-review

审一份代码改动，输出一份中文审查报告。全程中文，说人话，只报有依据的问题。

## 规矩

- 默认只读：不改代码、不提交、不推送、不合并、不切分支、不在 PR 上发评论。用户明确说"帮我修"或"发评论"才动手，动手前说清要改什么。
- 每条发现都要有代码出处和理由。说不出"哪一行、为什么错、会造成什么后果"的，不报。
- 纯个人偏好（命名口味、换个写法也行）不报；仓库规范里写明的才算规范问题。
- 改动没问题就直说"没发现需要改的问题"，不要为了显得认真硬凑意见。
- 没看到的东西不下结论，放进"没查到的部分"。

## 第一步：确定审查范围

按用户给的输入选一种：

| 输入 | 怎么拿到改动 |
|---|---|
| PR 链接或编号 | `gh pr view <号> --json title,body,baseRefName,headRefName,files` 和 `gh pr diff <号>`；没有 gh 就用 GitHub 工具读 |
| 分支名 | 找到基准分支（通常 main），`git fetch` 后 `git diff $(git merge-base origin/main <分支>)..<分支>` |
| 本地未提交改动 | `git diff` 加 `git diff --cached`，再用 `git status` 看新文件 |
| 没说清楚 | 当前分支有 PR 就审 PR；否则审当前分支相对 main 的改动；都没有就问用户 |

拿到后先列出改了哪些文件、各加减多少行。改动超过约 1500 行或 40 个文件，先告诉用户范围大，建议分批或先挑高风险文件。生成文件、锁文件、快照只扫一眼是否该提交。

## 第二步：写意图摘要

先读 PR 标题、描述、关联的 issue 或需求文档、提交信息，用 2～4 句话写下：

- 这次改动想解决什么问题；
- 打算怎么解决；
- 有没有明说不做的事。

意图读不出来就照实写"意图不明"，并按代码本身推断。后面判断"是不是 bug"都以这份摘要为准：代码和意图不符，本身就是一条发现。

## 第三步：按风险挑审查角度

正确性和测试覆盖每次都看，其他按改动内容挑，不要全量铺开：

| 角度 | 什么时候看 | 重点 |
|---|---|---|
| 正确性 / bug | 每次 | 边界值、空值、错误分支、并发与重入、状态没清理、条件写反 |
| 回归 | 改了已有行为、公共接口、配置、数据结构 | 调用方有没有一起改，老数据、老客户端还能不能用 |
| 安全 | 涉及鉴权、用户输入、SQL/命令拼接、文件路径、密钥、外部请求 | 注入、越权、敏感信息进日志或代码 |
| 性能 | 循环里查库或发请求、大数据量、热路径 | N+1、无界增长、不必要的重复计算 |
| 测试覆盖 | 每次 | 新逻辑和修的 bug 有没有测试，测试是否测的是行为而不是实现 |
| 可读性与规范 | 每次轻扫 | 仓库约定、命名、死代码、注释与代码不符 |
| 数据与迁移 | 改了表结构、迁移脚本、序列化格式 | 能否回滚、是否锁表、默认值 |

读 diff 时要打开改动周围的完整文件和关键调用方，只看 diff 片段容易误判。

可以配合仓库已有的 skill：

- 规范问题按 `code-style` 的规则判断；
- 想核对"改动是否满足需求"，用 `requesting-code-review` 的检查清单；
- 高风险改动（鉴权、支付、数据迁移、并发）或用户要求严审时，用 `interrogate` 让多个角度互相挑刺；

## 第四步：核实每条发现

报之前逐条自问：

1. 能指出具体文件和行号吗？
2. 是真会出问题，还是"可能也许"？能写出触发条件吗？能跑测试或小脚本验证的，就验证。
3. 是不是 diff 外面已经处理了（调用方校验、框架兜底）？
4. 是这次改动引入的，还是原来就有？原来就有的单独标"既有问题"，不影响结论。

严重程度：

- **P0 阻塞**：会导致数据丢失、安全漏洞、线上崩溃、核心功能错误，必须修了才能合。
- **P1 应修**：明确的 bug、缺关键测试、回归风险，正常情况下合并前要修。
- **P2 建议**：可读性、小的健壮性改进，可改可不改。

拿不准的降一级，并写明"不确定，原因是……"。

## 第五步：输出报告

```
## 审查结论：可合并 / 修后合并 / 不建议合并
一句话理由。

## 意图摘要
……

## 发现（共 N 条：P0 x / P1 y / P2 z）
### [P1] 标题
- 位置：`path/to/file.ts:42`
- 问题：……
- 为什么：触发条件和后果
- 怎么改：具体改法，必要时给几行示例代码

## 覆盖范围
看了哪些文件和角度，跑了哪些测试或命令。

## 没查到的部分
没看的文件、没法验证的假设、需要作者确认的问题。
```

结论规则：有 P0 就"不建议合并"；有 P1 没 P0 是"修后合并"；只有 P2 或没有发现是"可合并"。没有发现时，"发现"一节写"没发现需要改的问题"。

报告发完后，问用户要不要帮忙修其中哪几条，或者把意见发到 PR 上。用户同意再做。
