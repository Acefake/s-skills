# 影响范围

在一个改动上线之前，找出它会在别处弄坏什么。用于“X 的影响范围”、“这会弄坏什么”，或者审查一个你还不放心的小 diff。

它和 `代码怎么工作`、`代码为什么这样` 是一组的。`代码怎么工作` 告诉你代码做了什么。`代码为什么这样` 告诉你它为什么是这个样子。影响范围告诉你它会在别处弄坏什么。

列出调用方不是这里的工作。智能体一秒钟就能用 grep 搜出来。这里的工作是找出 grep 搜不出来的破坏。

## 别相信你自己写的说明

一份听起来很对的影响范围说明一文不值。不管它是不是真的，读起来都同样令人信服。所以不要交回这份说明。找出整件事所依赖的那一两个事实，通过运行代码来证明它们。

### 你有多确定

对于改动的安全性所依赖的每一个事实，在成本不高的前提下，尽量把它推到下面这个列表越往后越好的位置，并说明停在了哪一级。

1. 你说是这样。单独这一条一文不值。
2. 你指出了那一行。一个真实的 `file:line`，或者那个库自己的源代码。
3. 你证明了坏情况不可能发生。你一步一步走了一遍失败过程，它走不到那里。
4. 你运行过它。一个调用真实代码的脚本或测试，如果你错了，它会明确地失败。
5. 你在运行中的应用里复现了它。

第 4 级通常就是一个小脚本：导入应用实际打包的同一个库，调用你担心的那个函数。

## 步骤

1. 读这个改动。读 diff、它新增、修改和删除的符号，以及它现在有什么不同的行为，包括 diff 里没写明的那部分。用 `代码为什么这样` 的第 2 步拉取 PR 和提交记录。
2. 找出它之所以安全所依赖的那一个事实。大多数看起来有风险的改动，之所以安全，是因为某一个事实，比如“这个调用只会丢掉已经失效的缓存条目，别的什么都不做”。找到那个事实。如果它成立，大多数有风险的情况一下子就排除了。把时间花在这里，而不是花在一长串“也许”上。
3. 去看 grep 看不到的地方。读你调用的那个库的源代码，检查它锁定的版本和本地打的补丁。弄清楚东西是什么时候运行的：微任务、卸载和清理阶段、Solid 和 React 的区别。追踪符号搜索会漏掉的东西：API 返回的 JSON、一个数据库字段、一种线上传输格式、另一种语言读取同样的字节、一个功能开关、往下游隔了三层的代码。
4. 对每个风险都要诚实。给它一个真实的发生概率，以及发生后的真实代价。保留你确认过的风险。把你检查过并排除了的风险单独列出来。规则和 `代码为什么这样` 一样：引用真实的 `file:line`；什么都没搜到的搜索也算一个答案；永远不要编造调用方或 API。
5. 证明那一个事实。写一个运行真实代码的脚本或测试，运行它，把结果贴出来。
6. 对于大的或涉及面广的改动，把它当作一次 `多方案竞技场` 来跑。把同一个问题问不止一个模型，再合并答案。不同的模型会抓到不同的真实 bug。

## 要交回什么

- **它做了什么。** 改了什么，包括不明显的那部分。
- **它之所以安全所依赖的那一个事实。** 说出这个事实，说明你把它推到了第几级，并给出证明。如果没能证明，就写“未证明”。
- **风险。** 每一条都说明它怎么坏、`file:line`、可能性多大、后果多严重、怎么检查。对重要的风险，贴出证明。
- **已排除。** 你检查过什么，以及为什么没问题。
- **合并之前。** 能抓到真实 bug 的最便宜的测试或复现办法，包括你写的那个脚本。

用 `清理AI腔` 过一遍文字，引用真实的代码，在发到任何公开的地方之前，删掉所有私密内容。

**回复：** 上面那份说明，其中那个安全事实要么已证明，要么标为“未证明”。
