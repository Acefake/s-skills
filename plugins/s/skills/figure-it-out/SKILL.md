# 自己想办法搞定

当任务和任何 playbook（操作手册）都对不上时，就自己设计一套。在写任何代码之前，要交付的是工作流程本身：一串阶段，严谨程度和任务相匹配，按科学方法运行，并留下一条人离开一阵后回来可以审计的决定记录。

## 开始

开一个待办清单，第一项是阅读 **poteto-mode** skill 里的 Principles（原则）一节。然后把下面的各个阶段作为待办项加进去。

## 阶段 A：定框架

先弄清背景，再做决定。在你能说清下面这些之前，不要开始运行：

- “完成”的定义，要写成一个可以被证伪的判断条件（见 **prove-it-works** 原则 skill）。
- 范围，要量化：大致的单元数和工作量，以及摸底时发现的阻碍。
- 严谨程度，宁高勿低。单向门（做了就回不去的决定）和影响范围大的事情，要更严谨。可撤销的、风险低的步骤，可以少一点。严谨体现在关卡和产物上，而不是“更努力一点”。

在决定开始一次长时间运行之前，先把框架和取舍讲出来。可撤销的工作直接进行（见 **never-block-on-the-human** 原则 skill），但一次要跑好几个小时的运行，值得设一个检查点。

## 阶段 B：设计工作流程

拆成不可再分、可以各自独立合入的单元。最不确定、风险最高的先做。脚手架和验证在功能之前（见 **foundational-thinking** 原则 skill）。

- 在做工作之前先搭好验证工具，并从改动之前的状态采集基线，让检查结果读起来就是“旧值 vs 新值”。
- 对于单向门式的设计决定，运行 **architect** skill（它会运行 **arena**）。对于形状已经很具体的机械性工作，跳过它。对一个已经定下来的设计再开一次竞技场，就是过度设计（见 **laziness-protocol** 原则 skill）。
- 决定哪些要分派出去。只在接缝处并行，并给每个工作者它自己的 worktree 或分支（见 **separate-before-serializing-shared-state** 原则 skill）。不要分派过度。按 **poteto-mode** skill 里 “Subagents” 一节的规定，为每个子智能体的任务选择推理等级，以及快速还是标准速度。
- 把设计好的阶段列表写下来。人要审查的就是这份列表。

然后执行这个设计。把它的各个步骤作为具体的条目，加到待办清单里阶段 C 和阶段 D 之间。每一步都按阶段 C 的循环纪律来跑，并把阶段 D 的记录穿插其中，每完成一步就记一行，而不是把整条记录留到最后才写。

## 阶段 C：跑循环

每个单元都是一次实验。说出假设，做最小的改动，在真实的产物上对照判断条件去测量；如果有进展就保留，没有就撤回。按照 **sequence-verifiable-units** 原则 skill，每个单元都先验证，再开始下一个，而不是把检查攒到最后一起做。

- 通过检查产物来验证，永远不要靠自我汇报。当某件事过得太容易时，先怀疑观察方法，再怀疑系统。
- 委派出去的工作要配一个评审。如果某个工作者钻关卡的空子，就重来，并把约定收紧。如果关卡本身是错的，就在一个单独的改动里修好关卡，而不是绕过它。
- 结论只有 VERIFIED（已验证）、NOT VERIFIED（未通过验证）或 INCONCLUSIVE（无法确定）。无法确定不算通过。不要藏起负面结果。

## 阶段 D：保留审计记录

用 **show-me-your-work** skill 记录这次运行。figure-it-out 做的工作通常足够有野心，值得把记录提交进代码库，让审查者能在 PR 里读到它。这条记录加上 diff，才能让人回来之后信任这份工作。

## 阶段 E：验证并交回

在真实的产品上（而不只是在验证工具上）对照阶段 A 的判断条件检查整体。把任何反复出现的纠正写成一个关卡、一条 lint 规则、一个检查或一个脚本（见 **encode-lessons-in-structure** 原则 skill）。

**回复：** 你设计的这套做法、严谨程度及其理由、决定记录的路径、哪些已经对照判断条件验证过、哪些还没解决。
