# 设计理由模板

和类型草图一起交付的说明文字。一页。标题用句子式大小写，不要套话。把斜体的说明换成实际内容。

## 问题（Problem）

*一段。我们想做什么，以及现有系统或约束的哪些方面让形状不那么显而易见。如果[阶段 A](../SKILL.md#phase-a-ground-the-problem)发现了设计必须遵守的约束（要互相配合的已有类型、不能弄坏的调用方、穿过我们边界的不变量），就在这里说出来，让读者看到你看到的同样的约束。*

## 用法（调用方视角）（Usage (caller's view)）

*先写这一节，在类型草图之前。展示使用者会读的 README 或快速上手，再加上他们自己代码里两三个真实的调用处。他们导入什么，调用什么，得到什么。[形状](#shape)里的类型草图就是从这里推导出来的。两者必须一致。当它们不一致时，让草图去配合用法，而不是反过来。调用方的体验就是规格。类型为它服务。*

## 形状（Shape）

*推荐的架构。先写数据结构。然后写数据怎样流过各个函数签名。说出承重的那些决定。说明哪些不变量编码在类型里、校验放在哪里、系统故意不做什么。明确地评判接口深度。说明公开接口藏住了什么复杂度、还有什么暴露给了调用方，以及为什么这个接口没有比需要的更大。引用每个决定背后的原则（例如 `per boundary-discipline`）。不要复述原则本身。*

## 综合决定（Synthesis decision）

*由 [arena](../../arena/SKILL.md) 填写。记录哪个候选成了基础以及原因、从其他每个候选那里借鉴了什么，以及否定了什么、为什么。*

## 接受的取舍（Tradeoffs accepted）

*选定的形状做出的每一个取舍，各写一条。格式：“我们接受 X，以换取 Y。”说出任何未来的读者可能误以为是疏忽的东西，包括那些看起来像是过早优化或过早简化的东西。*

## 考虑过的备选方案（Alternatives considered）

*必填。至少说出一个具体的备选形状，并用一行说明它为什么落选。评判每个备选方案要看接口深度，而不只是看实现是否简单。说出它暴露给调用方的复杂度和它藏住的复杂度。当设计空间里有真正的竞争者时，这里写两三个备选方案。如果约束逼出了唯一的答案，写一个就够了，结论写成“这是唯一可行的形状，因为……”。避免列出同一个形状的几种变体。这一节写的是选定形状考虑过并否定了的设计备选，而不是其他参赛者的候选。*

## 未解决的问题和风险（Open questions and risks）

*你在画草图时注意到的、需要人来权衡的事情，以及在开始实现之前值得指出的风险。写成问题，而不是断言，这样人的回答就是结论，而不只是一条评论。*

## 下一个实现步骤（Next implementation step）

*照着草图要做的第一件事。一句话。综合完成之后（或者如果选了检查点，在阶段 D 批准之后），你会马上开始写的东西。*
