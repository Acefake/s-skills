# 打造杠杆

只要工作不简单，就打造一个工具去做，而不是亲手去做。

codemod、生成器或脚本每次都用同样的方式完成工作，而且重新运行不花任何成本。这个工具是审查者可以阅读、可以重新运行来检查工作的一份产物。手工做的改动，只能靠重做一遍来重新验证。一个确定性的脚本，把“相信我”变成“运行这个”。

默认就去打造杠杆。只有当任务很简单、只是一眼就能看清的几处明显改动时，才跳过。

- 先手工做第一个单元，弄清做法，然后再写工具。用工具在这个单元上重新跑一遍，和你手工做的版本做 diff 对比，以此证明工具是对的。让杠杆可以安全地重复运行。
- 改代码用 codemod 或脚本，重复性的文件用生成器，分析用导出到 sqlite 再查询的办法，验证用可以重复运行的检查。
- 确定性的杠杆胜过分派任务。如果工具一次就能处理所有单元，就自己运行它。不要派一群代理去手工做脚本就能做的事。
- 当你把工作分给子智能体时，把杠杆写成一个它们都会读的 skill：做法、验证约定、不许碰的边界，都放在一份产物里。把它放在这些代理能写的范围之外，免得它们悄悄改掉约定。
- 用了这条原则，就会产生一个文件。如果你引用了这条原则，但 diff 里没有 codemod、脚本、生成器或给代理的 skill，那你其实没有用它。
- 当工作的生命期比这次会话长时，把杠杆提交进代码库。

门槛是“是否简单”，而不是“是否重复”。一次性的工作，只要杠杆能让工作变得可检查，也值得做一个杠杆。按照 [Laziness Protocol](../principle-laziness-protocol/SKILL.md)（偷懒守则），只写能完成或证明这项工作的最小脚本，永远不要写成框架。

和 [Encode Lessons in Structure](../principle-encode-lessons-in-structure/SKILL.md)（把教训写进结构）不同：那一条是把反复出现的指示变成持久的护栏。这一条讲的是眼前这份工作的产出效率和可审查性。关于把验证本身写成脚本，见 [Prove It Works](../principle-prove-it-works/SKILL.md)（证明它真的能用）。
