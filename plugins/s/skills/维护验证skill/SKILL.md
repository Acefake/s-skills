# 维护一个验证 skill

应用一改，功能地图就开始过时。这个 skill 是对 `/创建验证skill` 生成的 skill（或任何带功能地图的项目内验证 skill）做日常维护的循环。严谨的单位是功能，而不是每一句话：要从源代码覆盖每一个功能文件，并实际操作每一个功能，但不需要把每一条要点都跑到底。

## 结果

选一个，并说明是哪一个：

- **clean**（干净）：每个功能都得到了源代码和实时操作的覆盖；没有值得提交的东西。不建分支，不开 PR。
- **changed**（有改动）：开一个 PR，提交已经证明过的文档、测试工具或地图修正。
- **blocked**（被卡住）：覆盖没能完成，或者一个已证明的修复没法安全地提交。确切说明是什么卡住了它。

## 修改范围

只修改验证 skill 自己的目录（它的 SKILL.md、features/，以及它拥有的测试工具脚本）。运行期间永远不要修改产品代码：地图里描述了、应用却不再那样做的行为，要么是文档过时（修地图），要么是产品退化（报告它，不要在文档里掩盖它）。

## 一遍检查

0. **找到目标。** 找到要维护的验证 skill：项目里那个正文有启动/操作部分、并带有功能地图的 skill。Cursor 通常在 `.cursor/skills/verify-*/`，别的软件在它自己的 skill 目录里；对不上就在仓库里搜带功能地图的 `SKILL.md`。有好几个候选就问是哪一个；一个都没有就停下，并指向 `/创建验证skill`，而不是编造一个目标。

1. **索引整理。** 读功能地图的 README，并用通配符列出它旁边的文件。修掉缺失、多余、重复或失效的条目。轻量处理；不要生成清单。

2. **源代码一轮。** 每个功能文件派一个只读的子智能体，同时启动。每个子智能体都从源代码解释“这个面向用户的功能是怎么工作的？”，带引用地标出可能过时的文档，并返回一份简洁的实时验证做法。子智能体永远不操作应用，也永远不修改文件。返回格式：功能概要 / 源代码入口 / 可能的过时之处或“无” / 一份做法。

3. **整合。** 每个功能文件都要有一份返回的概要。把重叠的做法合并成尽量少的应用状态。抽查被引用的过时之处；不要重新证明那些说没问题的结论。扫一遍最近的改动，找出地图里缺失的面向用户的界面，在说某个缺失之前，必须有一个具体的源代码路径。

4. **实时一轮。** 即使源代码看起来没问题，也必须做。所有操作都由协调者负责；遵循验证 skill 自己的启动模式：对服务器和界面，用一个长期运行的实例，按顺序操作；对短命的命令行工具，每次操作都用一个全新的隔离会话（由那个 skill 的 Launch 部分决定，而不是由这个 skill 决定）。每个功能至少操作一次，并且在整个过程中，不管出了什么故障，都要守住三条不变量：(1) 一个实例自从上次出现意外情况之后，如果你还没对它做过健康检查，就永远不要操作它：第一次操作前做 doctor；如果以会话为单位，每个新会话都做 doctor；任何一次操作失败后再做 doctor；如果 doctor 看不到故障（进程健康、界面却卡在某个状态），就重置到一个已知状态或重新启动，而不是心存侥幸。(2) 到目前为止采集到的证据，在每一次清理之后都还在，要到它指定的位置去检查，而不是假设它还在。(3) 一次操作启动的任何东西，在这次操作没用之后都不能继续存在：不管会话是卡住、退出了还是共享的，失败迭代留下的残余都要清理掉（如果是共享的实例，清理残余，而不是清理实例）。由 skill 过时导致的 doctor 失败，就是过时：在修改范围内修好它，然后重试一次（只重启被这个修复弄失效的东西，别的不动），之后才能把这一遍判为 `blocked`。一个无法到达的功能，只有在写明了具体的前提条件（登录、权限、操作系统、外部状态）和尝试过的路径时，才能判为 `verified-unreachable`；如果地图里漏了这个前提条件，那就是过时。在分诊中做的任何测试工具修复，在提交之前都要再实时操作一遍。最后的清理在这次运行的最后一次操作之后进行（包括那些重新证明的操作），这样就没有东西在运行结束后还留着（按照那个 skill 的规定，证据保留）。

5. **分诊。** 从用户角度的描述错了或缺了，就是文档过时，修掉它。行为正常、测试工具却操作不了，就是测试工具缺口，修掉它；测试工具的修复遵循和生成时一样的辅助脚本规则（脚本可执行，调用方式写在 skill 正文里）。应用的行为确实坏了，就是产品缺口；把它记下来告诉用户，不要放进这个 PR。

6. **提交或停下。** 如果是 changed：开一个包含已证明修正的 PR，先把每个改动过的文件重新读一遍。如果是 clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

在一个临时位置保留简洁的运行笔记（覆盖了哪些功能、无法到达的前提条件、确认的过时之处、结果）；不要提交它们。
