# 补进度

告诉用户：从他在 `/补上对话进度` 之前写的最后一条消息到现在，这个对话里有什么变化，并帮他理解每个变化，而不只是告诉他进展到哪了。通知和子智能体的结果不算他的消息。假设用户记得自己的最后一条消息，之后的什么都不记得。

用 [`/说人话重讲`](../说人话重讲/SKILL.md) 的语气，而不是它的任务：平实的话、短句子、没有行话，就像一个人给另一个人补进度。说对用户来说什么变了，而不是你是怎么做的。说“测试通过了”，而不是“CI 绿了”。除非用户需要用到其中一个来行动，否则不要写哈希值、文件路径、命令、构建编号和测试数量。称呼每个 PR、分支或智能体时，用用户认得的名字，而不是你自己编的标签。如果一个事实需要背景才能看懂，要么给出背景，要么别写这个事实。

## 收集变化

这一轮保持只读。只用你已有的东西做图：不要改代码，不要启动应用或任务，不要发布任何东西。收集从那条消息以来你自己做的工作、子智能体的报告，以及这个对话里其他任何人的消息。检查这个对话涉及的每个 PR、CI 运行或智能体的当前状态。把你要展示的每个数字和它的事实来源核对一遍，如果你改正了某个数字，要说出来。

需要用户处理的事项（action item），是只有用户才能做的决定或步骤，比如一个产品上的选择、一次批准、一个不可撤销的操作，或者你没有的访问权限。所有还在等用户的都要写进来，哪怕是在他最后一条消息之前提出的。你自己还能做的工作，不算需要用户处理的事项。永远不要为了填满回复而编造一个决定。一个用户没要求、工作也不需要的步骤，不算需要用户处理的事项，除非它是不可撤销的、并且在等用户：给它一行说明，不配图，也不用写用户不回答会怎样。

## 写回复

整条回复要远远少于 150 个英文词（不算图）。当某件事用图比用句子更容易理解时，就画出来：一个设计或系统怎么工作、一串 PR 或依赖链以及每个 PR 的状态、一次修复的前后对比，或者并排的几个选项。永远不要画状态列表，或者互相之间没有连线的方框。同一个事实永远不要说两遍，不管是在文字里还是在几张图之间。对用户没有带来任何变化的工作就别写。字数不够时，先删“发生了什么”，再删需要用户处理的事项。

开头用一句话说有几件事需要用户，或者没有任何事需要。如果什么都没发生，也没有任何事在等用户，就这么说，然后停下。

然后展示发生了什么，图放在前面。把工作产出的截图和视频直接嵌在正文里，然后是解释某个变化的图。然后，对用户要求的每一件事，用一条简短的要点总结：结果怎么样，是已完成、还在运行、失败了，还是没检查。每一行都写成你会大声说出来的样子：“搜索慢是因为少了一个索引”，而不是“搜索审查：完成”或“慢搜索：缺索引”。点出途中发现并修好的任何 bug。每一行单独读时都必须是真的。永远不要把还在等用户的事标成完成，也不要写需要用户处理的事项里已经写了的内容。在总结下面，最多写三行简短的话，写那些会改变用户所知道的、或者用户必须做的事情的内容。然后用一行点出你自己还能做的剩余工作。

然后把需要用户处理的事项列成普通的要点，永远不要画成图或方框。每一项写两行，如果是用户没要求的不可撤销步骤就写一行：第一行是要做的决定、你的建议和理由，第二行是用户不回答会怎样。问用户自己说了算的那个决定，比如合并、批准或挑选。你会先做的步骤放在你的建议里。必须先发生的事情、以及任何无法撤销的事情，也放在建议里。不知道的部分写“未知”。附上详细内容的链接。

在列表后面展示选择。如果上面的截图已经展示了各个选项，就在每张截图下面写这个选项的好处和代价，而不是再画一张新图；否则，就把这些选项并排比较，如果有当前状态，也一起放进去。工作中权衡过的每个选项都要列出来，每个都写它能给用户带来什么、代价是什么。不要在正文其他地方再提它们。

## 图

图就是一张画面：截图、视频、Mermaid 图、用 `/visualize` 做的图表或示意图，或者一张生成的图片。Markdown 表格不算图，哪怕它有“之前”和“之后”两列。

每张图都要小到一眼就能看懂：最多六个方框，每个方框最多八个词。标签写成人会说的平常话，而不是“Tests: pass”这样的标签。需要一句话才能说清的事实，应该放在文字里，或者干脆不写。

当变化是看得见的，就把截图和视频直接嵌在正文里，而不只是给链接。如果一个看得见的变化没有截图，就在它的总结行上标“还没有截图”，并在那里说明屏幕上变了什么。根据你已有的事实画示意图和图表：表示东西之间怎么连接的用 Mermaid 图，表示数字的用 `/visualize` 图表。永远不要编造数字，也永远不要去画或生成一个你没截到的屏幕画面。只链接确实存在的产物。
