# 系统化调试

## 概述

随意修复浪费时间，还会制造新的 bug。临时补丁会掩盖底层问题。

**核心原则：** 在尝试修复之前，始终先找到根因。只修症状就是失败。

**违反本流程的字面要求，就是违背调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果还没完成阶段 1，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间紧迫时（紧急情况会让人想靠猜）
- 「只改一处就好」看起来很明显
- 你已经试过多种修复
- 上一次修复没有奏效
- 你还没有完全理解这个问题

**以下情况不要跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你很赶时间（赶工必然返工）
- 管理者要求立刻修好（系统化比乱试更快）

## 四个阶段

必须完成当前阶段，才能进入下一阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决办法
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能稳定触发它吗？
   - 确切步骤是什么？
   - 每次都会发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查近期变更**
   - 哪些变更可能导致这个问题？
   - Git diff、近期提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → build → signing，API → service → database）：**

   **在提出修复之前，先加上诊断埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误位于调用栈深处时：**

   本目录中的 `root-cause-tracing.md` 有完整的反向追踪方法。

   **简要版本：**
   - 坏值从哪里来？
   - 是谁带着坏值调用了这里？
   - 一直向上追，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**先找到模式，再动手修复：**

1. **找到能工作的例子**
   - 在同一代码库中定位相似且能工作的代码
   - 和坏掉的部分相似、却能工作的是什么？

2. **对照参考实现**
   - 如果要套用某个模式，把参考实现完整读完
   - 不要略读——逐行读
   - 完全理解这个模式之后再应用

3. **找出差异**
   - 能工作的和坏掉的有什么不同？
   - 列出每一处差异，再小也要列
   - 不要假定「那无关紧要」

4. **理解依赖**
   - 它还需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与检验

**科学方法：**

1. **只形成一个假设**
   - 明确陈述：「我认为 X 是根因，因为 Y」
   - 写下来
   - 要具体，不要含糊

2. **做最小检验**
   - 用尽可能小的改动来检验假设
   - 一次只变一个变量
   - 不要一次修多件事

3. **继续之前先验证**
   - 奏效了吗？是 → 进入阶段 4
   - 没奏效？形成新的假设
   - 不要在上面再叠更多修复

4. **当你不知道时**
   - 说「我不理解 X」
   - 不要装作知道
   - 寻求帮助
   - 再做研究

### 阶段 4：实施

**修复根因，而不是症状：**

1. **编写失败测试用例**
   - 尽可能简单的复现
   - 能自动化就写自动化测试
   - 没有框架就写一次性测试脚本
   - 修复之前必须先有
   - 用 `tdd` 技能来编写合格的失败测试

2. **只实施一处修复**
   - 针对已确认的根因
   - 一次只改一处
   - 不要顺手做「既然来了就改改」的改进
   - 不要把重构捆在一起

3. **验证修复**
   - 测试现在通过了吗？
   - 没有弄坏其他测试吗？
   - 问题真的解决了吗？

4. **如果修复无效**
   - 停下
   - 计数：你已经试过多少次修复？
   - 如果 < 3：回到阶段 1，用新信息重新分析
   - **如果 ≥ 3：停下，并质疑架构（见下面第 5 步）**
   - 没有架构讨论，就不要尝试第 4 次修复

5. **如果 3 次以上修复都失败：质疑架构**

   **表明架构有问题的模式：**
   - 每次修复都在别处暴露新的共享状态、耦合或问题
   - 修复需要「大规模重构」才能落地
   - 每次修复都在别处制造新症状

   **停下，并质疑基本假设：**
   - 这个模式在根本上站得住吗？
   - 我们是不是「纯粹因为惯性才坚持它」？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，先和你的人类搭档讨论**

   这不是假设失败——这是架构错了。

## 危险信号——停下并遵循流程

如果你发现自己在想：
- 「先快速修一下，以后再查」
- 「改改 X 看看行不行」
- 「一次改多处，跑测试」
- 「跳过测试，我手动验证」
- 「大概是 X，我来修」
- 「我没完全理解，但这个也许能行」
- 「模式说的是 X，但我要改成另一种做法」
- 「主要问题如下：[没调查就列出修复]」
- 还没追踪数据流就提出方案
- **「再试一次修复」（已经试过 2 次以上时）**
- **每次修复都在别处暴露新问题**

**以上全部意味着：停下。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（见阶段 4.5）

## 你的人类搭档发出的「你做错了」信号

**留意这些纠正：**
- 「那并没有发生吧？」——你没验证就做了假设
- 「它能告诉我们……吗？」——你本该加上证据收集
- 「别猜了」——你没理解就在提修复
- 「把这个想透」——质疑基本假设，而不只是症状
- 「我们卡住了？」（带着挫败）——你的方法行不通

**看到这些时：** 停下。回到阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| 「问题很简单，不需要流程」 | 简单问题也有根因。对简单 bug，流程很快。 |
| 「紧急情况，没时间走流程」 | 系统化调试比猜了再试的乱撞更快。 |
| 「先试这个，然后再查」 | 第一次修复会定下模式。从一开始就做对。 |
| 「等确认修复有效后再写测试」 | 没测试的修复站不住。先写测试才能证明。 |
| 「一次修多处能省时间」 | 无法隔离到底哪一处奏效。还会引出新 bug。 |
| 「参考太长，我改一改模式就行」 | 一知半解必然出 bug。把它完整读完。 |
| 「我看到问题了，让我修」 | 看到症状 ≠ 理解根因。 |
| 「再试一次修复」（已经失败 2 次以上） | 失败 3 次以上 = 架构问题。质疑模式，不要再修一次。 |

## 速查

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么、为什么 |
| **2. 模式** | 找到能工作的例子、对照 | 找出差异 |
| **3. 假设** | 形成理论、做最小检验 | 假设被证实，或形成新假设 |
| **4. 实施** | 编写测试、修复、验证 | bug 已解决，测试通过 |

## 当流程得出「没有根因」时

如果系统化调查表明问题确实是环境性的、依赖时序的，或来自外部：

1. 你已经走完流程
2. 记录你调查过什么
3. 实施恰当的处理（重试、超时、错误信息）
4. 加上监控/日志，便于以后调查

**但是：** 95% 的「没有根因」其实是调查不完整。

## 配套技术

这些技术属于系统化调试，就在本目录中：

- **`root-cause-tracing.md`** - 沿调用栈反向追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** - 找到根因之后，在多层加上校验
- **`condition-based-waiting.md`** - 用条件轮询替换任意超时

**相关技能：**
- **tdd** - 用于编写失败测试用例（阶段 4，第 1 步）
- **principle-prove-it-works** - 在宣称成功之前，对照真实结果验证修复确实有效

## 实际效果

来自调试会话：
- 系统化方法：15–30 分钟修好
- 随意修复：乱撞 2–3 小时
- 一次修好的比例：95% 对 40%
- 引入的新 bug：接近于零 对 很常见
