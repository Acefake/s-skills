# 创建日志：系统化调试技能

抽取、结构化并加固一项关键技能的参考示例。

## 源材料

调试框架抽取自 `~/.claude/CLAUDE.md`：
- 四阶段系统化流程（调查 → 模式分析 → 假设 → 实施）
- 核心要求：始终找到根因，绝不只修症状
- 规则设计用来抵抗时间压力和合理化借口

## 抽取决策

**要包含的：**
- 带全部规则的完整四阶段框架
- 反捷径（"NEVER fix symptom"、"STOP and re-analyze"）
- 抗压措辞（"even if faster"、"even if I seem in a hurry"）
- 每个阶段的具体步骤

**要排除的：**
- 项目特有的上下文
- 同一规则的重复变体
- 叙述性解释（压缩成原则）

## 遵循 skill-creation/SKILL.md 的结构

1. **丰富的 when_to_use** - 包含症状与反模式
2. **类型：technique** - 带步骤的具体流程
3. **关键词** - "root cause"、"symptom"、"workaround"、"debugging"、"investigation"
4. **流程图** - 「修复失败」的决策点 → 重新分析，还是再加修复
5. **逐阶段拆解** - 便于扫读的清单格式
6. **反模式一节** - 不该做什么（对本技能至关重要）

## 加固要素

框架设计用来在压力下抵抗合理化：

### 用词选择
- 用 "ALWAYS" / "NEVER"，不用 "should" / "try to"
- "even if faster" / "even if I seem in a hurry"
- "STOP and re-analyze"（明确的停顿）
- "Don't skip past"（抓住实际会做出的行为）

### 结构防线
- **必须先做阶段 1** - 不能跳到实施
- **单一假设规则** - 迫使思考，防止散弹式修复
- **明确的失败模式** - 「如果第一次修复无效」并附带强制动作
- **反模式一节** - 准确展示捷径长什么样

### 冗余
- 根因要求出现在概述 + when_to_use + 阶段 1 + 实施规则中
- 「绝不只修症状」在不同上下文中出现 4 次
- 每个阶段都有明确的「不要跳过」指引

## 测试方法

按照 skills/meta/testing-skills-with-subagents 创建了 4 项验证测试：

### 测试 1：学术情境（无压力）
- 简单 bug，没有时间压力
- **结果：** 完全遵从，调查完整

### 测试 2：时间压力 + 明显的快速修复
- 用户「很赶」，修症状看起来很容易
- **结果：** 抵抗了捷径，走完完整流程，找到真正根因

### 测试 3：复杂系统 + 不确定
- 多层失败，不清楚能否找到根因
- **结果：** 系统化调查，逐层追踪，找到源头

### 测试 4：第一次修复失败
- 假设不成立，想再加更多修复
- **结果：** 停下，重新分析，形成新假设（没有散弹式修复）

**全部测试通过。** 没有发现合理化借口。

## 迭代

### 初始版本
- 完整的四阶段框架
- 反模式一节
- 「修复失败」决策的流程图

### 增强 1：TDD 引用

## 最终结果

加固后的技能能够：
- ✅ 明确要求根因调查
- ✅ 抵抗时间压力下的合理化
- ✅ 为每个阶段提供具体步骤
- ✅ 明确展示反模式
- ✅ 在多种压力情境下测试过
- ✅ 说清与 TDD 的关系
- ✅ 可以投入使用

## 关键洞察

**最重要的加固：** 反模式一节展示那些当下觉得合理的精确捷径。当 Claude 想「我就再加这一处快速修复」时，看到这个模式被明确列为错误，会产生认知摩擦。

## 使用示例

遇到 bug 时：
1. 加载技能：skills/debugging/systematic-debugging
2. 读概述（10 秒）——想起这条要求
3. 遵循阶段 1 清单——被迫调查
4. 如果想跳过——看到反模式，停下
5. 完成所有阶段——找到根因

**时间投入：** 5–10 分钟
**省下的时间：** 少花数小时打地鼠式地修症状
