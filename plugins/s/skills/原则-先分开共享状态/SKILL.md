# 先分开，再考虑让共享状态串行

当并发的参与者可能共享可变状态时，先问它们是否真的需要同一个可变对象。如果不需要，就消除共享。当共享是真实需要的，就用结构化的方式强制串行：锁文件、按顺序的阶段、独占的归属。指示和约定都不算并发控制。

**为什么：** 对共享状态的并发写入会造成竞态条件，这种问题时有时无、很难复现，调试起来代价很高。

**做法：**
1. **找出共享的可变状态**（两方都读也都写的文件、两方都推送的分支、两方都定义也都使用的 API）。
2. **默认做法：消除共享的写入目标。** 问一句：这些参与者需要的是一个唯一的规范对象，还是只是在各自发布独立的事实？给每个参与者一个它自己拥有的文件、键、分支或状态目录，只在读取/汇报的边界上合并。两个 worker 各自往同一个 `state.json` 里写自己的 `lastX` 字段，仍然是共享修改。`indexer-state.json` + `metrics-state.json` 就不是。
3. **只有当“一个共享的写入目标”是真正必须的不变量时，才用结构化的方式串行访问**（锁文件、按顺序的阶段、单一写入者，或原子的比较并交换）。把“我们需要一把锁”当作需要检查的设计异味，而不是默认答案。
