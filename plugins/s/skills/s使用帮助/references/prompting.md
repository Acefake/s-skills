# 斟酌提示词

一条提示词说明意图和“完成”的检查标准。步骤由 playbook 提供，所以几句平实的话胜过一份规格说明。

## 要写进去的

- 目标。说清楚哪里有问题，或者用户想要什么。
- 完成的检查。它能判定通过或失败。“让它更好”和一段时长都不算检查。
- 要展示的证明。要求看真实的命令输出、一段流程的视频、存储的值，或者前后对比的数字。
- 用户已经知道的东西。一个症状、一个复现步骤、一段日志或一个链接，能省掉智能体一次搜索。
- 真实的约束。“repro first”（先复现）、“don't change any code yet”（先别改任何代码）、“zero behavior change”（行为零改变）和 “let me review before proceeding”（继续之前让我先审查）都会改变智能体的做法。

## 不要写进去的

- 怎么做。说清楚要达成什么，给智能体留出找到更好办法的空间。
- 一串 skill 或步骤。手写的顺序会漏掉或打乱 playbook 本来会保留的步骤。只有在要推翻某一个选择时，才点名一个 skill。
- 用户自己对原因的猜测，在智能体复述问题之前先别说。说出来的猜测会让搜索范围变窄。

## 先加载上下文

- 对于一份很乱的报告，让智能体在做任何其他事之前，先用自己的话、用平实的英文复述背后的问题。理解错了，在写任何代码之前就会暴露出来。
- 在一个新对话里，先用 `/回想最近工作` 回想这个话题以前的工作。旧的对话里有新智能体没有的上下文。
- 在修改不熟悉的代码之前，用 `/代码怎么工作` 问清机制，用 `/代码为什么这样` 问清原因。一个没有追踪出心智模型的智能体，会在第一个看起来说得通的地方修掉症状。
- 让 `/一步步教我` 为一个选择做论证，比如 “convince me it fixes the cause and not the symptom”（说服我它修的是原因而不是症状）。一份论证比一份总结更容易检查。

## 先设计，再做计划

- 永远不要接受第一个设计。要几个方案的原型，界面类的要截图或视频，然后根据证据来挑。
- 让原型来回答还没解决的问题。不要对一份抽象的计划做对抗式审查，因为审查者会编出从来不会发生的风险。
- 对于一个共享的包或 API，先要 README 或教程，再倒推回代码。文档就成了智能体用来检查自己的目标。
- 只有在设计定下来之后，才要计划。计划的每一步都以一个检查结束。

## 跟进要简短

- 一旦对话里已经有了任务，“do it”（做吧）、“continue”（继续）和 “keep going until done”（一直做到完成）本身就是完整的提示词。
- 换话题时，以 “new task”（新任务）开头。否则模式会把这条消息当成下一步。

## 离开之前

- 说 “im going to bed”（我去睡了）或 “im stepping away”（我先离开一下），让智能体不再发问。
- 把“完成”写成每次迭代都能运行的检查。Cursor 可以把这个判断条件交给 `/loop`。别的软件没有这个命令时，用后台盯梢的子智能体，或自己过一会儿再看。
- 要求从一个指定的基础分支开一个新的 worktree。
- 提前回答智能体可能会停下来问的事情，比如 “don't ask me before committing”（提交之前不用问我）。
- 要求记一份决定日志，供以后审查。
- 给一个出口：“if you're truly stuck after a few hours, stop and write up why”（如果几个小时后真的卡住了，就停下来写清楚原因）。

## 一句话引导

- 重申目标：“i said the goal is to repro. i did not ask for a fix yet.”（我说了目标是复现。我还没让你修。）
- 点名原则：“apply prove it works. show me the real output, not the build log.”（应用“证明它真的能用”。给我看真实的输出，而不是构建日志。）
- 点名原则之所以管用，是因为智能体已经读过这条规则。它的回复会说出这条规则改变了哪个决定。
