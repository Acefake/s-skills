# 回想

**在你开始或继续工作之前，你要重建用户最近的工作上下文，并交回一个紧凑的小结：现在情况怎么样，下一步做什么。**

保持紧凑、不跑题。只读范围内的线索需要的东西，然后停下。

你的上下文存在两份记录里。你自己的聊天记录里，是你做过什么、决定过什么。共享记录里，是同一份代码周围以其他名义发生的一切：用户一直在报告的症状、上线后又被回滚的修复、生产环境里还在不断报的错误。第二份记录就是 **代码为什么这样** skill 去搜索的东西，范围包括版本控制、问题跟踪系统、聊天和问题频道、长篇文档和错误跟踪系统。一个有一长串 bug 尾巴的功能，大部分故事都在那里，所以不要只靠你的对话记录来重建它。

对话记录存放在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是工作区路径去掉开头的斜杠、并把每个 “/” 换成 “-” 得到的（所以 `/Users/you/proj` 会变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再分流。要接着某一次具体的以前的对话，是 `session-pickup` playbook 的事，不是这个。把习惯变成一个持久的 skill，是 `按我习惯定制` 的事。给人看的工作总结是另一项任务。回想是在你行动之前，把最近多次对话里的工作上下文加载进来。如果用户已经给了你一份完整的状态小结（路径、分支、改动），就直接用它，跳过挖掘。
2. 搜索之前先锁定范围。定下时间窗口（“最近”是一个真实的范围，默认最近 7 天）、话题（如果有点名的话），以及工作区（默认当前这个。没人要求的话，永远不要读别的项目的对话记录）。把范围复述一遍。永远不要悄悄把“全部”变成“最近 N 个”。
3. 在你的聊天记录上分派任务。在一个快速、便宜的模型上派出并行的子智能体，每个负责语料的一片。告诉每个子智能体：按真实的修改时间（`ls -t`）给候选排序，永远不要按 UUID 名字排序；先 grep 话题，然后只读匹配的对话，而且只读其中相关的部分；跳过当前这次对话以及明显的噪声（子智能体、评估和测试用的对话）。每个子智能体都按同样的格式返回，每次对话一块：话题、用户的目标、决定、未完成的线索、遇到的困难和纠正，以及产物（PR、工单、分支），每一项都引用对话的 UUID。如果只有一两次对话，就跳过分派，直接搜索。原始的对话记录留在子智能体那里。主线程只拿到它们的发现。按 **poteto工作模式** skill 里 “Subagents” 一节的规定，为每个子智能体的任务选择推理等级，以及快速还是标准速度。
4. 只要话题点名了某个功能、文件、子系统、领域或 bug，就扫一遍共享记录。这是默认动作，不需要判断，“我在 X 上的工作”也不能免掉它。把它交给 **代码为什么这样** skill 的各个来源调查者，但把它们的问题从“这为什么要这样构建”改成“现在的状态是什么，试过什么却没奏效，用户还在报告什么”。复用它针对每个来源的操作手册，让调查者和聊天记录挖掘并行运行，并沿用它的做法：每个来源一个调查者；没找到结果也算发现；某个 MCP 不可用就跳过并说明。把返回的内容并入简报。只有在纯粹回想活动、没有点名任何目标时（“我这周做了什么”），才跳过这一步，因为那时你自己的记录和实时状态就是全部答案。
5. 对照实时状态验证。把挖掘和扫描中出现的 PR、分支和工单拿出来，用 `git` 和 `gh` 检查。当答案取决于某个智能体实际做了什么（它运行的工具、读过的文件、遇到的错误）时，读完整的对话记录，而不只是一份删减过的本地副本。
6. 按下面的约定写简报。按线索分组。紧扣点名的话题。

## 输出约定

先写小结，然后是各条线索的状态，然后是问题，最后是下一步。更深的细节放在下面，或者删掉。

- **小结。** 最多 5 条。这项工作是什么，整体进展到哪里了。
- **线索。** 每条一行，前面加上恰好一个状态标签：`[merged #N]`（已合并）、`[open PR #N]`（PR 未合并）、`[in flight <branch>]`（正在进行）、`[verified, uncommitted]`（已验证、未提交）、`[reverted #N]`（已回滚）或 `[planned, not started]`（已计划、未开始）。没有标签的线索就是还没写完，所以要给它加上标签。
- **问题。** 最多 5 个，挑反复出现的。包括用户一直在报告的症状，以及上线后又被回滚的修复，让下一次尝试从上一次失败的地方开始。
- **下一步。** 唯一一个最有用的下一个动作，要具体。

相邻的功能或工单不要写进来，除非它卡住了这一个。当小结和线索行超过一屏时，先删细节，再删线索。用 **清理AI腔** skill 过一遍简报的文字，聊天记录里的发现用 UUID 引用，共享记录里的发现用它的来源引用（PR 编号、工单 ID、聊天永久链接、错误跟踪系统里的问题），在任何公开输出之前把私密的上下文清理掉。

**回复：** 按上面的约定写的简报。

## 在不同软件里怎么用

第 3 步的挖掘子智能体用较快、较便宜的写代码模型，并行，只读。第 4 步的来源调查沿用 [代码为什么这样](../代码为什么这样/SKILL.md) 文末的派法。

Cursor：每个切片一个 `Task`，`subagent_type: generalPurpose`，`readonly: true`，`model` 用 `how explorer` 那一档。没有配置、并且 `grok-4.7-xhigh-fast` 这次可用时，用这个名字。

OpenCode：每个切片一次 `subagent`，`background: true`，用 `s-how-explorer` 或内置 `explore`。Codex：提示词里 “Spawn one subagent per slice, use the fast model \<名字\>, wait for all”。模型名用这次账号里真有的，文档举例 `gpt-6-luna` 只在账号有它时才用。

WorkBuddy 用 `Explore`，能选的话用 `"lite"`。Claude Code 用 `Explore`，`model` 用 `haiku` 或 `sonnet`。只有一两次对话时不派，这和第 3 步一样。
