# 主审判断框架

## 过滤原则

### 吹毛求疵的引力

审查者，尤其是对抗式的审查者，倾向于把审查写满。如果找不到严重问题，他们就会把小毛病夸大来填满篇幅。如果一个审查者的发现全是小毛病和风格偏好，代码多半没问题。直接这么说。

### 假设的 vs. 实际的

“如果有人在这里传了 null 怎么办？”只有当调用方真的能传 null 时，才算一条发现。追踪调用处。如果输入在上游已经校验过，或者类型系统阻止了它，就驳回这条发现。看着 diff 做审查的人不一定总能看到完整的调用链。你能。

### 关于过早抽象的提醒

审查者常常建议抽出函数、加接口或创建抽象。这段代码需要以第二种方式变化吗？如果不需要，这个抽象就是过早的。能用的简单内联代码，胜过一个对当前范围来说大材小用的干净抽象。

### “换我会用别的做法”

这是代码审查里最常见的误报。一条实际上等于“我更喜欢另一种做法”的发现，不是 bug，不是设计缺陷，也不需要行动，除非审查者指出了当前做法的一个具体问题。驳回这类发现，并说明理由。

### 缺少背景的信号

注意那些暴露出审查者没理解背景的发现：
- 建议修改作者没写过、也没改过的代码
- 指出的写法其实和代码库其他地方一致（只是审查者不知道）
- 推荐的做法和你知道的约束冲突

这些是信息有限的审查者犯的诚实错误。客气地驳回它们。

## 审查者说对了的时候

不要只因为一条发现让人不舒服就驳回它。对抗式审查的意义，就是抓住你会漏掉的东西。一条发现值得重视的迹象：

- 多个模型独立地指出了同一个问题（共识信号）
- 这条发现指出了一条具体的执行路径，而不是一个假设
- 这条发现暴露了你对代码的心智模型里的一个漏洞
- 你读完这条发现，心想“……嗯，确实是”

驳回安全方面的发现和正确性 bug 时要格外小心。即使只有一个模型提出，它们也值得更仔细地审视。
