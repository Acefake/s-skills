# 代码质量审查

每个审查者除了评审标准之外，还要用上这个代码质量视角。这是一个严格的标准，关注的是实现质量、可维护性、抽象质量和代码库的健康。

最重要的是，对代码结构要有野心。不要只是找出局部的清理。要主动寻找“代码柔道”式的招数：在保持行为不变的前提下做重构，让实现变得简单得多、小得多、直接得多、优雅得多。

## 核心提示词

从这个基准开始（引用块里的英文提示词保持原样，后面附中文意思）：

> Perform a deep code quality audit of the current branch's changes.
> Rethink how to structure / implement the changes to meaningfully improve code quality without impacting behavior.
> Work to improve abstractions, modularity, reduce Spaghetti code, improve succinctness and legibility.
> Be ambitious, if there is a clear path to improving the implementation that involves restructuring some of the codebase, go for it.
> Be extremely thorough and rigorous. Measure twice, cut once.

（意思：对当前分支的改动做一次深入的代码质量审计。重新思考这些改动该怎样组织和实现，在不影响行为的前提下切实提升代码质量。努力改进抽象和模块化，减少面条式代码，让代码更简洁、更易读。要有野心：如果有一条清晰的路径能改进实现，哪怕需要重构一部分代码库，也去做。要极其彻底和严谨。量两次，再下刀。）

## 各个维度

每个维度只说一次。用上相关的那些。

0. **在结构简化上要有野心。** 不要停留在“这里可以再整洁一点”。寻找能让整个分支、辅助函数、模式、条件判断或层消失的重新组织方式。假设“代码柔道”式的招数常常是存在的。它更有效地利用现有架构，让改动简单得多。如果你能删掉复杂度，而不只是重新摆放它，就使劲争取删掉。

1. **除非有非常充分的理由，不要让一个 PR 把一个文件从不到 1000 行推到超过 1000 行。** 把这当作一个强烈的坏味道。优先抽出辅助函数、子组件或模块。如果 diff 跨过了这个门槛，就问一问代码是不是应该先拆分。只有在有令人信服的结构性理由、而且结果文件仍然组织得很清楚时，才放行。

2. **不要让已有代码长成一团面条。** 对新加的临时条件判断、四处散落的特殊情况、插进不相关流程里的一次性分支，要保持怀疑。把“随处乱放的古怪 if 语句”当作设计问题，而不是风格上的小毛病。优先把逻辑放进一个专门的辅助函数、状态机或模块里，而不是把一条已有路径缠成一团。

3. **倾向于把设计清理干净，而不只是接受能用的代码。** 如果行为可以保持不变，而结构能变得明显更干净，就争取那个更干净的版本。优先选择去掉活动部件的简化，而不是把同样的复杂度挪来挪去的重构。

4. **优先选直接、平淡、好维护的代码，而不是取巧或带“魔法”的代码。** 把脆弱的、临时拼凑的或“魔法般”的行为当作问题。对那些藏着简单数据形状假设的通用机制保持怀疑。指出那些增加了间接层、却没换来清晰度的薄抽象、原样返回的包装和转手的辅助函数。

5. **当类型和边界的整洁影响可维护性时，要坚持要求。** 如果本可以有一个更清楚的类型边界，就质疑不必要的可选性、`unknown`、`any` 或满是类型断言的代码。优先用明确的有类型模型，而不是形状松散的临时对象。如果某个分支靠一个悄悄的回退来掩盖一个不清楚的不变量，就问一问这个边界是不是应该明确下来。

6. **把逻辑放在规范的那一层，复用已有的辅助函数。** 指出功能逻辑渗进共享路径，或者实现细节通过 API 泄露出去的情况。优先用已有的规范工具函数，而不是量身定做的一次性代码。把代码推向正确的包、服务或模块，而不是让偏移变成常态。

7. **当更干净的结构显而易见时，把不必要的顺序编排和非原子的更新当作设计坏味道。** 如果独立的工作无缘无故地被串行执行，就问一问它们是不是应该并行。如果相关的更新可能让状态只应用了一半，就争取一个更原子化的结构。不要过分纠结微观优化，但要指出那些可以避免、又会让代码更脆弱的编排复杂度。

## 输出期望

先列结构上的代码质量退化和错过的简化，然后是面条式代码和分支复杂度，然后是边界、类型和文件大小方面的问题，最后是较小的模块化和可读性问题。

## 批准门槛

不要只因为行为看起来正确就批准。除非作者能给出正当理由，否则把下面这些都当作默认的阻碍：一个“代码柔道”式的招数本可以删掉大量附带的复杂度，PR 却保留了它们。把一个文件从不到 1000 行推到超过 1000 行。加了把已有流程缠在一起的临时分支。把功能检查散落在共享代码里。加了不必要的抽象、包装或满是类型断言的约定，或者重复了一个已有的辅助函数，或者在有明确规范归宿的情况下把逻辑放错了层。如果不满足这些条件，就留下明确的、可操作的反馈，并争取一个更干净的拆分。

## 审查语气

对质量要直接、严肃、要求高。不要无礼，但也不要把重大的可维护性问题软化成温和的建议。如果代码正在让代码库变得更乱，就直说。如果实现错过了一个明显的大幅简化，也要直说。当真正的问题是结构性的时候，不要满足于“也许把这个改个名”。
