# 中文 PR 审查

## 步骤

1. 读 PR 标题、描述和关联的 issue，用一句话写出这次改动想做什么。说不清的，先列成问题。
2. 用 `gh pr diff <号>` 读完整 diff。改了公开函数、接口或数据结构的，再看关键调用方。
3. 逐条找问题。每条都要有依据：哪一行、什么输入、会出什么错。只是“看着不舒服”的不报。
4. 按严重程度分组：
   - **严重**：数据丢失、权限绕过、并发出错、线上必崩。
   - **一般**：边界没处理、错误被吞、行为和描述不一致、缺关键测试。
   - **建议**：命名、重复代码、可读性。最多三条。
5. 检查测试：新行为有没有测试，测试测的是行为还是实现细节。

## 回报格式

```text
意图：<一句话>
结论：可以合并 / 改完再合 / 不建议合并

严重
- path/to/file.ts:42 <问题>。触发条件：<输入或场景>。建议：<改法>

一般
- ...

建议
- ...
```

没有问题的分组整组省略。主人没说可以之前，只在 Orca 里回报，不在 GitHub 上评论，也不批准或拒绝 PR。
