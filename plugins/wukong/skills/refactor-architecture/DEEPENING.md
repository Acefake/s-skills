# 加深

在给定依赖的情况下，怎样安全地把一簇浅模块加深。词汇见 [VOCABULARY.md](VOCABULARY.md)：**模块**、**接口**、**接缝**、**适配器**。

## 依赖分类

先说明候选模块共享哪项领域知识、现有耦合造成什么问题，以及合并是否减少协调和理解负担。职责独立或收益不明确时保留边界。确认合并有价值后，再按依赖分类选择验证方式；依赖类别和测试替身的存在都不是合并的理由。

### 1. 进程内

纯计算、内存状态、没有 I/O。若合并已通过职责与收益判断，可直接通过新接口验证行为，通常不需要适配器。没有 I/O 不代表不同职责应该合并。

### 2. 可本地替代

有可供本地验证的依赖环境或测试替身，例如数据库容器、兼容实现或内存文件系统。合并有价值时，可通过新接口带着它们验证相关行为，并核对与真实依赖的差异。是否暴露依赖接口由实际职责决定，不由测试替身决定。

### 3. 远程但自有（端口与适配器）

你自己的、隔着网络的服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深模块拥有逻辑，传输作为**适配器**注入。测试用内存适配器，生产用 HTTP/gRPC/消息队列适配器。

建议写法：_「在接缝处定义端口，生产用 HTTP 适配器、测试用内存适配器，这样即使部署跨网络，逻辑也在一个深模块里。」_

### 4. 真正的外部服务（Mock）

你控制不了的第三方服务（Stripe、Twilio 等）。加深后的模块把外部依赖作为注入的端口接收，测试提供 mock 适配器。

## 接缝纪律

- **按职责设置接缝。** 协议适配、副作用隔离或独立业务约定可以支持一个接缝，即使目前只有一个适配器。第二个实现只是证据之一，不是门槛；也不要为凑数量制造测试适配器。没有独立职责的转手层才应合并。
- **内部接缝和外部接缝。** 深模块可以有内部接缝（实现私有，给自己的测试用），也有接口处的外部接缝。不要因为测试用到内部接缝，就把它暴露到接口上。

## 测试策略：替换，不要叠加

- 删除旧测试前，把它们覆盖的正常行为、边界条件、错误路径和历史回归映射到新测试。新接口存在测试不代表覆盖已经迁移。
- 只删除已被等效覆盖的重复测试，或重写仅绑定旧实现细节的测试。尚未迁移的有效行为检查继续保留或先迁移，不能按模块层级批量删除。
- 新测试写在加深后模块的接口上。**接口就是测试面**。
- 测试通过接口断言可观察的结果，不断言内部状态。
- 测试应当扛得住内部重构，因为它描述的是行为不是实现。实现一改测试就得改，说明它测过了接口。
