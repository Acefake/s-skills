# 提示词优化

把含糊的需求变成能直接执行的请求：先研究项目，再问只有用户能答的问题，最后带着研究结果和答案去做。

本技能的流程和问题写法改写自 [severity1/claude-code-prompt-improver](https://github.com/severity1/claude-code-prompt-improver)（MIT，见 [LICENSE-prompt-improver](../../LICENSE-prompt-improver)）。由你点名，或模型判断需求确实含糊时加载。原项目靠钩子对每条提示词做判断；本库随插件带一个同源的钩子：Claude Code 默认开启，Codex 需手动配置，细节和跳过方法见[钩子](references/hook.md)；其他宿主靠点名或描述触发。

## 什么时候用

- 用户点名时加载；未点名时，目标、作用对象、范围、约束或验收有会明显影响结果的缺口，且对话无法补足时加载。
- 存在多个合理解释且会改变实现方向、修改范围或验收结果时，先加载再研究项目；不把“读代码也定不下来”作为加载前提。
- 需求已有足够信息时直接做。没有文件名、提示词短不等于含糊；有动作、有文件名或是讨论也不保证没有关键缺口。
- 以 `*` 开头、斜杠命令、`#` 开头的记忆指令、「可以」「继续」这类确认和 4 个字以内的消息：不介入。
- bug、报错、测试失败：走 [systematic-debugging](../systematic-debugging/SKILL.md)，先查根因，读代码能定位的不提问。
- 新功能或要改行为：设计问题交给 [brainstorming](../brainstorming/SKILL.md)，不在这里设计。

用不用本技能的判断，先看对话里已有的信息：最近的报错、提到的文件、刚做的决定、用户正在看的文件。这些足够时，就等于需求已清楚。

加载不等于必须提问。研究能确定的自行补齐；常规实现选择按项目惯例处理，合理假设简述即可。普通事实问答、明确的只读诊断、有上下文的“改吧”“测试一下”不因信息不完整强行介入。只问无法从证据确认、又确实影响结果且必须用户决定的问题。bug 与新功能分别由对应流程主导，已在那里确认的信息直接复用，不重复问。

## 流程

### 1. 研究

动手提问之前先研究，不能跳过。

1. **先看对话历史。** 已有上下文就不要重复探索。
2. **读项目记录。** 有 [project-memory](../project-memory/SKILL.md) 产出的 `docs/project/`，或 `CLAUDE.md`、`AGENTS.md`、README，先读这些。够用就不再扫代码。
3. **补缺口。** 只对还没答案的缺口做定向检索：目标文件、已有写法、相关测试、近期提交、TODO 和失败的测试。
4. **必要时查外部资料。** 本地文档、官方文档、最佳实践。
5. **记下发现。** 后面的每个问题都要能指到一条发现。

规则：

- 问题必须来自研究，不能来自猜测或常识。
- 简单缺口自己读。要读很多文件、跨多个目录时，按[公共派发规则](../wukong-mode/references/subagents.md)派只读检索子智能体，角色读 s 模型配置里的「检索与探索」。
- 派子智能体时，把对话里已有的文件路径、报错、已做的决定写进它的提示词；它看不到前面的对话。
- 派不出子智能体时，主对话里自己读，并说一句没有换模型。

具体做法见[研究方法](references/research-strategies.md)。

### 2. 生成问题

根据研究结果，列出 1 到 6 个能消除含糊的问题。

- **有依据**：每个选项都来自研究（代码、文档、已有写法）。
- **具体**：不要「其他方案」这类空选项。
- **选择题**：每题 2 到 4 个具体选项。
- **一题一个决策点**：不要把「改哪个文件」和「怎么改」放进同一题。
- **说清取舍**：每个选项带一句影响或代价。

数量：

| 数量 | 场景 |
| --- | --- |
| 1–2 个 | 简单含糊（改哪个文件？用哪种做法？） |
| 3–4 个 | 中等复杂（范围、做法、验证） |
| 5–6 个 | 大功能，有多个决策点；先考虑转 brainstorming |

模板、写法和常见错误见[提问写法](references/question-patterns.md)。

### 3. 取得澄清

用当前宿主的提问工具（见[宿主适配](../../HOSTS.md)「向用户提问的工具」）提问，没有就在对话里列选项。

- 能从研究里定下来的，不问：直接用，并在改写稿里标成「假设」。
- 只问研究定不下来、必须用户拍板的。
- 用户总能选「其他」自由作答。

### 4. 带着上下文执行

产出一份可直接执行的提示词，固定包含：

- 目标
- 涉及的文件和模块
- 必须遵守的规范（引用记录里的条目）
- 验收标准
- 明确不做什么
- 假设（来自研究、未经用户确认的部分）

然后按它执行，就像需求一开始就是清楚的。用户说「只要提示词」就停在产出，不执行。

示例见[示例](references/examples.md)。

## 原则

1. **先研究**：先收集上下文，再提问。
2. **有依据**：用研究结果，不用猜测。
3. **要具体**：选项来自真实的代码和文档。
4. **收得住**：最多 6 个问题，每个只管一个决策点。
5. **只读**：研究阶段不改文件、不跑会改状态的命令。
