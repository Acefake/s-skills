# 研究方法

在提问之前收集项目上下文的做法。改写自 severity1/claude-code-prompt-improver 的 research-strategies（MIT）。

## 目录

- 先找出缺什么
- 写研究计划
- 代码库
- 文档
- 外部资料
- 对话历史
- 选工具

## 先找出缺什么

研究前先说清缺口属于哪一类：

| 缺口 | 要回答的问题 |
| --- | --- |
| 目标 | 改哪个文件、函数、组件？ |
| 做法 | 怎么实现？用哪种模式？ |
| 范围 | 改多少？这次请求包含什么？ |
| 现状 | 现在是什么样？已有哪些写法？ |

## 写研究计划

动手前列 3 到 5 步，每步写「查什么 + 用什么查」。例：

```
研究计划（「把 bug 修了」）：
1. 对话里的报错信息 — 回看最近的消息
2. 失败的测试 — 搜 failing、error、TODO
3. 近期提交里有问题的区域 — git log
4. 相似代码的写法 — 读相关文件
```

做完后写下发现：涉及的关键文件、已有写法、项目里常见的做法、需要遵守的约束。

## 代码库

| 目的 | 做法 |
| --- | --- |
| 摸结构、找相似实现 | 派只读检索子智能体，或自己顺着入口文件读 |
| 找文件 | 按名字模式找，例如 `**/*auth*.ts`、`**/*.test.ts`、配置文件 |
| 找代码模式 | 按内容搜，例如 `TODO\|FIXME`、`try.*catch`、具体函数名 |
| 看架构 | 先入口（`index`、`main`、`app`），再 `package.json`、`tsconfig.json`，再目录结构和 README |
| 看历史 | `git log --oneline -20`、`git log --grep=关键词`、`git log -S 函数名`、`git diff HEAD~5..HEAD --stat` |

例：「加测试」→ 找 `**/*.test.ts`，发现测试与源码放在一起、用 Jest，那问题就是「放哪里」而不是「用什么框架」。

## 文档

本地文档按这个顺序读：

1. 项目根 README
2. `docs/project/`、`docs/`、架构文档
3. 各包的 README
4. CONTRIBUTING
5. API 文档

第三方库：读 `package.json` 里的版本，看本地示例，必要时查官方文档。

代码注释里常有约束，搜 `NOTE:`、`WARNING:`、`IMPORTANT:`、`FIXME:`。例：迁移文件里写着「不能改 user_id，外键依赖它」，那「改表结构」的问题里就得带上这条约束。

## 外部资料

只有项目里查不到、而决定又依赖它时才查：

- 当前的做法和行业标准：搜索时带上年份。
- 库的对比：例如 JWT 与会话、Joi 与 Zod。
- 框架官方文档：框架版本从 `package.json` 读，再查对应版本的文档。

外部结论只作为选项的依据，不替用户做决定。

## 对话历史

总是第一步。看这些：

- 最近消息里的报错
- 提到的文件名
- 讨论过的功能
- 已经做的决定
- 贴出或引用的代码

例：用户依次说了「`Cannot read property 'id' of undefined`」「点登录按钮时出现」「修一下」。从历史就能推出：未定义的属性访问，在登录按钮的处理函数里，这时通常不用再问。

## 选工具

| 要找的东西 | 用什么 |
| --- | --- |
| 不熟的区域、多处相关代码 | 检索子智能体 |
| 已知名字模式的文件 | 文件名搜索 |
| 代码里的关键词 | 内容搜索 |
| 已知文件 | 直接读 |
| 历史和最近改动 | git |
| 当前做法、版本变化 | 网络搜索 |

顺序：对话历史 → 项目记录 → 定向检索 → 外部资料。前一步够用就停。
