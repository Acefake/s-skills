# Architecture 布局修复

在实际视觉审查发现多条缠绕的路由之后使用本文。一个成功的机器回执并不能说明构图没问题。在已有候选稿上操作，保留所有必需的组件、关系、标签、证据、边界和节点尺寸。

## 选择修复范围

如果主链和次链已经清晰可读，就在局部修复孤立的缺陷。如果主链被阻挡、多条路由缠绕，或者局部修复把缺陷转移到了另一条路由上，就在一次编辑中重排相连的场景。保留所有语义和用户固定的几何；代理生成的位置和路由控制可以改变。移动节点后，移除过时的生成路由覆盖，让自动路由能利用新的布局。

回执中的 `directCorridorBlockers`（如果有）指出位于某条连线对齐端点之间的节点。这是几何证据，并不证明该连线是主路径，也不是新的校验失败。先追踪读者实际的主路径。当列出的阻挡节点打断了该路径时，重新放置相连的组，而不是再加一个绕行。

## 一次连贯的修复

1. 在 JSON 中追踪受影响的关系及其端点。在选择坐标之前，把读者的主路径写成由已有连线组成的有序列表，然后找出共享状态和真实的反馈环。主路径中每一对相邻节点之间都必须有被解释的那条关系；把其他组件放在其实际所有者旁边的分支上。如果紧凑回执和截图没有揭示所需的路由或标签几何，就运行一次 `validate architecture <candidate.json> --layout-json --repo-root <root>`；只有对没有仓库证据的设计才省略 `--repo-root`。不要猜测重复的途经点坐标。
2. 按阅读顺序放置这些相连的主路径邻居。把共享状态放在其读者/写入者之间，必要时放在相邻的行上，这样就不会有某个写入者需要一条横贯整个执行区域的线。按反馈环实际的连线顺序把它排成一个围绕空心矩形的环，其他消费者放在其所有者旁边。例如，如果连线是 `client → API → dispatcher → worker → collector → runner → dispatcher`，就把前四个放在上面一行，collector 放在 worker 下方，runner 放在 dispatcher 下方：回程就走下面一行，再加一条短的向上连线。这只是说明相邻关系，不是可照抄的图或坐标；只使用候选稿中存在的关系。保留每一条连线及其实际方向。
3. 对新布局保持自动端点。只有当某个分支或回程需要特定走廊时才约束一侧；对照每一条受影响的关系检查该走廊，包括存储分支。如果这个局部约束引入了另一个冲突，就回到相连布局，而不是在各种侧边组合之间来回尝试。只对剩余的经测量缺陷使用详细的 `via` 或标签坐标。把外部参与者放在解析后的边界矩形之外，包括其内边距；不把某个节点列入 `wraps` 并不会在视觉上把它排除在外。把内部关系及其标签保持在共享边界之内，除非跨越边界传达了一个真实事实；不要仅为避开另一条路由而暗示一次外部跳转。
4. 当 `composition/label-gap` 报告了一个测量出的最小值时，扩大那段净空，或把相连的组移到另一条可读的行上。让完整标签留在它自己的路由旁边；把它放到远处的空白区域并不能修复该关系。压缩未使用的空隙，同时保留测量出的标签空间和之前的文字大小。在默认桌面视图中保持主要交互和所有必需节点可读；不要用大片空白画布、极小的文字，或一条没有语义理由就折返的链来换取更少的交叉。

编辑后运行一次完整的 `finalize`，然后对成功的产物运行 `visual-check` 并检查其桌面截图。替换一个已审查过的产物时，按照 [the delivery contract](delivery-contract.md#a-new-candidate-at-an-existing-output-path) 中所述，为两条命令使用同一个全新的 `--out-dir`。追踪主路径、每条次链，以及每个受影响的箭头和标签。可以进行一次有界的第二轮修复，处理剩余的具体缺陷。如果仍未通过视觉验收，保留候选稿并报告具体差距；不要把它算作成功修复，也不要继续盲目地修改坐标。
