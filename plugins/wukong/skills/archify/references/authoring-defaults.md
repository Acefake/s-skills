# 编写默认值

在编写全新候选稿之前通读一遍。已冻结的现有候选稿若直接进入 `finalize`，只有在修复改变了其编写内容时才需要阅读本文。

## 构图与含义 <a id="composition-and-meaning"></a>

对于 Architecture，默认画一张以主要用户旅程为主线的系统概览，除非用户要求更窄的机制、模块地图或部署拓扑。若分组后仍能讲清所要求的交互，就把协作的角色归入命名准确的子系统。若分组会掩盖控制归属、信任或持久化边界、生命周期行为，或读者询问的其他区别，就把这些角色分开。次要功能和需主动开启的功能放在简洁且注明来源的注释中，除非它们的路径与所问问题相关。若刻意收窄了范围，必须在标题中写明。

保留每一项所要求的职责、关系方向、协议以及会改变行为的条件。审批、授权和状态迁移的门槛要标在受影响的节点或关系上；仅靠一张卡片无法为一条原本无条件的箭头加上限定。每个断言都要附带其来源证据。边界表达真实的隔离、归属、运行时或持久化事实。卡片回答读者的额外问题；它们不能替代必需的拓扑。节点、连线、来源、卡片或边界都没有数量配额。若已编写的概览在失败后需要重新分组，使用 [构图修复](authoring-contract.md#composition-repair)；用户提供或已商定的拓扑保持不变。

关系标签承载含义。给它们留出清晰的空间，并保留动作、协议、方向、异步行为或跨边界的含义。在模式 schema 允许省略标签的地方，只有当两个端点已完全隐含该标签时才可省略；发生碰撞时应通过调整间距或路由来修复。当实测证据报告碰撞时，参见 [标签修复](authoring-contract.md#label-repair)。

## 布局与路由 <a id="layout-and-routing"></a>

在分配坐标之前，先按 Architecture 节点的实际连接来摆放它们；路由器无法重新排列方框，所以摆放决定了线条能否保持笔直。先给每条关系分类，再摆放：

- **主路径**：读者的主要旅程，相邻节点按阅读顺序紧挨着。让中等长度的路径跨越有意义的行逐步推进，而不是做成一条扁平的横向长条。
- **分支或存储**：放在拥有、读取或写入它的节点的正上方或正下方，并以该节点为中心对齐，使连线成为一条直线段。同一行的所有存储和分支都放在该行的同一侧。
- **返回**（回到主路径上更早的节点）：把它的源节点放在主路径上没有分支或存储的那一侧，使它穿过空走廊，而不是与它们交叉。
- **第二入口**（进入一个已有入边的节点）：放置新的源节点，使其从另一侧到达该节点，通常是正下方或正上方。
- **扇出**：有 k 条关系的一侧至少需要 `32 + 14 × (k − 1)`px（四条需要 74px）。把枢纽节点的对端分散到两到三侧，或放大枢纽节点。父节点以其子节点为中心居中，只有一个父节点的子节点与该父节点对齐。

写坐标之前，逐条追踪每条非主路径关系：它的直线或单折走廊绝不能穿过其他节点或与其他关系交叉。若会穿过或交叉，就移动不在主路径上的那个端点。主角色及其第一个相连步骤一起从画布原点附近开始（约 `[40, 40]`，而不是 `[200, 200]`）；用内容行形成纵向节奏。原点过高留下的顶部/左侧空白会浪费画布、降低填充率，且不会提升可读性。全新 Architecture 省略 `meta.viewBox`，让 Reader 测量内在高度。提供的固定几何始终以其为准。

先使用自动路由和端点侧。只有在必要的分支、返回或提供的几何中才固定某一侧。对于全新 Architecture，若没有必需的侧约束阻止平行直线，相邻的请求/响应方向保持自动；保留提供的侧固定。`via`、`channelX`、`channelY` 和标签坐标只留给实测缺陷使用。写坐标之前，为每条位于并排方框之间的带标签连线（无论是否在主路径上）预留 `6.5px × ASCII units + 21px` 的净间隙，CJK 字符计为两个单位；按该连线自身的标签长度计算，而不是用整行固定的间隙。边界框是包住其所有成员并带内边距的方框：把成员摆成一个紧凑的轴对齐簇（不留可能让非成员落入带内边距框内的空位），并让每个非成员——尤其是外部角色——位于该框之外。Architecture 画布宽度保持在 1240px 以内，或在宽度至少为高度 1.55 倍时保持在 1790px 以内；超出后其 8px 的关系标签会低于桌面端下限。Architecture 副标签按其首选的 9px 文字以 `5.4px × text units + 8px` 计算尺寸，CJK 计为两倍；辅助文案保持简洁，但不得丢弃必需事实。不要为了减少交叉而牺牲可读性或含义。[几何参考](authoring-contract.md#executable-geometry-rules) 给出了针对已诊断布局问题的实测间距、端口、画布和路由规则。

## 证据与 schema

对于真实仓库，检查源码时遵循 [仓库编写](repository-authoring.md)。在 `meta.repository` 中冻结其不含凭据的 origin 和 40 字符的提交，给每个关键语义节点附上已检查的、相对于仓库的 `sources`，并在第一次 `finalize` 时传入 `--repo-root`。每个引用只证明该位置可见的事实。沿着重要的关系和条件追到它们实际的来源；不要把启动处的引用复用为协议或持久化证据。

示例只展示字段形态，不代表合法取值或来源事实。它们是完成的展示品，所以其中可选的展示字段（`meta.subtitle`、`meta.viewBox`、`meta.column_fit`、`via`、`labelAt`）不是默认值；以本文的默认值为准。在添加字段、枚举或受约束的文本之前，先阅读模式 schema 和共享定义。尤其要检查 Architecture 的边界类型。较长的证据放在卡片中，同时保留该事实。详见 [Schema 查阅](authoring-contract.md#schema-lookup)。

## 呈现与模式 <a id="presentation-and-modes"></a>

动画自动启用。省略 `meta.animation`；使用查看器的 Live/Still 按钮暂停或恢复播放。

根据用户的选择或请求/对话，使用一种主要编写语言。设置 `meta.locale`；`en`、`zh-CN`、`zh-TW`、`es`、`ko` 和 `ar` 会选用内置的查看器语言目录，无需其他操作。对于其他语言，提供带可复用 UI 译文的 `meta.translations`，或说明查看器的固定 UI 与 `<html lang>` 会回退为英文。保留产品、代码、协议、命令、API 和环境的确切名称，同时本地化周围的说明文字。双语情形参见 [语言一致性](authoring-contract.md#language-consistency)。

经典样式省略 `meta.visual_preset`，只要标题的页头省略 `meta.subtitle`，如实的自动图例省略 `meta.legend`，普通系统概览省略 `meta.engineering_profile`。显式样式和副标题都需要用户提出要求。按照 [图例](authoring-contract.md#legend-contract) 或 [工程配置](authoring-contract.md#engineering-profile-default) 契约使用图例或部署归属。品牌标识是可选的，在节点命名真实产品时需显式设置；[品牌标识](brand-marks.md) 给出该分支的查找与采集规则。绝不让徽标取代语义类型、标签或关系事实。将必需的 `meta.output` 设为工作目录内可移植的 POSIX 相对 `.html` 路径；原生路径的例外参见 [输出路径契约](delivery-contract.md#output-path-contracts)。

全新 Workflow 使用 schema v2 并省略 `meta.viewBox`，让编译器测量实际占用尺寸；不要为了满足视口比例而添加空画布。保留提供的固定几何和 v1 源。在未固定的草稿中省略节点 `width`：节点起始宽度为 92px，并随其标签、副标签和标记增长，最多到 200px。显式画布以及绝对路由或标签固定沿用以前的几何契约。泳道或分组几何需要细节时，使用其 [布局契约](../renderers/workflow/README.md#layout-contracts)。

全新 Sequence 省略 `meta.viewBox` 和 `meta.column_fit`：自动高度贴合时间线（没有 760px 下限），标签放得下时 2–3 个短标签参与者会收紧到 920px 以内，画布仍会为拥挤的标签加宽，直到其可读宽度；保留已编写的 `meta.viewBox`。需要历史固定坐标时显式设置 `meta.column_fit: "fixed"`；当宽 viewBox 留下未使用的横向空间，或有意义的标签需要宽度时，使用 `spread`。参与者的内部动作写成其所在的真实跨参与者消息上的注释，保留其含义和顺序；Sequence 不支持自消息循环。全新摆放时，在放置下一条消息之前为该注释预留纵向空间：28px 是无注释消息的基本间距，不是注释的预算。注释向其消息下方延伸；在共用该空间的下一条消息之前，渲染一行至少留 44px，两行留 55px，三行留 66px（例如，y=200 处的三行注释要求下一条消息位于 y=266 或更靠后）。换行取决于最终泳道宽度，所以较长的注释要留更多空间，并保留每条注释的含义而不是删掉它。这些间隙并不保证与分段标题、其他注释或激活条之间有足够间距。提供的固定 y 值始终以其为准；在代理编写的全新草稿中，按需一并调整后续消息、分段边界和激活边界，保留顺序和含义，并在这些约束内使用 `sequence/note-overlap` 证据进行修复。

全新 Dataflow 从 2 到 5 个阶段、行 0 到 4 的阶段/行网格开始，并遵循规范的 [Dataflow 画布与展示默认值](authoring-contract.md#dataflow)。相邻阶段中心相距 215px，默认节点宽 112px，两者之间约留 100px，所以流标签保持在约 17 个文本单位以内（CJK 计为两个），更多细节移到卡片中；针对提供的几何或实测约束，再添加尺寸或路由控制。

对于 Dataflow 血缘，从每个所要求的输出反向追溯到其生产者实际消费的值。把原始载荷与派生配置组合起来的转换，要为每一项各接收一个带标签的输入；每个上游节点只能转发它实际输出的值。有证据的存储端点使用 `database`，并写明文件或存储的名称。内存中计算出的结果通过产生它的 `backend` 操作来表示，并在其标签或副标签中写明结果字段。

Dataflow 要求每个流都有非空的 `label`。按照默认图例告诉读者的含义来选择 `variant`：省略/`default` 是普通数据流，`emphasis` 是主要数据，`security` 是策略/PII，`dashed` 是异步批处理。普通依赖、返回或回退使用 `default`；只有当来源支持该含义时才使用 `security` 或 `dashed`。若用户要求不同的视觉约定，给受影响的 `meta.legend.entries.<variant>.label` 写上能如实描述使用该 variant 的每个流的措辞，并遵循 [图例契约](authoring-contract.md#legend-contract)。

Lifecycle 使用 schema v3：在 `mainPath` 中列出顺利路径，并编写每一个迁移，包括主路径上的迁移；渲染器会摆放所有其他状态和路由。保留每个出口的标签、注释和 variant；[符合条件的等价出口](../renderers/lifecycle/README.md#layout) 会自动共用路由。迁移标签保持简短；可恢复的失败需要一条真实的回退迁移。

Class 省略 `meta.viewBox`，网格保持三列；只有在类型宽度接近 180px 默认值时才可用四列：长成员会让类型向 `layout.typeMaxW`（300px）增长，而每多一列都会加宽画布，并让所有文字向可读性下限缩小，所以应改为增加行。`layout.gapX` 和 `layout.typeMaxW` 是宽度控制项。

仓库或目录的 Tree 设置 `layout.direction: "right"`；浅而均衡的拆解保持默认的 `"down"`。当某个模式特有的摆放或视口问题需要更多细节时，阅读 [各模式的放置](authoring-contract.md#mode-placement)。

`finalize` 执行浏览器关卡。让完整图形在桌面端舒适可读，且横向溢出为零。必要时使用有意义的纵向行和按内在高度的页面滚动。6px 的投影文字检查是失败下限；在 1440px 下，普通上下文文字目标约为 7.5px 或更大。视口证据失败时，参见 [自动化浏览器证据](delivery-contract.md#automated-browser-evidence)。
