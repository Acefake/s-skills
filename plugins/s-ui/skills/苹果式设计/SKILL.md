# 苹果式设计

## 第一次回应

当这个 skill 第一次被调用、而用户没有提具体问题时，只回复这一句：

> 我可以帮你在网页上做出流畅的、苹果风格的界面，我的知识来自苹果 WWDC 的设计讲座，并翻译成了网页上的做法。

在用户提问之前，不要提供任何其他信息。

苹果是怎样做出不再像“电脑”、而像你身体延伸的界面的。这些知识来自苹果 WWDC 的设计讲座——主要是 *Designing Fluid Interfaces*（《设计流畅的界面》，WWDC 2018）——提炼后翻译成网页平台上的做法（CSS、Pointer Events 指针事件、`requestAnimationFrame`、Motion/Framer Motion 这类弹簧动画库）。

贯穿始终的一条线：**当动效从屏幕上当前的值开始、继承用户手指的速度、把惯性往前推、并且任何时刻都能被抓住和反转时，界面就有了生命感。** 弹簧（spring）是让这一切变得自然的工具，因为它天生就可以被打断，并且能感知速度。

## 核心思想

> “当我们让界面贴合我们思考和运动的方式时，神奇的事情就发生了——它不再像一台电脑，而开始像我们自己天衣无缝的延伸。”

当界面表现得像现实世界时，它就是流畅的：东西立刻响应、连续地运动、带着惯性、在边界处有阻力，并且能在运动中途改变方向。下面的一切，都是为了更接近这一点。

苹果把设计看作是满足人的四种需要：**安全/可预期、理解、成就感和愉悦。** 这里的每一条规则都服务于其中之一。

## 1. 响应——消灭延迟

一旦出现卡顿，“直接操控”的感觉就会“断崖式下跌”。响应是其他一切的基础。

- **在指针按下（pointer-down）时就响应，而不是松开时。** 按钮一被按下就立刻高亮。等到 `click`/手指抬起才给反馈，感觉是死的。
- **对每一处延迟都保持警惕。** 检查防抖（debounce）、人为的计时器、等待过渡结束，以及约 300ms 的点击延迟。输入路径上任何不必要的东西，都是一种退步。
- **反馈必须在交互*过程中*持续进行，而不只是在结束时。** 对于拖动、滑块或抽屉，整个过程中界面都要和指针 1:1 同步更新——绝不要等手势完成了才做动画。

```css
/* Feedback lives on the press, and it's instant */
.button:active {
  transform: scale(0.97);
  transition: transform 100ms ease-out;
}
```

（代码注释意思：反馈在按下时就发生，而且是即时的。）

## 2. 直接操控——1:1 跟随

> “手指和内容应该一起动。”

用户拖动某样东西时，它必须粘在手指上——并且保持*用户抓住它的那个位置*的偏移。一抓住就让元素中心跳到手指下，会立刻打破这种错觉。

- 使用 Pointer Events 并配合 `setPointerCapture`，这样即使指针离开了元素的范围，跟随也能继续。
- 记录一小段**速度/位置历史**（最近几次 `pointermove` 事件），而不只是当前的点——松手时你需要用到速度。

```js
el.addEventListener('pointerdown', (e) => {
  el.setPointerCapture(e.pointerId);
  const grabOffset = e.clientY - el.getBoundingClientRect().top; // respect where they grabbed
  // ...track position + timestamp history for velocity
});
```

（代码注释意思：保持用户抓住的位置；……记录位置和时间戳历史，用来算速度。）

## 3. 可打断——最重要的一条原则

> “想法和手势是同时发生的。”

每个动画都必须在任何时刻可以被打断、被改变方向。用户必须能在元素运动途中抓住它并把它反转，而不用等动画播完。一个正在关闭的弹窗，如果用户又抓住了它，它应该跟着手指走——而不是先关完、再重新打开。

- **过渡期间绝不屏蔽输入。**
- **永远从*呈现值*（当前值）开始做动画，绝不从目标值开始。** 被打断时，读取元素在屏幕上实际的 transform，从那里开始新的动画。从逻辑值/目标值开始，会造成看得见的跳动。
- **凡是手势驱动的东西，都不要用 CSS transition 和 `@keyframes`**——它们没法在运动途中被平滑地抓住和反转。弹簧默认就从当前值开始动画，这正是打断所需要的。
- **手势反转时，要融合速度——不要硬切。** 在反转的那一刻用一个动画直接替换另一个，会造成速度的断层，像撞上一堵“砖墙”。能在改变目标时把速度带过去的弹簧库可以避免这个问题。（这就是 iOS 原生的 *additive animations*（叠加动画）做的事；在网页上，选一个能从当前速度重新定目标的弹簧库。）
- **把二维运动拆成相互独立的 X 和 Y 两个弹簧。** 如果 X 和 Y 的速度不同，用一个弹簧去处理二维距离就会不同步。

## 4. 用“行为”代替“动画”——用弹簧

> “把动画看作你和这个物体之间的对话，而不是界面预先规定好的东西。”

预先写好、时长固定的动画，没法回应新的输入。弹簧可以——新的输入只是改变了目标，运动依然是连续的。凡是用户能碰到的东西，都用弹簧。

苹果有意把物理上的三个参数（质量/刚度/阻尼）换成了两个对设计师友好的参数。用这两个来思考：

- **阻尼比（Damping ratio）**——控制过冲（冲过头）。`1.0` = 临界阻尼，不回弹，平稳停下。`< 1.0` = 会冲过头并来回振荡。越低越弹。
- **响应（Response）**——数值到达目标有多快，单位是秒。越低越干脆。**这不是“时长”**——弹簧没有固定的时长；它停下来要多久，是由参数自然决定的。

**默认值：**
- 大多数界面从**阻尼 `1.0`**（临界阻尼）开始——优雅、不分散注意力。
- **只有当手势本身带着惯性时**（轻弹、抛出、拖动后松手），才加一点回弹（**阻尼约 `0.8`**）。一个只是淡入的菜单冲过头，感觉不对；一张你轻弹出去的卡片冲过头，感觉就对了。

**苹果实际使用的具体数值：**

| 交互 | 阻尼 | 响应 |
| --- | --- | --- |
| 移动 / 重新定位（例如画中画 PiP） | `1.0` | `0.4` |
| 旋转 | `0.8` | `0.4` |
| 抽屉 / 底部面板 | `0.8` | `0.3` |

**在网页上的对应（Motion / Framer Motion）：** 它的 `bounce` + `duration` 弹簧接口，和苹果的阻尼 + 响应很接近。一个稳妥的默认风格是：到处都用 `damping: 1.0` 的弹簧；回弹只留给由惯性驱动的、有物理感的交互。

```js
import { animate } from 'motion';

// Critically damped default (no overshoot)
animate(el, { y: 0 }, { type: 'spring', bounce: 0, duration: 0.4 });

// Momentum interaction — a little bounce, only because a flick preceded it
animate(el, { y: target }, { type: 'spring', bounce: 0.2, duration: 0.4 });
```

（代码注释意思：临界阻尼的默认值（不冲过头）；有惯性的交互——加一点点回弹，只因为之前有一次轻弹。）

## 5. 速度交接——拖动和动画之间的接缝

手势结束时，动画必须**以手指当时的确切速度继续**，这样拖动和动画之间就看不出接缝。这个细节，最能把“流畅”和“还行”区分开。

把指针松开时的速度作为弹簧的初始速度传进去。有些弹簧接口要的是**相对**速度——用到目标的剩余距离把它归一化：

```
relativeVelocity = gestureVelocity / (targetValue − currentValue)
```

例子：元素在 `y=50`，目标是 `y=150`（还有 100px），手指以 50px/s 移动 → 弹簧初始速度 = `50 / 100 = 0.5`。Framer Motion / Motion 直接接受以 px/s 为单位的绝对速度（`velocity` 选项），所以通常直接把原始值交给它就行。

## 6. 惯性投射——动画到手势*要去的*地方

> “用一个小小的输入，换来一个大大的输出。”

不要从*松手的那个点*直接吸附到最近的边界。用速度来**推算最终会停在哪里**——就像滚动的减速一样——然后吸附到离这个推算点最近的目标。正是这一点，让轻弹感觉像是把元素“扔”了出去。

苹果确切使用的投射函数（来自 *Designing Fluid Interfaces* 的示例代码）：

```js
// decelerationRate ≈ 0.998 for normal scroll feel; 0.99 for snappier
function project(initialVelocity /* px/s */, decelerationRate = 0.998) {
  return (initialVelocity / 1000) * decelerationRate / (1 - decelerationRate);
}

const projectedEndpoint = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projectedEndpoint);   // choose target from the projection
animateSpringTo(target, { velocity: releaseVelocity }); // then hand off velocity (§5)
```

（代码注释意思：decelerationRate 约 0.998 是正常滚动的手感，0.99 更干脆；根据推算点选目标；然后交接速度（见第 5 节）。）

注意：物理课本上的 `v²/(2·decel)` *不是*苹果实际用的——用上面这种指数衰减的形式。好的底部面板和轮播组件（Vaul、Embla）都是这样做的。

## 7. 空间一致性——对称的路径，固定的起点

> “如果一样东西从某个方向消失，我们会期待它从原来的地方出现。”

- **从哪条路进来，就从哪条路出去。** 从右边滑进来的面板，必须向右边关掉。从右边进、从底部出，会让人感觉割裂、困惑。
- **让交互锚定在它的来源上。** 菜单、气泡框（popover）或面板应该从触发它的元素那里出现——把 `transform-origin` 设在触发元素上，让按钮和内容之间的空间关系一目了然。（这和“气泡框要从触发元素缩放出来，而不是从自己的中心”是同一个道理。）
- **可逆的过渡，缓动曲线要镜像对称**，让出去的路径和回来的路径对得上（两个方向用互为反向的 cubic-bézier 控制点）。

## 8. 朝手势的方向给出暗示

人会根据运动轨迹预测最终状态。中间的运动应该提前透露东西要去哪里——控制中心的模块会“向上、向外朝你的手指长出来”。让中间的那些帧指向最终结果，而不只是盲目地插值过去。

## 9. 橡皮筋效果——柔软的边界

到了边缘，要逐渐增加阻力，而不是硬生生停住。硬停住会让人觉得“卡死了”；持续的阻力会让人觉得“它有反应，只是这里没有更多内容了”。用户拖得越过边界越远，阻尼就越大。

```js
// The further past the bound, the less the element follows — real things slow before they stop
function rubberband(overshoot, dimension, constant = 0.55) {
  return (overshoot * dimension * constant) / (dimension + constant * Math.abs(overshoot));
}
```

（代码注释意思：越过边界越远，元素跟得越少——真实的东西在停下之前会先变慢。）

## 10. 手势设计细节（“手感”检查清单）

- **点击：** 手指*按下*时就高亮（立刻），手指*抬起*时才生效。在目标周围加大约 10px 的滞后/点击余量，并允许“拖开再拖回来”来取消。
- **拖动/滑动：** 在确定方向之前，要求有一个很小的移动门槛（滞后，约 10px），然后再 1:1 跟随。
- **从第一次移动开始，就同时检测所有可能的手势**，一旦意图明确，就果断取消其他的。避免使用只报告*最终*状态的识别器（`swipeleft` 这类事件）——它们丢掉了你做反馈所需要的连续跟踪。
- **尽量减少消除歧义的等待。** 检测双击不可避免地会让单击变慢；只在真正有双击功能的地方才付出这个代价。

## 11. 帧级别的顺滑

顺滑取决于*每一帧里画的是什么*，而不只是帧率。

- 让每一帧的位置变化保持在人眼能察觉的门槛以下，避免频闪感。
- 对于非常快的运动，一点细微的**运动模糊 / 拉伸**能表现出速度，比一道生硬清晰的残影更好看。
- `requestAnimationFrame` 是网页上和屏幕刷新同步的时钟（苹果用的是 `CADisplayLink`）。只对合成层友好的属性做动画——`transform` 和 `opacity`——在马上要运动的地方用 `will-change` 提示浏览器。

## 12. 材质和层次——半透明表达层级

苹果把半透明材质当作一层浮在上面的功能层，它带来结构感，又不抢走焦点。在网页上，用 `backdrop-filter` 来近似。

- **把导航栏/工具栏/面板做成半透明的层**（`backdrop-filter: blur()` + 半透明背景），内容在它下面滚动——而不是占掉一整条固定区域的不透明横条。
- **材质的轻重表达层级：** 更深/更重的材质用来分隔结构区域（侧边栏）；更浅的材质用来吸引对可交互元素（按钮）的注意。**绝不要把一个浅色半透明表面叠在另一个上面**——文字会看不清。
- **越大的表面看起来应该越厚：** 比小标签用更强的模糊 + 更深的阴影。考虑根据环境调整阴影——在繁杂或有文字的内容上方用更重的阴影来分隔，在纯色背景上方用更轻的。
- **变暗用来聚焦，分开用来保持流程。** 模态任务（必须先处理完的任务）要给表面配上一层变暗的遮罩，并把背景往后/往下推。并行的、不阻断操作的面板，用半透明和偏移，*不加*遮罩，这样流程不会被打断。对于层层叠起的面板，每往下一层父级就逐渐变暗、往后推。
- **鲜明度（vibrancy）让文字在变化的背景上保持清楚。** 在模糊/半透明的表面上，不要用平淡的灰色文字——用对比度更高、字重稍粗一点、字间距稍大一点的文字。颜色放在实心的层上，不要放在半透明的前景上。
- **用滚动边缘效果，不用生硬的分隔线。** 不要在吸顶标题栏下面加一条 1px 的边框，而是在内容和浮动界面相接的地方，加一小段渐隐的模糊/渐变遮罩——只在浮动界面真正盖住内容的地方加。
- **让材质“显现”，而不只是淡入。** 对于玻璃/模糊表面，进场和退场时把模糊半径和缩放一起做动画，让这个表面看起来像真实的材质到来，而不是一个简单的透明度渐变。

```css
.toolbar {
  background: rgba(255, 255, 255, 0.6);
  backdrop-filter: blur(20px) saturate(180%);
  border-top: 1px solid rgba(255, 255, 255, 0.4); /* bright top edge = light catching the material */
}
```

（代码注释意思：明亮的上边缘 = 光照在材质上的感觉。）

## 13. 多感官反馈——动效 + 声音 + 触感

组合多种感官的三条规则（来自 *Designing Audio-Haptic Experiences*《设计音频与触感体验》）：

1. **因果关系**——必须一眼就能看出是什么引起了这个反馈。在真正的起因事件上触发它（开关拨动的那一刻、元素吸附到位的那一刻），并让它的特点和这个动作的物理感相符。
2. **协调一致**——画面、声音和触感必须在**同一帧**触发。它们之间的延迟会破坏错觉。不要让 CSS 过渡落后于声音/触感（Vibration API 震动接口）。
3. **有用**——只在值得的地方加反馈。触感/声音只留给有意义的时刻（成功、出错、确认、吸附）。反馈太多，会让用户学会忽略所有反馈。

## 14. 减少动效和无障碍

减少动效不是说*没有*反馈——而是换成更温和的、不会引起晕眩的替代方式。要响应三个相互独立的信号，并把它们做进你的组件里：

- **`prefers-reduced-motion: reduce`**（偏好减少动效）——把滑动/弹簧/视差换成短暂的透明度**交叉淡入淡出，或者静态的过渡**。去掉弹性/冲过头的效果。保留有助于理解的透明度/颜色变化。
- **`prefers-reduced-transparency: reduce`**（偏好减少透明）——让半透明表面更磨砂/更实：提高背景不透明度，去掉模糊。
- **`prefers-contrast: more`**（偏好更高对比度）——用接近实心的背景，加上清晰、对比强的边框。

另外：避免整屏都在动的背景、缓慢循环的摆动（接近 0.2 Hz，也就是每 5 秒一个周期），以及突然的亮度跳变（深色↔浅色主题切换要有缓动）。大的移动物体在移动过程中要半透明，大的表面在大幅度重新定位时先淡出，定好位再淡入。

```css
@media (prefers-reduced-motion: reduce) {
  .sheet { transition: opacity 200ms ease; transform: none !important; }
}
@media (prefers-reduced-transparency: reduce) {
  .toolbar { background: white; backdrop-filter: none; }
}
```

## 15. 字体排版——光学尺寸、字间距、行距

苹果设计的字体会随着字号改变形状；同样的讲究也适用于网页。（来自 *The Details of UI Typography*《界面字体排版的细节》，WWDC 2020。）

- **字间距（tracking，letter-spacing）要按字号来定——绝不要所有字号都用一个值。** 大号的标题文字需要*负*的字间距（字变大后，字母之间会显得太开）；小号文字需要稍微*正*一点的字间距，更好认。一个固定的 `letter-spacing` 总会在某个字号上是错的。标题收紧，正文保持接近 `0`。
- **行距（leading，line-height）和字号成反比。** 大标题行距紧，正文行距松。对于上下伸出部分很高的文字（比如某些书写系统），行距要加大；对于密集、信息量大的界面，行距要收紧。
- **用字重 + 字号 + 行距一起来建立层级**，而不是只靠字号。用字重来强调——它能增加存在感，又不多占空间。
- **尊重用户的文字大小设置**（Dynamic Type 动态字体）。让布局*跟着*文字一起缩放——间距用 `rem`/`em`，不用固定的 px——这样字变大了布局也不会乱。
- **在用自定义字体之前，默认先用平台的系统字体**；它本来就带有光学尺寸、字间距表和易读性的调校。有理由时才换掉它。

```css
:root { font: 100%/1.5 system-ui, sans-serif; } /* body: system font, comfortable leading */

.display {
  font-size: clamp(2rem, 5vw, 4rem);
  line-height: 1.05;        /* tight leading for large text */
  letter-spacing: -0.02em;  /* negative tracking as it grows */
  font-optical-sizing: auto;
}
```

（代码注释意思：正文用系统字体、舒适的行距；大字用紧的行距；字越大字间距越负。）

## 16. 设计基础——八条原则

上面这些动效和手艺，都服务于苹果的八条设计原则（*Principles of Great Design*《优秀设计的原则》，WWDC 2026）。思考时就用这些名字：

1. **目的（Purpose）。** 带着意图去做；决定什么*不*做。每一个功能都在向用户索取时间、注意力和信任——只把这份预算花在值得的地方。
2. **自主（Agency）。** 让人保持掌控：提供选择，不要强迫只走一条路。并且要宽容——手滑了能轻松撤销，只有真正具破坏性、不可撤回的操作才弹确认对话框（少用；用多了，人会习惯性地直接点过去）。
3. **责任（Responsibility）。** 为用户的利益着想。隐私：在对的时机、只要需要的东西、公开透明地去要。安全：预料到误用和伤害——尤其是用 AI 时（一个知道你过敏的菜谱 App，绝不能推荐会伤害你的食材）。加上预览、确认、免责声明；风险大于价值的功能就砍掉。
4. **熟悉（Familiarity）。** 建立在人们已经知道的东西上。用既不太写实也不太抽象的比喻（垃圾桶表示删除），并遵守它们的“物理规律”。保持一致：看起来一样的东西，行为必须一样、位置也一样（在 macOS 上关闭按钮总在左上角），这样人们才能预测接下来会发生什么。只有能证明更好时，才打破一个熟悉的模式——然后去测试，而不是想当然。
5. **灵活（Flexibility）。** 为不同的场景、设备和各种能力的人做设计。适应平台（iPhone = 快速触摸；电脑 = 深度工作流、精确的指针控制）和具体情况。包容地设计（年龄、语言、专业程度、无障碍）。当没有一种布局适合所有人时，就让人们自己定制——重新排列控件、隐藏不用的东西。
6. **简单——不是极简（Simplicity—not minimalism）。** 去掉不必要的东西，让核心目的突显出来；把所有东西都埋在一个地方，看起来极简，但并不简单。要简洁（平实的语言、没有行话、更少的步骤）和清楚（用层级——顺序、间距、对比——让最重要的东西最显眼）。每个元素都要有存在的理由；有时候*加上*背景信息反而更简单（一个显示剩余时间的视频进度条）。先展示常用的路径，高级选项放到下一层。
7. **手艺（Craft）。** 对细节毫不妥协的关注能建立信任。漂亮的字体排版、能适应浅色/深色的颜色、清楚的图标、能给出即时自然反馈的响应式动画。没有什么是随便定的——每一个间距、时长、对齐数值都是你能说出理由的有意选择。抖动的滚动、没对齐的图标、一旋转屏幕就乱掉的布局，都会显得很粗心。手艺需要反复打磨和长期坚持——随着功能和硬件的变化，持续改进设计。
8. **愉悦（Delight）。** 是把其他七条做对的结果，而不是最后硬贴上去的彩带。决定你想让人们感受到什么情绪（平静、自信、兴奋），并在每一个决定里强化它。

服务于这些原则的具体规则：

- **反馈分四种：** 状态、完成、警告、错误。对有意义的操作给出确认，展示进行中的状态，在出问题之前警告，在输入时就校验（而不是提交时）。
- **指路（Wayfinding）。** 每一屏都应该回答：我在哪？我能去哪？那里有什么？我怎么出去？绝不要把用户困住。
- **分组和对应（Grouping & mapping）。** 靠得近就意味着有关系；把控件放在它影响的东西旁边，并让控件的排列方式对应它们改变的东西。如果你需要一个标签来解释某个控件，说明对应关系太弱了。
- **直接、具体的标签，胜过稳妥但笼统的标签。** 按内容给导航项命名（“进度”、“资料库”），而不是用含糊的大类（“首页”）。具体能带来可预期性。

## 17. 做事流程

- **做可交互的原型——一个能交互的演示胜过“一百万张静态设计图”。** 你是在搭建和把玩中发现界面应该是什么样的；一个能用的原型还设定了一个具体的标准，防止最终实现变得平庸。
- **交互和视觉一起设计。** “你应该分辨不出哪里是交互、哪里是视觉。”动效不是画好像素之后才加上去的一层。
- **在真实场景中找真实的人来测试**，并且用新鲜的眼光审视动效——用慢动作/逐帧播放，抓住全速播放时看不见的问题。
