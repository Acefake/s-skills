# 基于仓库的编写

当任何类型的图必须解释一个真实仓库时，使用本参考资料。对于职责、调用、边界和持久化，源码是权威依据。当所请求的含义已被覆盖、且每一条断言的事实都有支撑它的源码证据时，图才算完成。

## 按需探索

1. **冻结身份。** 在目标仓库中记录 `git rev-parse
   HEAD`、`git remote get-url origin` 和 `git status --short`。在记录 origin 或把它放进候选稿之前，移除 HTTP(S) userinfo（包括用户名、密码和令牌）。保留其传输协议、端口、路径和 `.git` 后缀；不要把内部 SSH origin 改写成 HTTPS。把不含凭据的 URL 和四十个字符的修订号固定在 `meta.repository` 中。对于 SSH origin、不受支持的代码托管平台、刻意只用本地的源码链接，或其 HTTPS URL 仅作为仓库身份的本地 fixture，使用 `link_mode: "local-only"`；保留 URL 和修订号。Web 链接需要受支持的 GitHub、Gitee 或 GitLab HTTPS origin；GitHub、Gitee、gitlab.com，以及用 `provider: "gitlab"` 声明的自托管 GitLab 主机，会与同一主机上的 SSH origin 匹配。如果工作区是脏的，在你的回复中注明改动的路径；候选稿没有用于记录它们的字段。仓库证据是针对固定修订号上已提交的字节验证的，而不是工作区中的编辑：对于任何被引用的已改动路径，检查该修订号的干净检出。不要把未提交的字节当作 `HEAD` 的证据呈现；`local-only` 不会记录这些字节的可验证快照。

2. **划定切片。** 利用项目说明、清单文件、入口点、注册代码和部署配置，定位候选的运行时单元。阅读与请求相关的入口、配置和模块。顺着 import 和调用点追下去，直到所请求的职责到达其实际的输入、输出或副作用。读一个小的相连切片，而不是为了找一个方便的标签去扫描整个仓库。

3. **追踪归属。** 运行时和 I/O 关系，要从调用点上观察到的执行者、操作和目标推导出来；部署和信任关系使用相应的配置或强制执行证据。区分请求某个操作的控制者、执行它的运行时，以及接收字节的存储。对于文件或数据库连线，源码必须指明其实际的读取者或写入者；“维护任务” 这样的职责陈述并不能证明直接 I/O。阅读时把这些事实与源码位置放在一起，不要另建规划产物。用 [Composition and meaning](authoring-defaults.md#composition-and-meaning) 选择哪些区别需要单独的节点；发现一个实现角色并不会自动把它加进概览。已配置的提供方、注入的适配器、本地桩和持久服务是不同的声明；只标出源码支持的那一种。

4. **边读边记录证据。** 为每个组件和有意义的关系保留确切的仓库相对路径和闭区间行号范围。跟随实际的分支、重试、降级和错误处理。一个被导出或被配置、但正常路径从不调用的函数是可选能力，不是必需的运行时连线。对于关于权威状态变更或控制归属的声明，要追到实际的写入或执行位置以及允许它发生的条件；仅凭一个上游调用者并不能确立这些条件。

5. **点明不确定性。** 把未解决的问题写在它影响的那条声明旁边：例如，“这里调用了 `writeFile`；持久性未知。” 通过阅读下一段相关源码范围来解决问题，或者把它保留为明确的未知项。绝不把一个标签、包描述或配置值变成未经观察的服务或行为。

当每一项所请求的职责、关系和边界都有源码蕴含支撑，且剩下的未知项无法改变这一覆盖时，停止探索。没有要达到的节点、连线、引用、视图、卡片或边界数量。不要仅仅为了表示完成而增加一个总结步骤。

已知相关的独立文件要批量读取。读取源码片段时带上其原始行号（例如 `nl -ba <file> | sed -n '40,90p'`）。从显示的源码中照抄引用的起止行，当片段读到 EOF 时也包括实际的最后一行。每多读一次，都应回答一个能改变图的未解决问题。复用本任务中已验证过的简洁事实及其源码范围；跨修订时，重新检查受影响的入口点、配置、依赖和证据。

## 各类图的证据

只有主要元素携带 `sources`，每个最多三个范围：Architecture 组件、Workflow、Dataflow 和 Tree 节点、Sequence 参与者、Lifecycle 状态、ERD 实体、Class 类型、Timeline 事件和 Waterfall span。关系、消息、流和转换都没有：把调用、写入或转换的位置引用在拥有它的元素上（调用者、写入者、被离开的状态），更多证据放在注释或卡片里。文件夹节点引用它自己的 README 或入口文件，否则引用定义或运行它的文件。Timeline 事件引用固定修订号上记录它的文件，例如 changelog 条目，并从该历史中的 tag 或 commit 获取时间，对于只有日期的记录则取当地时间中午。该历史之外的 tag 或 commit 不可引用。在卡片中说明使用了哪一种。没有已记录追踪数据的 Waterfall 使用 `meta.evidence: "illustrative"`，并保持其时长被标注为示意；不要仅为了计时而运行项目。

## 按结构选择示例

在加载其内容之前，利用请求和源码检查本就需要的仓库元数据，在 [Type router](../SKILL.md#type-router) 中选定主示例。选择要放进已有的读取批次中，不需要额外的消息、命令或全仓扫描。对于混合或不明确的任务，在正常检查中一旦得知所请求的职责和入口点就使用它们；保留它们的实际角色。当某项必要能力仍无法解释时，再读另一个示例。示例教的是形状，不是事实：一个库不必因此获得文件系统节点，完成的 showcase 仍然遵循初稿自动路由规则。

## 依据证据编写

使用该模式完整的 JSON 形状，包括仓库身份、组件和连接；每个有仓库支撑的组件都需要支撑它的源码引用，而边界或卡片只有在回答了读者的真实问题时才添加。先让自动路由和自动 viewBox 尺寸生效。保持主路径可读，把异常路径放在其所有者旁边，当源码显示存在独立职责时，把文件系统存储放在控制边界之外。

已有示例教的是字段形状，不是事实或任意值。它不授权新的边界种类、长注释、viewBox 尺寸或路由控制。无论所选示例是否已包含该字段，都要查阅具体模式的 schema 和 `schemas/common.schema.json`；使用 schema 的枚举、长度、标识符和仓库规则。Architecture 边界目前使用 `kind: "region"` 或 `kind: "security-group"`；源码引用使用 `path`、`line` 和可选的 `end_line`。

有仓库支撑的组件需要简洁、真实的 `sources` 引用。在概括文件系统 I/O 时保留控制归属：读取或写入文件的代码拥有该操作，而纯内存变换只是接收和返回值。这项事实核查并不要求为每个辅助函数单独建一个概览节点。用已有示例获取有效的字段形状，然后把所有标识符、措辞、源码路径和声明替换为经过检查的仓库事实。
