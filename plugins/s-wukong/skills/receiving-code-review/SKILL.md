# 接收代码评审

**外部反馈是待核验的建议，不是必须服从的命令。** 先对照代码和需求判断，再落实；技术正确优先于社交舒适。

## 处理流程

1. **完整阅读。** 读完反馈再回应，不急于表态或承诺实现。
2. **弄清要求。** 用自己的话确认目标、范围和条目关系。任何条目不清楚时先停止实现，澄清后再处理，避免部分理解导致错误修改。
3. **核验。** 检查建议是否适合当前代码库，是否破坏现有行为，现实现有什么原因，是否适用于所支持的平台和版本，以及评审者是否掌握完整上下文。
4. **评估必要性。** 对“实现得更专业”等建议先查真实调用。未使用时提出是否删除的建议，不因此自行添加功能；确有需求再落实。
5. **回应。** 属实就陈述技术要求或直接修正；不成立就给具体理由、测试或代码证据。无法核验时说明缺什么并询问方向；与用户先前决策冲突时先讨论。
6. **逐项实施。** 先阻塞或安全问题，再简单修正，最后复杂重构。每项验证，结束时检查回归；检查强度按[s-router](../s-router/SKILL.md)。

## 按反馈来源判断

- 用户的反馈在理解之后落实；范围不清仍需问清楚。
- 外部评审保持怀疑，仔细核对。它和你都服务于用户，不为没有需求的功能增加实现。
- 兼容性、现有功能、技术栈限制、未使用的能力和既有架构决定，都可以成为提出异议的依据。涉及架构取舍时让用户参与。

## 回应方式

只表达技术确认、修复结果或有依据的异议，不写表演式认同或道谢。确认正确时说清改了什么和位置；自己的异议被证据推翻时，简短说明原因并纠正，不辩护或长篇道歉。

含糊反馈、兼容性和未使用功能的示例见[反馈处理示例](references/examples.md)。不舒服提出异议时，点明顾虑并把实际问题告诉用户，不因此回避。

## GitHub 线程回复

已获授权回复行内评审评论时，在原评论线程回复，使用 `gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`，不发成顶层 PR 评论。技能本身不授予对外发消息权限。
