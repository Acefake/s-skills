**结果。** 需求按它的类型走到应有的终点，由负责这件事的 Compound Engineering skill 来完成；所有没解决的问题都记录在用户能看到的地方。大多数需求的终点就是那个 skill 给出的结果，不需要新建分支（branch）。只有“改代码”这一类需求有自己更多的步骤：它的终点是一个已经打开的合并请求（PR），你手上有它的网址，CI（持续集成，就是代码提交后自动跑的检查和测试）已经有了结论。在这之前，代码要经过：实现、简化、审查（审查中符合条件的问题已经修好，其余的记录下来）、把值得长期保留的经验记下来、提交（commit）、推送（push）。合并（merge）由用户自己决定，除非用户这一次明确授权你合并。

**工作依据。** 在会改代码的路线上，本次运行中没有经过核实的工作依据，就什么都不能实现。只有两种东西算数：一份可以直接动手实现的计划，由 `按计划实现` 来实现；或者 `查bug` 返回了 `fixed`（已修复），这个修复本身就是实现。这份计划必须是本次会话里明确指出来的，具体按 `references/intake.md` 的定义。绝不要去计划文件夹里翻找候选计划，也不要根据你自己找到的文件行动。已经有计划时，绝不要从零重新做计划。

**按需求的类型选路线。** 把需求交给负责这件事的 skill；运行环境里的 skill 列表就是目录。选择之前先读 `references/intake.md`；只有它规定了有哪些路线、谁优先、每个子 skill 要传什么参数、怎么理解每个返回结果。简单说：

- 给了计划文件路径，或者本次会话里 `做计划` 写过一份计划：走计划路线。
- 具体报告某个功能出错或不正常：交给 `查bug`；复现问题是那个 skill 的事，不是入口阶段的事。
- 一个改动取决于用户还没拿定主意的判断：先交给 `ce-pov`，只有结论支持这个改动才继续；如果这个判断没有东西要做，就以结论结束。
- 产品要做成什么样有不止一种合理理解：有人在场时交给 `头脑风暴`；没人在场时用流水线模式（pipeline mode，就是全自动、不提问的模式）交给 `做计划`。
- 需求的结果不是改代码：交给负责那种结果的 skill（`解释代码`、`ce-prototype`、`ce-pov`、`ce-ideate` 等）；调用它就是这次运行的全部：返回它的结果，然后结束。
- 其他所有改代码的需求：交给 `做计划`。

拿不准时，选对证据要求更高的那条路线。

**和用户的互动。** 只通过 `头脑风暴` 向用户提问，而且只在有人在场时提问。其他事情都不等待，直接往下做：能撤销的工作直接做完，展示给用户，让他事后纠正；只有超出用户授权范围、又不能撤销的操作（用户没授权的合并、强制推送 force-push、删除数据）才停下来。`全自动开发` 会被定时任务、循环和嵌套的编排程序（orchestrator，就是调度其他 skill 的上层程序）调用。唯一的另一个问题，是 `references/stage-routing.md` 规定的路线歧义问题：当对话里把规划或实现指定给某个模型或运行环境时，选路线前先读这个文件；只有它规定了传递用的字符串和清理规则。

**出现下面任何一种情况，就停下来并说明原因：**

- 拿不到工作依据：规划返回了 blocked（被卡住），诊断没找到安全的修复办法，修复会跑偏，`ce-pov` 不支持这个改动，或者某个阶段的指定无法传下去。
- 子 skill 的返回结果不是“已完成且有证据”。
- 之前已经定下来的决定被推翻了。
- 项目自己规定的发布流程没有做到。

停下来时，不能推送任何之前没推送过的东西。

这里提到的每个 skill，都要在运行环境的可用 skill 列表里找到对应条目，并调用那个确切的条目；有的环境会加命名空间前缀（`compound-engineering:ce-plan`）。开始前先读 `references/task-visibility.md`：它规定了通过平台的任务跟踪功能展示的阶段视图、在聊天里怎么说明进度，以及完成规则：一步只有真的跑过才算完成；子 skill 返回后，在同一轮里接着做下一个编号的步骤；在输出 DONE 或停下来之前，这一轮不能结束。

## 运行步骤（会改代码的路线）

1. **按 `references/intake.md` 拿到工作依据。** 走计划路线时，先读 `references/plan-brief.md`；只有它规定了“已定决定摘要”（settled-decisions brief）和产物根目录规则。任何明确的 `status: blocked` 返回，包括 `settled-decision-invalidated`（已定决定被推翻），都会让运行停止。blocked 状态比已有的产物优先，而且绝不重试。只有在既没有阻塞、`做计划` 本次也没报告写出计划文件时，才用同样的参数再调用一次 `做计划`，并原样复用已写好的摘要；这份计划之后必须通过 `references/plan-brief.md` 里的“可以动手”检查。走计划路线时，如果规划阶段的指定已经确定，就把 `plan_model:<alias>` 这个标记跟需求一起传过去。把工作依据记下来，后面每一步都要用。LFG 从不直接启动 `/goal`；要不要用 goal 模式由 `按计划实现` 决定，它做完后把控制权交回来。

2. **先读 `references/work-return.md`**，然后用 `mode:return-to-caller <plan-path-from-step-1>` 调用 `按计划实现` skill。走修 bug 路线时不做这一步：`查bug` 已经实现并提交了，`references/debug-return.md` 就是它的关卡。只有合格的 `status: complete` 才能往下走；其他任何状态或格式不对的返回，都会让流水线停止。

3. **现在读 `references/review-followup.md`**；它管第 3 到第 7 步。对分支的改动（diff，就是改了哪些地方）调用 `简化代码` skill；只有纯文档改动或大约不到 10 行的改动，才跳过这次调用。

4. 用 `mode:agent plan:<plan-path-from-step-1>` 调用 `代码审查` skill；走修 bug 路线时去掉 `plan:`。如果有一条 `settled_conflict`（和已定决定冲突）的发现，它的证据表明那个已定决定行不通（做不到、做错了东西、或者会造成破坏），就在发布前提条件之前，以 blocked 停止流水线，并报告这条发现。

**发布前提条件（从第 5 步起每次推送都适用）。** 先运行一次 `git remote`。如果没有远程仓库（remote），就是纯本地：各步骤要求的提交照常做，但跳过所有推送、创建或修改 PR、查看 CI 的操作，第 10 步整个跳过。这是正常结束，不是错误。

5. **按那个文件的规定，应用并保存审查修复。** 如果符合条件的审查修复还只在工作区、没有提交，就不能进入遗留问题交接、不能跑浏览器测试、也不能输出 DONE。

6. **自动交接遗留问题**：只要存在以下任何一种：没应用的可处理发现、第 4 步的 `settled_conflict` 标记、或者第 2 步“继续做但已标记”的 `settled_decision_conflicts` 条目，就按那个文件的规定把它可靠地记下来：写在 PR 说明里；如果不会有 PR，就写进工单（ticket）或 DONE 报告。三种都没有时才跳过。遗留问题没记牢之前，不要输出 DONE。只要报告里写明了，就绝不要因为工单系统提交失败而卡住 DONE。不要去问用户。

7. 如果这次运行产生了值得长期保留、但代码、测试和计划里都没有记下的思路，就用 `mode:non-interactive` 调用 `ce-compound` skill；完整条件见那个文件。返回 `Documentation skipped`（跳过文档）也算成功；在这里运行，能让这条经验在 PR 打开时就写进去。

8. 用 `mode:pipeline` 调用 `ce-test-browser` skill。

9. **先读 `references/shipping.md`**；它管第 9 到第 11 步。然后用 `mode:pipeline branding:on` 调用 `提交推送开PR` skill。

10. 有打开的 PR 时（按 `references/shipping.md` 的判断），用 `ce-babysit-pr mode:pipeline <pr-url>` 盯着这个 PR，直到 CI 出结论。不要在这里自己重新实现盯 CI 的逻辑。

11. 按 `references/shipping.md` 做完收尾后，输出 `<promise>DONE</promise>`。
