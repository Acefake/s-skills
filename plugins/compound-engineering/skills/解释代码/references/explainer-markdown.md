# 说明文档的 Markdown 渲染

> 翻译自 Compound Engineering 插件（编号 680）的 `解释代码` skill 参考文件，原作者 Kieran Klaassen 和 Trevin Chow（版权 © 2025 Every），许可证 MIT，仅供自用。

说明文档怎样渲染成 markdown——这是接收阶段确定为 `output:md` 时的备用格式。在写的时候加载，不要更早。内容和按读者调整由 skill 正文负责；markdown 的兼容性由这份参考文件负责。

## 硬性规定

- **YAML frontmatter 放元数据：** `title`、`date`、`input_shape`（concept / diff / idea / recap）、`subject`；证据退回到模型知识时加 `unverified: true`；请求指定了另一个读者时加 `rendered_for: <reader>`（给用户本人看的版本完全不写这一项）。在不同格式之间，保持这些现有的产物字段名不变。
- **纯 markdown。** 不用 HTML 元素，不用 `<details>`，不用内联样式。
- **只用来展示。** 没有交互式的练习或测验内容。“检查理解”如果有，就是 `references/check-in.md` 负责的那一节静态 `## Check yourself`：先问题，后答案，全是可见文字。
- 引用任何文件都用**相对于仓库的路径**；绝不用绝对路径。

## 呈现

深度、语气和版式由 skill 正文里关于读者的约定决定。给读者足够的项目背景，让他不看原来的对话也能看懂解释。按读者已经知道的东西来调整这些背景。

当图示能让解释更清楚时就用。Markdown 的渲染规则仍然适用：

- 图示用围起来的 `mermaid` 代码块。绝不手画方框线或 ASCII 图。
- 表格类的内容用竖线分隔的 Markdown 表格。
- 每个围起来的代码块都要标上语言。源代码位置用相对于仓库的链接，放在代码块外面；某个运行环境特有的“文件和行号”引用格式，不算语言标签。

图示是文字的补充；跳过图示的读者，也能从文字里得到完整的解释。保留来源引用。讲项目行为时用真实代码，自己编的示例要标明是示例。

当证据超出要求的范围或深度时，挑出相关的线索，并说明省略了什么。绝不要悄悄去掉回顾的后半段，然后把它当成整个时间段来呈现。
