# 用户要求的目的地

> 翻译自 Compound Engineering 插件（编号 680）的 `解释代码` skill 参考文件，原作者 Kieran Klaassen 和 Trevin Chow（版权 © 2025 Every），许可证 MIT，仅供自用。

只有在要求交付到某个目的地时才加载。用那个目的地可用的功能，并核实生成的文件、网址或文档引用。如果外围的产物归调用它的流程负责，那么放在哪里、怎么发布也归它负责；改为把解释返回给它。

只弄清完成请求所需要的目的地信息。不要求用户看菜单，也不要提议重写或改进解释。在请求任何必需的发布同意之前，先按预定读者调整好内容。交付失败时，保留正式的本地产物，并报告哪些没完成。没有授权时，不要换用别的发布方式。

## Claude Artifact

当会话是 Claude Code、并且有它的 Artifact 工具时，HTML 输出可以用这个。把正式的 `$RUN_DIR/explainer.html` 交给这个工具，遵守它当前的约定，并把返回的网址或引用告诉用户确认。为适应它的产物运行环境所需要的任何调整，都由这个工具负责；不要为它预先处理 HTML。

## 公开发布到 ht-ml.app

没有选 Claude Artifact 时，这是首选的 HTML 发布方式。ht-ml.app 接受完整的独立 HTML 文档，通过普通的 HTTP 工作，和智能体的运行环境无关。

发布之前，要说明**这个页面是公开的，可能会被搜索引擎收录、被抓取、被复制或被存档**，并在这个警告之后，针对实际要发送的这份产物获得明确的确认。最初的请求本身不算确认。警告之后给出的确认，适用于同一份产物。如果产物有了实质性的变化，要对改过的内容重新获得确认。如果拿不到确认，就不要发布；保留正式的 `$RUN_DIR/explainer.html`，并报告它的本地路径。绝不在无人值守时发布。如果内容敏感，就留在本地。

用户选了带警告的那个选项，或者在警告后明确确认之后：

1. 优先使用当前会话里检测到的任何 ht-ml.app 或通用 HTML 发布功能。如果它是一个 skill，就通过平台调用 skill 的功能调用它，传入正式的 `$RUN_DIR/explainer.html` 和用户对公开发布的确认；否则就直接调用检测到的工具、连接器或浏览器功能。遵守那个功能当前的约定。不要假设某个特定的 skill 名字或安装路径。
2. 如果没有安装任何发布工具，就用能访问的网页或 HTTP 接口，按照 ht-ml.app 写给智能体看的说明 `https://ht-ml.app/llms.txt`（或它链接的 API 帮助）来发布完整的正式 HTML。说明文档已经写好了；不要选模板，也不要重新设计。
3. 给出返回的网址。如果返回了用于更新的凭证，要把它当作密钥：不要在聊天里打印出来，也不要嵌进页面里。失败时，等一会儿重试一次，然后报告错误，退回到正式的本地文件路径。

## 本地文件

1. 如果用户已经说了路径，就不用再问；否则按 skill 正文的互动规则，问出缺少的路径。
2. 把产物从运行目录复制到那个路径（`cp "$RUN_DIR/explainer.html" <path>`——markdown 运行时是 `explainer.md`），需要时创建上级目录。
3. 报告绝对路径。如果用户要求、并且运行环境支持，就打开它。

## 发布到 Proof（只限 markdown 输出）

Proof 接收的是 markdown，所以只有当运行确定为 `output:md` 时才显示这个选项。如果安装了 `ce-proof` skill，就通过平台调用 skill 的功能调用它，传入产物路径、标题（`Explainer: <subject>`）和身份 `ai:compound-engineering` / `Compound Engineering`；给出返回的分享网址。如果没装这个 skill，但能访问 Proof 的网页 API，就按那个 API 用 POST 发送 markdown。失败时：等一会儿重试一次，然后直白地报告上传没成功以及原因，退回到本地文件路径。这是单向发布；运行目录里的文件仍然是正式版本。

## 发送到 Thinkroom

只有检测到 Thinkroom 功能时才提供——会话 skill 列表里有 Thinkroom skill、能访问的 MCP 工具，或者有文档说明、能响应的命令行工具。用那个功能提供的接口，根据说明文档的内容创建/分享一份文档，标题和正文格式遵守那个接口自己的约定。给出返回的文档引用。发送失败时，报告失败并退回到本地文件路径。检测不到任何功能时，绝不要去猜 Thinkroom 的 API 是什么样——这个选项就不显示。
