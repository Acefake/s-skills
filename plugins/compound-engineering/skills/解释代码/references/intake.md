# 接收请求

在开始收集任何证据之前，先把请求归入一种输入类型——概念（concept）、改动（diff）、想法（idea）或工作回顾时间段（work-recap window）——并确定读者是谁。靠理解用户的提示来判断；不要依赖参数标记的替换机制，因为不同运行环境的做法不一样。

> 翻译自 Compound Engineering 插件（编号 680）的 `解释代码` skill 参考文件，原作者 Kieran Klaassen 和 Trevin Chow（版权 © 2025 Every），许可证 MIT，仅供自用。

## 标记（flag token）

标记的存在，是为了让自动化程序和连续调用能强制做出某个决定。用普通语言调用这个 skill 是人平常的用法，并不是次一等的方式——大多数请求根本不带标记，也必须同样可靠地分类。

| 标记 | 例子 | 作用 |
|-------|---------|--------|
| `diff:<ref-or-range>` | `diff:abc1234`, `diff:main..HEAD`, `diff:PR#42` | 强制用 diff 模式解释那个改动 |
| `since:<window-or-ref>` | `since:monday`, `since:7d`, `since:v2.1.0` | 强制用 recap 模式回顾那段时间 |
| `output:<md\|html>` | `output:md` | 覆盖产物的格式（默认 `html`） |
| `audience:<who>` | `audience:team`, `audience:"the design review"` | 写给那个读者看，而不是给用户本人看 |

**一个 `word:value` 组合，只有读起来像标记时才算标记。** 它要放在请求开头或单独出现，冒号后面没有空格，而且——决定性的检验——**把它去掉后，请求仍然说得通。如果去掉它会让句子变得不通，它就从来不是标记。** 把它留在请求文字里，按意思来分类。普通的技术文字里到处都是冒号，一个把冒号吃掉的标记解析器，会悄悄改变用户的要求：

- "walk me through the diff: why did we split the parser"——去掉 `diff:why` 后变成 "walk me through the did we split the parser"。句子不通了，所以这是普通文字。按意思分类（一个关于拆分解析器的 diff 请求），绝不要让假的引用 `why` 压过这个判断。
- "explain how we pick the audience: engineers vs designers"——这是一个关于“怎样选择读者”的概念请求，写给用户本人看。不是一个指定 "engineers" 的 `audience:` 标记。
- "teach me how our renderer decides output: html or terminal escape codes"——普通文字。注意，这个例子如果解析错了，是悄无声息的，因为 `html` 本来就是默认格式，看不到任何矛盾。
- `diff:main..HEAD`，或者放在请求开头的 `audience:team`——是真正的标记：去掉它，剩下的不会变得不通。

- 放在标记位置上的标记，优先于推断。普通文字里的冒号不算。
- `diff:` 和 `since:` 同时出现会冲突——按 skill 正文里的互动规则来确定用户想要的主题。
- 不认识的 `<word>:<word>` 标记（包括出现在话题里的约定式提交前缀，比如 `feat:`）不是标记——它原样作为请求文字传下去。*认识的*标记如果没通过上面“读起来像标记”的检验，也一样。
- 值为空或缺失的标记不是标记——当作普通文字处理。
- `output:` 带了不认识的值：去掉这个标记，记一句 `Ignored unknown output: value '<value>' — using html`，然后继续。

## 推断（没有强制标记时）

按形式给剩下的文字分类：

- **Diff（改动）**——请求点名了一个能确定下来的改动：一个 sha（提交编号）、分支、PR、“上一次提交”、“你刚才做的”、“这个改动”。
- **Recap（回顾）**——请求问的是一段时间里发生了什么（“我这周做了什么”、“帮我补补进度”、“帮我准备站会”），**或者只说了一个时间段、别的几乎没说**（“从上周一起”、“上周”、“过去 3 天”、“这个迭代”）。只有时间段的请求是回顾请求，不是要解释的话题——不要把“从上周一起”当成一个叫“从上周一起”的概念。
- **Idea（想法）**——请求提出了用户自己的一个提议或想法，要求理解它：“解释一下我关于 X 的想法”、“Y 意味着什么”。这个想法是固定的前提（见 SKILL.md 的“边界”）。
- **Concept（概念）**——其他所有情况：一个要学习的话题、模式、子系统或外部主题。

**确定时间段（recap 模式）。** 时间段要么以标记的值出现（`since:monday`），要么以普通文字出现（“从上周一起”、“过去 3 天”）——两种都用同样的方法换算成具体的日期范围，并在产物的 `Subject` 里写明换算后的范围。`since last Monday` 和 `since:monday` 意思一样；有没有冒号不能改变答案。只有当请求完全没说时间段时，才退回到默认的最近 7 天；绝不要用这个默认值悄悄代替用户说过的时间段——如果用户说的时间段没法有把握地换算出来，就说明你用了什么。

**平局规则——概念还是改动：** 当一个请求两种都说得通时（一个仓库里的话题，同时又点名了一个能识别的最近改动，比如“解释一下我们刚加的重试逻辑”），能具体确定下来的改动胜出：用 diff 模式，把概念当作背景框架。没有可确定改动的话题，就是概念。

**仓库关联检查（概念模式）：** 只有当一个概念真的和仓库有关时，才去仓库里找证据。外部主题（某个语言特性、一个面试题、一篇论文）不需要在仓库里找证据——不要硬扯。

## 读者和交付方式

根据请求和上下文，确定谁会用这份解释、拿来做什么。默认读者是用户。准备照着解释去讲话的人，仍然是读者。当有人为别人请求内容时，那些人就是预定的读者。按这个用途调整用词、切入角度、深度和呈现方式，但不改变证据，也不把别人的工作算到用户头上。

如果一个回答，或者一段给别的文档用的文字就能满足请求，就返回它。如果请求是要深入学习、要保留一份说明文档、或者要一份独立的文档，那就值得做一份产物；这份产物默认用 HTML，用户要求时用 markdown。点名了 `diff:` 或 `since:`，只是选定了主题，并不决定是否必须做一份文档。明确的 `output:` 选定产物格式。如果用户要求更短的解释或一段可以分享的摘录，就照办，不要求做一份完整的教学文档。

在创建运行目录或加载渲染说明之前，先选定交付方式。预定用途清楚时，不需要额外的模式或确认。缺少主题或存在重要歧义时，按 skill 正文里的互动规则处理。
