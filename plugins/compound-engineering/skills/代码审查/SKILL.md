# 代码审查

帮助调用方在商定的范围内交付一个正确的改动。找出那些后果严重到值得处理的缺陷和改进点；按代码本来要实现的行为和项目要求来评判，而不是按你自己偏好的重写方式。即使改动很小，严重的缺陷依然重要。一个合格的改动，可以一条发现都没有。

**完成标准：** 必需的审查和验证都完成了，保留下来的每条发现都有源代码作为依据，并且调用方拿到一个清楚的结果，里面写明了还有哪些地方没覆盖到。只有在调用时授权了、并且符合下面的规则时，才应用修改。

## 产物根目录

<!-- ce-docs-root:start -->
**在拼出任何产物路径之前，先确定 CE 产物根目录 `<root>`。**

- **读取：** 只从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取。没有设置时，`<root>` 就是 `docs`，和以前完全一样。
- **校验：** 如果设置了值，它必须是一个相对于仓库的目录，它的真实路径（把符号链接 symlink 解析之后）要在仓库里面，而且既不能是仓库根目录，也不能在 `.git/` 下面。否则就报错停下，报错里写明 `docs_root` 和它的值——绝不要退回用 `docs`。
- **使用：** 把 `<root>` 作为唯一的产物存放位置：不存在就创建；每个路径都拼成 `<root>/<subdir>`，用这个 skill 自己的子目录；绝不要同时再去读 `docs`。

## 执行主线

按顺序做下面这些步骤；参考文件提供细节，但从不改变顺序。进入某一步时，读管这一步工作的参考文件；在这一步之前读过不算数；只是交给下层子智能体（leaf）去读的参考文件，不算你读过。

1. 先读 `references/modes-and-output.md`。它确定参数、参数冲突怎么处理、“快速审查”的捷径、审查深度关卡，以及这次调用要返回什么。
2. **Stage 1（第 1 阶段）。** 读 `references/scope.md`，确定要审查的改动、范围模式，以及确定性的范围信号。然后在 Stage 2 之前应用那个审查深度关卡。lite（轻量）深度会直接结束运行，不再读后面主线的参考文件；lite 和 focused（聚焦）两种深度都按 `references/depth-paths.md` 在当前上下文里运行。
3. **Stage 2。** 读 `references/intent-and-plan.md`，写出每个审查者都会收到的“意图摘要”，并找到 Stage 6 用来核对需求的那份计划。
4. **Stage 3。** 读 `references/persona-catalog.md` 和 `references/select-and-route.md`，然后根据改动的风险选出需要的审查者（persona，指扮演不同审查角色的子智能体），找到适用的规范文件，并决定对抗式审查（adversarial review，专门挑刺、找最坏情况的审查）怎么进行。
5. **Stage 3d。** 如果对一个本地的待审代码选了对抗式审查，就在**派发任何本地审查者之前**，启动并保存 `references/cross-model-review.md` 规定的、经过认可的跨模型任务（cross-model，就是交给另一个 AI 模型做的审查）。只要你已经按要求说明了接收方是谁、哪些代码会离开本机，调用这个 skill 本身就等于授权使用已配置或在允许名单里的对等路线（peer route）。不要再让用户确认第二次，也不要因为用户没重复授权就跳过这个对等审查。如果用户明确禁止外部审查，或者代码仓库设置了 `cross_model_review_mode: off` 并且当下没有主动开启，就以这些为准；这两点都要在绑定路线之前确定。一旦对等审查启动了，它就在这一阶段代替本地的对抗式审查者；只有在确定范围、允许名单、连接、认证或启动真的失败时，本地的备用审查者才会留在名单里；后面的阶段仍可能在那个参考文件说明的条件下恢复本地审查者。
6. **Stage 4。** 读 `references/dispatch-reviewers.md`。把选中的本地审查者作为一批同时派发出去，在这一轮里收齐结果，批次大小以运行环境允许同时运行的智能体数量为上限。每个成功启动的审查者，只有拿到它的最终结果才算收回：合格的简洁返回就采用；工具报错或格式不对的输出，就记为审查失败；只有“已启动”的确认不算结果。对于异步回执，在那个参考文件规定的时限内，用运行环境的“阻塞等待收取”功能去收；超时还没收到的审查者就算失败。最终结果可能是调用的返回值、阻塞等待的返回值，或者运行环境发来的一条写明是哪次启动、并带有内容的最终消息；进度更新不算。如果已启动的工作没法可靠地收回，就把它停掉；对于已保存的对等任务（跨模型任务），在返回失败结果之前，按它的参考文件做清理；绝不要以“还在进行中”结束这一轮去等它。禁止把本地审查放到后台、靠轮询去等。跨模型对等审查是唯一允许在后台独立运行的工作，它可以和这批审查同时进行。
7. **Stage 5 和 6。** 所有审查者的结果都到齐后，按 `references/finish-input.md` 的规定写出“收尾输入”，并一直按那个参考文件做：它负责启动验证者（validator）和运行产物清单。按顺序派发它点名的两个下层子智能体，每个都以 `references/finish-review.md` 作为起始内容（由下层智能体从磁盘读取，你自己不打开）：先是一个“合并”子智能体，它把对等审查的发现合并进来一次，并从运行目录合并结果；然后，在你启动并收回它选定的验证者之后，再派一个“报告”子智能体来生成报告。这两个子智能体都不会再启动子智能体；所有子智能体都由你启动。把报告子智能体的返回内容原样作为这个 skill 的回复输出。绝不要直接根据审查者的原始产物自己综合结论，也绝不要在派发的上下文里自己合并或生成报告。在多智能体路径下，只输出这个 skill 的报告：不要再调用运行环境自带的发现或报告工具，那只属于“快速审查”捷径。

## 工作原则

- **默认只报告；绝不推送。** 单纯调用 `代码审查` 只产出发现，不应用修改。要进入应用阶段，需要 `apply:local`，或者调用时用户明确要求应用或修复这次审查的发现；已经废弃的 `mode:autofix` 标记两者都不算。`mode:agent` 从不修改代码，即使它嵌套在一个之后会应用发现的流程里。在任何模式下都绝不推送、开 PR 或提交工单。
- **不使用会等待回答的提问。** 绝不使用 `AskUserQuestion`、`request_user_input`、`ask_user` 或其他会等待回答的提问工具。从明确的标记、git 状态、PR 信息和对话中推断意图、计划和范围。把不确定的地方写在 Coverage（覆盖情况）或结论里——不要停下来问。
- **只做明确授权的修改。** 绝不运行 `gh pr checkout`、`git checkout`、`git switch` 或类似的切换分支命令。传入 PR 编号、网址或分支名，只是选择**审查范围**，不代表允许修改工作区。没提交的改动只能在保存着它们的那个代码副本里审查，所以要在功能分支上审查它们，就留在那个分支上（或者自己切过去），然后传入 `base:` 或不传目标。
- **报告结果，不报告内部机制。** 展示给用户的内容只关于审查本身：在检查什么、包含了哪些覆盖面、每个按条件加入的审查角度的一句话理由、独立的跨模型审查，以及发现。说用户认得出来的东西，比如 PR 编号、某个审查者关注的问题，或者某个对等模型。这个 skill 的内部标签、派发记录和准备过程的叙述，不要出现在给用户看的文字里。关于对等审查，绝不要说得比它的回执能证明的更多。这条规定的是你*展示和隐藏什么*，不是措辞；用你自己的说话方式。
