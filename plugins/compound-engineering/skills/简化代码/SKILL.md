把最近改过的代码变得更清楚、更多复用、质量更好、效率更高，同时保持行为完全不变。优先写好读、意思明确的代码，而不是紧凑的代码——行数少不是目标。


## Step 1：确定范围

按下面的顺序确定要简化的范围：

1. **用户点名的范围**说了算；不要扩大它。
2. **否则，如果在 git 里**，就用当前分支相对于它的基准分支（base）的改动。没有可用的基准分支时，就用已暂存和未暂存的改动（`git diff HEAD`）。
3. **不在 git 里或者没有改动时**，就用用户点名的文件，或者对话里之前编辑过的文件。

如果上面都得不到一个非空的范围，就停下来问用户要简化什么，而不是去猜。使用运行环境当前工具列表里已有的“会等待回答的提问工具”（按功能匹配，不按某个环境特有的名字）。工具出现在当前列表里，就证明它存在；绝不要为了确认它存不存在而去调用面向用户的提问工具。如果列表里有匹配的工具但还没加载，就用运行环境的“工具发现”功能把它加载进来——不要去找别的环境的工具名。只有列表里没有这种工具，或者真的调用时报错，才退回到在用户能看到的聊天界面里列出带编号的选项。绝不要悄悄跳过问题。

**预检查。** 如果范围里没有实质性的、人写的代码——只有文档、自动生成或第三方拷进来（vendored）的文件、依赖或锁文件（lockfile），或者机械性的改动——就报告没有可简化的东西，然后停下，不派审查者。范围里混着这些时，只保留代码部分。这个检查看的是改动的种类，从不看大小：明确指定的小范围照样要跑，任何大小或成本门槛都由调用方来定。

如果平台有任务跟踪功能，就展示审查、应用和验证的结果，但不要给每个审查者各建一个任务。否则就直接继续，不要在聊天里模拟一个任务清单。

## Step 2：同时启动 3 个审查智能体

通过平台的子智能体功能（Claude Code 里是 `Agent`/`Task`，Codex 里是 `spawn_agent`），在可用时派出三个通用子智能体——代码复用、代码质量、效率三个审查者；没有这个功能时，就在当前上下文里直接做或者一个一个做。对每个审查者，从这个 skill 的目录读出它的提示素材，把**文件的完整内容**作为子智能体的提示传过去，同时附上确定好的范围（完整的改动或文件集合），让它有完整的背景：

- `references/personas/code-reuse-reviewer.md`
- `references/personas/code-quality-reviewer.md`
- `references/personas/efficiency-reviewer.md`

不要凭记忆转述这些评审标准。每个文件都要读出来原样传过去，否则审查者会丢掉那些保证“行为不变”的规则。

**有限派发。** 把三个审查者排好队，运行环境同时能接受几个就启动几个。出现并发数或活动智能体数量上限的报错，说明运行环境满了，而不是审查者失败了：让它继续排队，等有空位再试。如果某次派发既等不到正在运行的工作结束、也没有支持的释放方式、改正调用方式也恢复不了，就用同样的提示素材在当前上下文里直接做那一轮审查，并说明做了这个替代。

**智能体的生命周期。** 在清理之前，先收齐所有最终结果，包括失败。如果运行环境提供由调用方负责的清理功能，就在补充空位、进入下一阶段或返回之前，关闭或释放审查用的智能体。不要给已经完成、没有剩余工作的智能体发消息。不要因为某个智能体完成了或被打断了，就推断它占的名额已经释放，也不要自己编造清理操作。

**选择模型。** 如果当前运行环境提供已知的覆盖设置，就给这些审查者用平台上均衡的中档模型。在 Claude Code 里就是 Sonnet 这一档。在 Codex 里，只有当前派发功能提供了明确的模型选择或自定义智能体选择时，才用这一档；光在任务描述里写不会换模型。否则就不设置覆盖，沿用上层的模型——用上层模型跑通一轮，胜过一次失败的派发。

**权限模式。** 派发调用时不要带 `mode` 参数，让用户自己配置的权限设置生效。

## Step 3：修复问题

只有三个审查结果都完成后——不管是子智能体返回的，还是在当前上下文里做出来的——才继续。值得改的发现直接应用；误报和价值不大的发现记为“已跳过”，不用问用户。

为了评估一条发现，需要时可以看范围以外的代码，但只编辑范围以内的代码，以及它需要的 import/export（导入/导出）行。如果范围是用户点名的文件或目录，那些 import/export 行也必须在这个范围里；会改到修改边界以外的修复，一律跳过。

每个修复都必须保持输出、报错、副作用和执行顺序不变。如果无法确认这一点，就跳过。

如果某个接口或数据结构只存在于当前还没发布的这批改动的早期版本里，那么在你核实了它在范围以外没有任何已部署的、已持久化保存的、公开的、外部的、依赖它的分支的、或仓库里的调用方之后，它就不算受保护的行为。只有当所有需要跟着改的调用方都在现有的修改边界之内时，才删除这条兼容路径；否则就保留它。

**绝不要把安全检查“简化”掉。** 保留信任边界上的校验、防止数据丢失的保护、安全检查，以及无障碍（accessibility）功能。任何会削弱或删除这些的发现，都跳过。

**遵守调用方传入的结构固定要求。** 带着“结构固定”（structure-pin）约束传进来的计划路径，是背景信息，不是范围。保留其中标为 `session-settled:` 的关键技术决定（Key Technical Decisions），包括有意的重复或有意的拆分。

## Step 4：验证行为没有变

运行整个项目的类型检查（typecheck）和代码风格检查（lint）。按影响范围（blast radius）运行测试：局部改动跑相关的测试，共享的或影响面广的改动跑更大范围的测试，测试工具不能按范围跑时就跑全部测试。

报告失败时，写明检查的名字和相关输出。由简化导致的失败，要么修好，要么撤回造成问题的那个改动；绝不要放宽断言、削弱类型或跳过测试。

如果项目没有配置测试、lint 或类型检查，就在总结里明确说出来；不要悄悄跳过验证。

## Step 5：总结

总结哪些地方本来就没问题，哪些地方改进了。按复用、质量、效率分别报告应用了几条；跳过了几条；以及各项检查的结果。如果什么都没改，就直说。不要用“净删了多少行”作为成功的标准。
