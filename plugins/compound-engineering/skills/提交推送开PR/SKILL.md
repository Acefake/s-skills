# Git 提交、推送和开 PR

**问用户时：** 使用运行环境当前工具列表里已有的“会等待回答的提问工具”（按功能匹配，不按某个环境特有的名字）。工具出现在当前列表里，就证明它存在；绝不要为了确认它存不存在而去调用面向用户的提问工具。如果列表里有匹配的工具但还没加载，就用运行环境的“工具发现”功能把它加载进来——不要去找别的环境的工具名。只有列表里没有这种工具，或者真的调用时报错，才退回到在聊天里提问；绝不要悄悄跳过问题。

## 模式

- **只写说明**——用户*只*要一份说明（“写/起草一份 PR 说明”、“描述一下这个 PR”、贴了一个 PR 网址或编号）。只做 Step 4，把结果打印出来。只有用户要求时才应用到 PR 上。把用户贴的 PR 引用传下去，让 Pre-A 确定改动范围。
- **更新说明**——刷新或重写一个已有 PR 的说明，不打算提交或推送。按下面“了解现状”的规则判断有没有 PR：退出码为 0 且结果是 `[]`，表示“没有打开的 PR”（报告后停下）；非零退出码表示**不知道**（先解决登录或网络问题，在弄清有没有 PR 之前停下）。**有打开的 PR 时**，对那个网址以 PR 模式做 Step 4，然后做 Step 5：预览、确认，再用 `gh pr edit` 应用。
- **完整流程**——其他情况：做 Step 1-5。如果用户的意图或偏好是要一组堆叠 PR（stack），就改进入**堆叠模式**。

**`mode:pipeline` 修饰符**，由 `全自动开发` 这类编排程序设置。以不交互的方式运行选定的模式，压下所有会等待回答的提问。每个被压下的提问都取保守的默认值：不重写已有的 PR；保留分支；目标分支（base）确定不了就停下，不去猜；“更新说明”的预览直接应用，因为这次调用本身就表示要应用。流水线下的堆叠模式只使用调用时给出的意图和范围，并把姿态（posture）传进交接里。

## 堆叠模式（需主动开启）

**只有主动要求才开启。** 当用户的意图或一贯偏好是要多个 PR 组成的堆叠（stack，一组前后依赖、逐层叠加的 PR）时才进入。明确要求堆叠是**必须照办的意图**——不要把它重新理解成一个自定义了 `--base` 的单个 PR。**不要**主动建议用堆叠 PR。当用户**没有**要求时，**拒绝**没有意义的堆叠（只有一个逻辑改动、硬切出来的分片），保持单个 PR。

在堆叠模式下，**在 Step 3 之前**加载 `references/stack-submit.md`，只照着它做探查、拓扑结构和事后拆分构建；那套逐层提交的流程代替普通的 Step 3。**不要在那里提交上去。** 由 Step 5 负责提交上去、`gh stack` 命令行工具依赖和遗留问题，以及交接姿态：默认是 `posture:stack-ready`，只有明确要求合并落地时才是 `posture:stack-land`，从**最底层的、打开的、非草稿**PR 开始。不要把 `posture:` 加进这个 skill 的 argument-hint 里。

## 了解现状

**在 Step 1 之前读 `references/context.md`。** 它规定了命令表、各退出码的含义、fork（复刻仓库）和游离 HEAD 的陷阱，以及 Step 1-2 用到的分支和 PR 判断方法。其中有两条规则也写在这里。绝不要问要不要建分支：如果是游离 HEAD，或者在默认分支上且有改动，就新建一个分支；如果在默认分支上但没有改动，就报告后停下。另外，用约定式提交（conventional commits）时，拿不准就默认用 `fix:` 而不是 `feat:`，除非用户另有要求。

这次运行受三条规则约束。

**每一次 `git` 和 `gh` 探查都是单独的、参数列表形式的调用**，收集信息和重新核实都一样，它的退出状态就是流程控制的依据。参考文件里给出了原因，并点名了这个 skill 固定使用的两种组合写法。

**探查结果只是一张快照。** 在每个有后果的操作之前——Step 3 的推送、Step 5 的创建——都要重新核实分支、远程仓库和 PR 的状态。

**只有对目标仓库（base repo）查询时退出码为 0 且结果为 `[]`，才表示“没有打开的 PR”。** 非零退出码表示**不知道**，绝不等于“没有”。在 fork 的代码副本上，用 `-R` 指向目标仓库，只传分支名，因为 `--head <owner>:<branch>` 会悄悄返回 `[]`。有结果时，**不要**盲目取第 0 个：要核对 head 的所有者和分支名，匹配不唯一就停下。记下那条结果的网址和正文——Step 5 用网址来决定走“已有 PR”路径，Step 4 会重写已有的正文。

## 产物根目录

开启归档（archival）时，确定一次 `<root>`：它会在 `<root>/explainers/` 下写一份说明文档。

<!-- ce-docs-root:start -->
**在拼出任何产物路径之前，先确定 CE 产物根目录 `<root>`。**

- **读取：** 只从 `<repo-root>/.compound-engineering/config.yaml` 读取 `docs_root`（`<repo-root>` = `git rev-parse --show-toplevel`）。不要从 `config.local.yaml` 读取。没有设置时，`<root>` 就是 `docs`，和以前完全一样。
- **校验：** 如果设置了值，它必须是一个相对于仓库的目录，它的真实路径（把符号链接 symlink 解析之后）要在仓库里面，而且既不能是仓库根目录，也不能在 `.git/` 下面。否则就报错停下，报错里写明 `docs_root` 和它的值——绝不要退回用 `docs`。
- **使用：** 把 `<root>` 作为唯一的产物存放位置：不存在就创建；每个路径都拼成 `<root>/<subdir>`，用这个 skill 自己的子目录；绝不要同时再去读 `docs`。

## Step 3：提交并推送

提交和推送的具体做法见 **`references/commit-and-push.md`**，默认分支的处理见 `references/branch-creation.md`。如果堆叠模式已经提交了各层，就直接跳到 Step 4；由 Step 5 把它们提交上去。

**项目的发布关卡。** 在发布提交之前，要满足所有适用的“推送前”或“可以审查”的要求，这些要求来自上下文里项目当前有效的说明和约定，以及管着这些已提交路径的其他范围性说明。只有对“正要发出去的这个确切提交状态”有效的证据才算满足；否则就在对外写入之前停下，报告缺了什么或什么没通过。没有这类要求就继续。

绝不用 `git add -A` 或 `git add .`。在 add 和 commit 两步里都写明文件名，让无关的已暂存文件留在外面。遵守 `exclude:<paths>`：不动这些文件，并在报告里说明。

## Step 4：写 PR 标题和正文

**你必须完整读 `references/pr-description-writing.md`**——它规定了标题和正文的内容规则，包括重写时要保留已有的 `Related:` / `Fixes` 这条规则。然后读 **`references/compose.md`**，里面是写之前要做的三个决定：证据决定；教学决定，其中 `pr_teaching_section` 默认**开启**，`pr_teaching_archive` 默认**关闭**，只有**有效的（没被注释掉的）**配置项才能改变它们；以及品牌标注决定：品牌标注默认**关闭**，**除非**这次调用带了 `branding:on`，或者用户在这次提示里要求加上 Compound Engineering 的品牌标注。

如果 Step 1 找到了已有的 PR，就把它的网址传给 Step 4，让 PR 模式去获取已有的正文。

## Step 5：应用并报告

应用、预览、归档和交接的做法见 **`references/apply-and-handoff.md`**。在 `gh pr create` 之前，再检查一次有没有 PR：有匹配的 PR 就走“已有 PR”路径，退出码 0 且结果 `[]` 就新建，非零就卡住。用 `--body-file <path>` 传正文，绝不用标准输入（stdin）——那样 `gh` 会以退出码 0 结束，但正文是空的。

**在这里判断是否完成。** 交互式的完整流程，或流水线下的堆叠提交，在 `ce-babysit-pr` 接手已发布 PR 的后续跟进之前，都**不算完成**。只报告 PR 网址不算成功。加载被调用的那个 skill 来选择监控模式。如果在本次会话里运行它，就一直进行到它的停止条件允许输出最终报告为止。

只有 `babysit:off`、CE 配置里的 `auto_babysit: false`，或者 `references/apply-and-handoff.md` 里的某种 "Do not fire"（不要触发）情况，才能跳过它。没有任何其他监控方式可以代替：不能用 `ci-watcher`，不能用 `gh pr checks --watch`，不能自己写轮询，也不能“以后再说”。如果 `ce-babysit-pr` 加载不了或启动不了，就停下并报告卡住了。
