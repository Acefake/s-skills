# 执行工作的命令

## 结果

- **产出：** 根据计划、需求规格或具体工作要求，得到一组完整实现、并在本地验证过的改动。
- **下一个使用者：** 单独使用时，由发布流程（shipping workflow）把验证过的改动送去审查和交付。在“返回调用方模式”（Return-to-Caller Mode）下，调用它的流程会收到结构化的实现和验证结果，剩下的关卡由那个流程负责。
- **完成标准：** 范围内的每个任务都完成了，必需的验证证据都记录了，相关检查都通过了，并且这次运行走到了以下之一：由它自己负责的发布交接（带有代码审查回执，或者明确的跳过说明——见 Phase 3-4）、一份完整的返回结果，或者一个明确的阻塞原因。
- **意图：** 把要求的功能做完，不重新讨论计划，也不把“正式合并代码”的权力交出去。干活的子智能体（worker）只拿到范围有限的单元；由主编排程序（host orchestrator）检查实际改动，并负责权威的验证和正式提交（canonical commits）。

## 执行流程

**附带的参考文件必须真的去读，绝不能凭印象。** 下面提到的每个参考文件或脚本路径，都要从这个 skill 已加载的 `SKILL.md` 所在目录去找，用运行环境给出的完整 skill 路径；绝不要在目标代码仓库里用通配符（glob）搜索来找附带文件。进入某个阶段时，读管这个阶段的参考文件；在这个阶段之前读过不算数；本文件说要再读一遍的参考文件，到了那一步要再读，哪怕它已经在上下文里。如果运行环境不给出 skill 目录，或者必需的文件读不了，就在它管的那个操作之前停下，报告缺了哪个文件。不要凭记忆重建它的规则；报告缺失的参考文件，而不是自己照常往下做。

### Phase 0：判断输入类型

**先判断是不是“恢复”请求。** 在把输入归类为计划、路径、空白或普通要求之前，先识别是不是要续做、查看、回收（reap）或清理一个已有的运行。恢复时绝不派新的 worker、不选新路线、不去找别的计划、不重跑已完成的验证，也不进入任何一条发布路径。如果缺少 run id（运行编号），就去问；绝不要猜一个。

在做任何其他输入判断之前，先读 `references/input-triage.md`。它决定了：来源怎么确定、控制标记（control token）、恢复、只读的探查、计划是否可以动手、非代码工作怎么转、空白输入，以及普通要求的规模判断。其中有三条规则在这里也成立：

- 如果普通要求很小（Trivial）——只涉及一两个文件，而且不改变程序行为——就跳过任务清单，但在写之前仍然要确定执行引擎。纯机械性的改动，发出去后也不用在 PR 之后盯着。只要其中任何一点拿不准，就走更完整的路线。
- 如果某个普通要求在本次会话里已经由 `做计划` 判断过规模，就直接执行，不再重新规划。需要用户权衡的决定，要作为问题去问，绝不要因此转回 `做计划` 或 `头脑风暴`。
- 如果那个参考文件读不了，就停下；绝不要把控制标记或不能执行的产物当成代码工作来做。

当判断结果选了“返回调用方模式”时，立刻读 `references/return-to-caller.md`，并记下：这次运行怎么结束由它决定。如果读不了，就在做任何修改之前停下；不要退回单独使用时的做法。

### Phase 1：快速开始

1. **准备工作区。** 在切换分支、编辑、派发或提交之前，先读 `references/workspace-setup.md`。它决定了：用哪个可写的代码副本（checkout）、计划里不清楚的地方怎么澄清、分支放在哪里、开工前的清点、已经有改动（dirty）的文件，以及任务的准备。没有可写的正式代码副本时绝不写入；除非用户在本次会话里明确要求，否则绝不在真正的默认分支上写。

   **用户没给出的东西，不要提交也不要发布。** 当某个单元需要一个本来就有改动的文件时，单独使用模式下要问一次：这个文件是包含进来还是排除。“返回调用方模式”既不问也不改它；而是返回 blocked，说明冲突在哪里以及怎么恢复。

2. **先定执行引擎，再定策略。** 在有限地读完计划、拆出任务之后，但在选定某个单元去执行、写入、派发或提交之前，先读 `references/execution-engines.md`，并完成它的路线选择。不管有没有明确的类型绑定，这一步都适用；只有当那个参考文件选择了“本地原生执行”，或者已经用完了允许的退回方案时，才可以本地原生执行。引擎的选择绝不会改变“这次运行怎么结束”由哪个参考文件决定。

   如果选了跨模型执行（cross-model execution，就是把部分工作交给另一个 AI 模型），在任何内容或权限交给另一个模型之前，先读 `references/cross-model-execution.md`。它规定了控制器初始化、初始化后锁定引擎、有限的数据外发、事务、恢复以及回执。

   在选择直接做（inline）、一个一个做（serial）还是同时并行做（parallel）之前，以及在派发任何 worker 之前，先读 `references/execution-strategy.md`。它决定了任务安排、隔离、每个 worker 拿到的工作包、worker 的生命周期，以及怎样把结果合在一起。权威的验证和正式提交始终由主编排程序负责。

### Phase 2：执行

在第一次写实现代码之前（包括走 Trivial 路线时），先读 `references/implementation-loop.md`。它决定了：怎样选择证据、怎样验证、什么时候停止一个单元、分步提交、沿用已有的写法、持续测试、简化做到哪里为止、界面（UI）工作、进度跟踪，以及已定决定。

本文件里的提交规则全程有效：每一次实现提交，都只包含这个单元自己负责的文件。直接运行 `git commit` 可能会把用户原来暂存区（index）里的东西一起提交进去，所以禁止这样做。

### Phase 3-4：质量检查和收尾

任务和本地验证都完成后，单独使用模式下，在做任何质量检查或交付之前，先读 `references/shipping-workflow.md`。它决定了：简化、代码审查回执和退回方案、遗留的发现、最终验证，以及交付。

**代码审查完成关卡（只适用于单独使用）。** 发布前必须真的做代码审查。在发布参考文件记录下一份真正完成的 `代码审查` 回执，或者它规定的某种确切的授权跳过状态之前：这次运行不算完成，不能调用提交或发布的 skill，也不能报告发布已完成。绝不要用“在脑子里自己审一遍”或“之前已经应用过的发现”来代替。这条规则不适用于“返回调用方模式”。

## 返回调用方模式（Return-to-Caller Mode）

“返回调用方模式”只做实现和本地验证。它不能进入 Phase 3-4，也不能做最终简化、代码审查、创建 PR、盯 CI（持续集成检查）、照看 PR（babysitting）或其他任何单独使用时的发布操作；这些步骤归调用方负责。

就在输出结果之前，再读一遍 `references/return-to-caller.md`。只有它规定了完整的返回结果、证据是否齐全的检查、路线和模型的记录、恢复的含义，以及 `standalone_shipping_skipped: true`。不要只根据本文件拼出完整结果。

如果在规划或实现已经产生了状态之后，这次必需的读取失败了，就保留每一个改过的文件、提交、工作区和控制器记录。按本文件返回最少的 blocked 结果：`status: blocked`、`plan_path`、已知时的 `run_id`、`changed_state`、写明缺失参考文件的 `blockers`，以及 `recovery_path`。不要抹掉做了一半的状态，不要报告成功，也不要掉进单独使用时的发布路径。
